# Slurm macOS / Apple Silicon Native Port 要件定義

SchedMD/SlurmをApple Silicon搭載macOS上でネイティブ動作させるためのFeature Specを作成してください。

今回は**要件定義フェーズのみ**を実施してください。

まだ実装を開始しないでください。
`design.md`および`tasks.md`の作成にも進まず、まず`requirements.md`を完成させ、要件の妥当性・整合性・実現可能性をレビューできる状態で停止してください。

---

# 1. プロジェクト目的

現在Linuxを主対象としているSchedMD/Slurmを修正し、Apple Silicon搭載macOSをSlurmノードとして利用可能にすることを目的とします。

最終的には以下を目指します。

1. macOS上でSlurmをネイティブビルドできる
2. macOS上でSlurm CLIを利用できる
3. macOS上で`slurmd` / `slurmstepd`を動作させられる
4. SlurmジョブをmacOS上で実行できる
5. CPU・メモリをSlurmリソースとして管理できる
6. M5 Max内蔵Apple GPUをGRESとして管理できる
7. Linux版Slurmとのプロトコル互換性を維持する
8. 可能な限りSchedMD upstreamへ提出可能な設計・実装とする

単に「コンパイルが通る」ことを成功条件にしてはいけません。

ジョブ投入、プロセス管理、ジョブ終了、Plugin状態共有、ユーザー権限、リソース認識などが正しく動作することを最終的な成功条件としてください。

# 7. 最重要課題：Slurm Plugin Architectureとdyld

これは本プロジェクトの最優先課題です。

過去のmacOS対応PRがmergeされなかった最大の理由として、SchedMD側から以下の問題が指摘されています。

Linux/ELF環境ではSlurm pluginが親binary側に存在するsymbolやglobal stateを暗黙的に参照する設計があります。

しかしmacOSのdyldでは同じsymbol inheritanceを保証できず、

```text
slurm_conf
```

などの重要なglobal dataがplugin側から正しい親processの状態を参照できない可能性があります。

つまり、

```text
コンパイル成功
↓
pluginロード成功
↓
しかしplugin内部のslurm_confが空または別状態
↓
一見動作するが内部的には壊れている
```

という最も危険な状態が発生する可能性があります。

## 必須要件

macOS対応を「成功」と判定する前に、

**Pluginが親Slurm processと正しいruntime stateを共有できること**

を証明可能にしてください。

少なくとも以下を対象に調査してください。

```text
src/common/plugin.c
plugin_load_from_file()
plugin_load_and_link()
plugin_context_create()
dlopen()
dlsym()
RTLD_LAZY
RTLD_GLOBAL
strong_alias
weak symbol
weak_import
slurm_conf
```

## 要件定義では

この問題について、

- 原因
- 影響範囲
- affected plugins
- Linux/ELFとDarwin/Mach-O/dyldの差
- 必要となるarchitectural change
- backward compatibility
- plugin ABIへの影響

を明確にしてください。

まだ解決方法を1つに決めないでください。

例えば設計フェーズでは、

- explicit plugin context
- accessor API
- host API table
- plugin init API拡張
- shared runtime state library
- symbol export方式変更

などを比較する可能性があります。

ただし、Linux plugin ABIを不要に破壊する設計は禁止します。

# 8. cgroupをmacOSへ無理に移植しない

現行SlurmはDarwinではcgroup supportを無効化しています。

macOSにはLinux cgroup v1/v2と同等の機構がありません。

したがって、

```text
task/cgroup
proctrack/cgroup
jobacct_gather/cgroup
```

をmacOS上でLinuxと同じ形で実装することを前提にしてはいけません。

Darwin向け代替機構を定義してください。

# 9. Process Tracking要件

`proctrack/pgid`を調査してください。

現在の実装ではFreeBSD以外で`/proc`を参照してPID一覧を取得するコードが存在します。

macOSにはLinuxの`/proc`が存在しないため、そのままでは利用できません。

macOSではpublic APIを利用したDarwin backendが必要です。

候補として、

- libproc
- `proc_listpids`
- `proc_pidinfo`
- sysctl / KERN_PROC
- POSIX process group

等を調査してください。

ただし要件定義段階では実装方法を固定しません。

## 必須動作

```text
sbatch
 └─ shell
     ├─ process A
     │   └─ process B
     └─ process C
```

のようなprocess treeについて、

```bash
scancel <jobid>
```

実行後、

- shell
- child
- grandchild

を含め、Slurm管理対象processが残存しないこと。

PID漏れやorphan processを許容しないこと。

---

# 10. CPU Affinity要件

Linux版Slurmの`task/affinity`は`sche​d_setaffinity()`等に依存しています。

macOSにはLinuxと同等のCPU affinity APIがありません。

Apple Siliconはさらに、

- Performance Core
- Efficiency Core

というheterogeneous core構成を持っています。

したがって、Linuxと同等のCPU bindingができると偽装してはいけません。

特に、

```c
sched_setaffinity(...)
{
    return 0;
}
```

のような「成功したように見せるstub」は禁止します。

MVPでは、

```text
TaskPlugin=task/none
```

を許容する案も含め、

- exact CPU binding
- advisory affinity
- unsupported
- future extension

を区別した要件としてください。

# 12. Unified Memory

M5 MaxはCPUとGPUでUnified Memoryを共有します。

したがって、

```text
CPU RAM
GPU VRAM
```

を完全に独立したmemory poolとして扱わないでください。

`RealMemory`としてSlurmが管理するmemoryとApple GPU利用時のUnified Memory消費の関係を明記してください。

初期実装ではGPU専用memory quotaを保証しないことを許容します。

# 14. UID / GID / privilege処理

これはSecurity Requirementです。

Linux固有の、

```text
setresuid()
setresgid()
```

等を単純なshimへ置き換えてはいけません。

Slurmはroot daemonからjob userへcredentialを切り替えるため、ここを誤るとprivilege escalationにつながります。

最低限、

- UID
- primary GID
- supplementary groups
- effective UID/GID
- saved UID/GID相当の意味
- privilege drop
- privilege regainの可否

を確認してください。

Acceptance Testには、

```bash
id
id -u
id -g
id -G
whoami
```

を含めてください。

root権限が不正に残らないことを必須条件としてください。

# 16. Apple GPU / GRES

M5 Max内蔵Apple GPUをSlurmからresourceとして扱えるようにすることを最終目標とします。

ただしCPU/macOS portとApple GPU supportを同時に完成させる必要はありません。

段階化してください。

## GPU Phase 1

M5 Max内蔵GPUを、

```text
Gres=gpu:apple:1
```

のような**1 logical Apple GPU resource**としてstatic registrationできること。

GPU core数をGPU個数として登録してはいけません。

例えば40 GPU coresだから、

```text
gpu:40
```

とする設計は禁止します。

GRES countとGPU execution coresは別概念です。

## GPU Phase 1 Acceptance

例えば、

```bash
sbatch --gres=gpu:apple:1 job.sh
```

を投入した場合、

Slurm schedulerがApple GPU resourceを正しくallocateできること。

exclusive設定の場合、同一GPUを要求する別jobがresource releaseまで待機すること。

## GPU Phase 2

Apple GPU autodetectionを検討してください。

候補：

```text
AutoDetect=apple
gpu/apple
```

Appleのpublic APIのみを利用してください。

候補：

- Metal
- Metal Performance Shaders
- IOKitのpublic API
- system information API

private frameworkへの依存は禁止します。

## 注意

macOSにはNVIDIA CUDAの

```text
CUDA_VISIBLE_DEVICES
```

と同等の標準GPU isolation mechanismがありません。

したがって、

```text
GRES allocation
```

と

```text
kernel-level GPU isolation
```

は別物として要件化してください。

「Slurmがallocateしたから他jobからGPUを使用できない」と誤認してはいけません。

# 21. Linux regression禁止

macOS対応のために既存Linux版Slurmを壊してはいけません。

これは必須Non-Functional Requirementです。

既存Linux buildについて、

- x86_64
- arm64

へのregressionを起こさないこと。

可能な限り、

```c
#ifdef __APPLE__
```

を無秩序に各所へ追加する方式を避け、

OS abstraction layerまたは既存portable wrapperを利用してください。

---

# 22. Compatibility shimのルール

missing APIに対しcompatibility shimを実装する場合、

元APIと意味的に同等であることを確認してください。

特に以下はSecurity / Correctness上重要です。

```text
setresuid
setresgid
fexecve
accept4
pipe2
eventfd
timer_create
sched_setaffinity
```

「コンパイルを通すためだけに成功を返すdummy implementation」は禁止します。

実現不能なら、

```text
unsupported
```

として明示的にエラーを返す方を優先してください。

---

# 23. Public APIのみ利用

macOS実装では原則としてAppleが公開しているAPIのみを利用してください。

private APIや非公開frameworkへの依存は禁止します。

理由：

- OS updateで壊れる
- code signing
- SIP
- security
- upstream acceptance

への悪影響が大きいためです。

---

# 24. Upstreamability

可能な限りSchedMD upstreamへ提出可能な変更としてください。

要件として、

- Linux behaviorを変更しない
- OS-specific codeを分離
- portability abstractionを優先
- unnecessary forkを避ける
- coding styleを既存Slurmに合わせる
- plugin ABIを不用意に破壊しない
- regression testを追加する

を含めてください。

# 26. MVPの定義

最初のMVPでは、以下で構いません。

```text
Linux slurmctld
        │
        │ Slurm protocol
        ▼
macOS native slurmd
        │
        ▼
macOS native slurmstepd
        │
        ▼
macOS process
```

MVPでは以下を許容します。

```text
ProctrackType=proctrack/pgid
TaskPlugin=task/none
JobAcctGatherType=jobacct_gather/none
```

ただし`proctrack/pgid`にはmacOS用の正しいprocess enumerationが必要です。

MVPでcgroup相当の完全resource isolationを要求しません。

Apple GPUについても最初はstatic GRESで構いません。

---

- MIG相当機能

ただし将来拡張としてrequirementsに記録してください。

# 29. EARS形式

Kiro Feature SpecのEARS形式を利用してください。

例：

```text
WHEN slurmd starts on macOS 26.5.2
THE SYSTEM SHALL detect the Apple Silicon CPU and installed memory without relying on Linux /proc or /sys interfaces.
```

```text
WHEN a Slurm plugin is loaded by dyld
THE SYSTEM SHALL provide the plugin with the same runtime configuration state that the equivalent plugin observes on Linux.
```

```text
WHEN a job is cancelled
THE SYSTEM SHALL terminate all Slurm-managed descendant processes without leaving orphaned job processes.
```

```text
WHEN CPU affinity cannot be enforced with Linux-equivalent semantics
THE SYSTEM SHALL report the feature as unsupported rather than returning a false success result.
```
