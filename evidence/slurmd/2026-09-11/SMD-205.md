# SMD-205 GRES設定不一致

- 状態: `PASS`
- 対象: Apple M5 Max / arm64 / macOSの`slurmd`登録経路
- Slurm: `26.11.0-0rc1`
- production設定変更: Phase Bでworker `gres.conf`を一時変更し、byte/hash/metadataを完全復元

## Research Question

controllerがPC-210に`gpu:apple:1`を構成している状態で、workerがGPU deviceを0件として
登録した場合、controllerは不足を検知してnodeを利用可能な`IDLE`にせず、production
`gres.conf`復元後に安全に再登録・復旧できるか。

## 同梱sourceからの期待動作

`src/interfaces/gres.c`の`_node_config_validate()`は、slurmdが報告するGRES countが
controller設定値より小さい場合、次のreasonを構築して`EINVAL`を返す。

```text
gres/gpu count reported lower than configured (0 < 1)
```

callerの`src/slurmctld/node_mgr.c`は`gres_node_config_validate()`の失敗時に
`NODE_STATE_INVALID_REG`を付け、既にDOWN/DRAIN/FAILでなければ同じreasonでnodeをDRAINする。
したがって期待状態は`INVAL`を含むDRAINであり、workerが0件を報告しているのにcontrollerがnodeを
通常の`IDLE`としてGPU jobへ割り当てる動作は反証条件である。

一方、worker側でcontroller設定より多いGRESは`Ignoring excess count`として切り詰める実装なので、
不足countの方が本試験の拒否動作を一意に観測しやすい。最初のphaseではproductionを変更せず、
一時directoryのconfigでこの不足状態を`slurmd -G`に再現する。

## Phase A: 読み取り専用preflight

Phase Aはproduction `slurm.conf`、`gres.conf`、launchd plistのhash、controller/node/queue、
launchdとpidfileのslurmd identityを保存する。その後、`/tmp`にconfig copyと空の`gres.conf`を作り、
productionとcandidateの`slurmd -G`結果を比較する。daemon restart、controller update、job投入、
production file変更は行わない。

PC-210のroot shellで実行する。

```bash
sudo env SMD205_GRES_PREFLIGHT_CONFIRMED=YES /bin/sh \
  /Users/REDACTED_USER/dev/slurm.26-05/contribs/macos-tests/smd205_gres_mismatch_preflight.sh
```

併せてUbuntu controllerのroot shellで権威設定を読み取る。

```bash
date --iso-8601=seconds

grep -nE \
  '^[[:space:]]*(GresTypes|AccountingStorageTRES)=' \

grep -nE \

```

## Phase A Attempt 1 — HARNESS_FALSE_NEGATIVE_MISSING_CANDIDATE_KEY_PATH

2026-09-11 22:31 JSTの初回preflightは、production `slurmd -G`で
`gpu:apple:1 File=/dev/null`を確認した後、candidate実行が次のfatalで停止した。

```text
fatal: auth/slurm: cannot stat '/tmp/slurm-smd205-preflight-20260911T223116/candidate/slurm.key': No such file or directory
```

candidate用に`SLURM_CONF`を`/tmp`へ切り替えたため、`get_extra_conf_path("slurm.key")`も
candidate directoryを基準にした。空`gres.conf`の評価前に停止しており、GRES mismatch機能の
失敗ではない。production controllerはUP、nodeはIDLE・CPU/memory割当0、queue空だった。
実行前slurmd PIDは75048で、preflightはdaemon操作やproduction file変更を行っていない。

修正版はkeyを`/tmp`へ複製せず、candidate commandに限って既存production keyを
`SLURM_SACK_KEY=/opt/slurm/26.11.0/etc/slurm.key`で参照する。またUbuntu static config確認用の
初版grepは`NodeName=PC-210`選択肢にも末尾`=`を要求する誤りがあり、NodeName行を別grepへ分離した。

生Evidence: [`SMD-205-preflight-attempt1.txt`](SMD-205-preflight-attempt1.txt)

Attempt 1判定は`HARNESS_FALSE_NEGATIVE_MISSING_CANDIDATE_KEY_PATH`。修正版preflightのruntimeは
未測定なので、この時点ではSMD-205を合格にしなかった。

## Phase B: 実registration mismatch試験案

Phase Aの証拠確認後、別途明示承認を得て次を行う。Phase B driverは作成・実行前に、現在の
production `gres.conf`をmetadata付きでbackupし、controllerが`gpu:apple:1`を期待したまま、
workerのdevice recordだけを一時的に0件へする。

1. nodeが`IDLE`、queue空、割当0、controller UP、launchd管理PID一致を確認する。
2. `/opt/slurm/26.11.0/etc/gres.conf`をbackupし、空のdevice recordへ一時置換する。
3. launchd管理下のslurmdをclean restartし、controllerのnode state/reasonとworker/controller logを保存する。
4. nodeが通常のGPU nodeとして`IDLE`にならず、GPU jobが開始されないことを確認する。
5. 元の`gres.conf`をbyte/hash/owner/modeごと復元し、slurmdを再起動する。
6. 必要な場合だけ`State=RESUME`し、`Gres=gpu:apple:1`、CfgTRES、IDLE、割当0を確認する。
7. 既存MLX smoke jobを1件実行し、GPU count、accounting、終了後の資源/process回収を確認する。

Phase B driverを次に作成した。

```text
contribs/macos-tests/smd205_gres_registration_mismatch_driver.sh
SHA-256: 1d6956f3dce05e687e491eb08bcf70f87a575bd9c121bbb68b7329049fd77579
```

driverは次を機械検証する。

- `SlurmdParameters=config_overrides`が有効ならproduction変更前に停止
- production 3 fileのhash、`gres.conf`のowner/group/mode、launchd/pidfile identity
- mismatch時の`DRAIN`と`INVALID_REG`、reasonの`0 < 1`
- `gpu:apple:1`要求jobが5回連続PENDINGでpayload markerを作らないこと
- pending job cancelとaccounting
- production `gres.conf`のbyte/hash/metadata完全復元
- restored slurmdの再登録、必要時だけのRESUME、既存MLX Apple GPU smoke
- generic/typed GPU ReqTRES/AllocTRES、最終IDLE・割当0・queue/step残留0

失敗trapは保存backupからGRES fileを戻し、launchd service再起動、登録確認、必要時RESUMEを試みる。
実行にはproduction `gres.conf`の一時置換、slurmd 2回restart、PENDING jobの投入/cancel、復旧後GPU
jobの投入が含まれるため、次のcommandは明示承認後だけ実行する。

```bash
sudo env SMD205_REGISTRATION_MISMATCH_CONFIRMED=YES /bin/sh \
  /Users/REDACTED_USER/dev/slurm.26-05/contribs/macos-tests/smd205_gres_registration_mismatch_driver.sh
```

`/bin/sh -n`、approval gateのexit 64、command path、production write箇所、`git diff --check`を
静的確認した。Phase B runtimeは未実施である。

## Phase B実測 — PASS

2026-09-11 22:48 JST、PC-210のroot shellから承認済みdriverを実行した。production
`gres.conf`を一時的にdevice record 0件へ変更してslurmdをrestartすると、PIDは
75048から91700へ変わり、controllerは次を返した。

```text
State=IDLE+DRAIN+INVALID_REG
Reason=gres/gpu count reported lower than configured (0 < 1)
```

worker logにも`Ignoring file-less GPU gpu:apple from final GRES list`が記録された。
GPUを要求したJob 408は`PENDING`のまま、`RunTime=00:00:00`、`AllocTRES=(null)`で、
専用payload markerを作成しなかった。cancel後のaccountingは`CANCELLED by 0|0:0`だった。
したがって、workerがGPUを0件として報告した状態でGPU jobを誤実行する反証条件は発生しなかった。

元の`gres.conf`を復元してslurmdをPID 91811で再起動すると、INVALID_REGは消えた。
残っていたDRAIN reasonをdriverが明示RESUMEし、nodeは`IDLE`、CPU/memory割当0へ復帰した。
復元前後のproduction 3 file SHA-256は一致し、`gres.conf`はbackupとの`cmp`が0、metadataも
`root:1002:0644`で一致した。

復旧後のJob 409はUID/GID 3001でApple M5 Max、MLX 0.32.2を使用し、
`gpu_smoke_test=PASS`、stderr 0 byte、job/batchとも`COMPLETED 0:0`だった。jobの
ReqTRES/AllocTRESとbatch AllocTRESには`gres/gpu=1`と`gres/gpu:apple=1`が記録された。

22:50:55 JSTの独立readbackでは、launchd serviceはrunning、PID 91811、PPID 1、
last exitなし、controller 6817接続成功、controller UP、node IDLE、割当0、queue 0、
slurmstepd残留なしだった。よってSMD-205を`PASS`とする。

生Evidence: [`SMD-205-pass.txt`](SMD-205-pass.txt)

## 安全境界

- Ubuntu controllerのstatic configは変更しない。
- GPU job実行中には行わない。
- test対象はworkerの報告不足1ケースであり、type名やcontroller countを同時に変更しない。
- 復元不能、複数slurmd、nodeが予期せずjobを受理、またはcontroller通信異常が出たら停止する。
- Phase Aの結果だけではregistration拒否を`PASS`にしない。実registrationと復旧jobが必要である。

preflight driver SHA-256:

```text
a6d8ed26b6aa2ac51c3df6909f92ccd8bf71a7e55e715fcc9b275e4bb7b2af9b
```

`/bin/sh -n`、approval gateのexit 64、`git diff --check`を確認済み。Phase A Attempt 2のruntimeは
`PASS_PHASE_PREFLIGHT`であり、生Evidenceは`SMD-205-preflight-pass.txt`に保存した。

## 未確認事項・Evidence境界

- controller stateとreasonは`scontrol`の権威readbackで確認したが、同時間帯のUbuntu
  `slurmctld` journalはrun directoryへ複製していない。これは追加 corroborationであり、
  SMD-205の成功条件を未測定にはしない。
- 既知の`_core_spec_init: not supported on macOS`とhttp parser plugin診断は両restart時にも
  出たが、登録・job・復旧を妨げなかった。対応可否は別のnegative/optional項目として扱う。
