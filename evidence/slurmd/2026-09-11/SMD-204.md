# SMD-204 GRESなしMLX jobとの競合

- 状態: `PASS`
- 対象: Apple M5 Max / arm64 / macOSの`slurmd`・`slurmstepd`
- Slurm: `26.11.0-0rc1`
- GPU tool: 既存MLX 0.32.2 smoke job
- production設定変更: なし

## Research Question

Slurmで`gpu:apple:1`をGRES登録しても、GRESを要求しないjobから同じMetal GPUへアクセスできるか。
アクセスできる場合、GRES要求jobと同時にMLX処理が成功するか、scheduler/accountingはその利用を
どのように扱い、短時間の実測値と終了後の資源回収はどうなるか。

## 仮説

`File=/dev/null`を使うApple GPU GRESはscheduler-visibleなcountであり、Metal deviceへの
kernel-level access controlではない。したがって、GRES要求jobがRUNNINGでも、CPU/memoryに空きが
あればGRESなしjobもRUNNINGとなり、`SLURM_JOB_GPUS`なしでMLXから同じGPUを利用できると予想する。

予想が正しい場合、両jobのMLXは成功する一方、accountingでGPU TRESが記録されるのはGRES要求job
だけである。これは試験としては観測成功だが、GPU isolationとしては制約の確認である。

## 実験設計

新しいGPU計算toolは作らず、SMD-203まで使用した既存
`/opt/slurm/26.11.0/share/macos-gpu-job/mlx_gpu_smoke.sbatch`を呼び出す。

1. GRESなしbaseline jobで同じMLX smokeを3回実行する。
2. `--gres=gpu:apple:1` jobとGRESなしjobを投入し、両方をbarrierで待機させる。
3. 両jobが同時に`RUNNING`であることを保存後、共通barrierを解放する。
4. 各jobで既存MLX smokeを3回実行する。
5. GPU device、全結果、平均kernel時間、accounting、worker log、process/資源回収を保存する。

各jobは2 CPU、4 GiB、最大3分で、合計4 CPU・8 GiBを使用する。baselineを含めGPU smokeは
合計9回。温度・電力・長時間性能はSMD-207の対象であり、この試験から一般化しない。

## 成功条件

- baseline、GRES要求、GRESなしの3 jobがすべて`COMPLETED 0:0`
- concurrent 2 jobがbarrierで同時に`RUNNING`
- 全9回がApple M5 Max / `Device(gpu, 0)` / finite result / smoke PASS
- GRES要求jobだけに`SLURM_JOB_GPUS=0`とgeneric/typed GPU TRESがある
- GRESなしjobはMetalを使えても`ReqTRES/AllocTRES`にGPUを持たない
- baselineとconcurrentの平均`elapsed_seconds`および比率を保存する
- 最終nodeが`IDLE`・割当0、queue・slurmstepd・payload残留0、slurmd PID維持

この成功はGPU isolationの成功を意味しない。GRESなしjobがGPUを使えた場合は
`UNMANAGED_GPU_ACCESS_CONFIRMED`として明示する。

## 実行command

PC-210のroot shellで、queueが空であることを確認して実行する。

```bash
sudo env SMD204_GPU_COMPETITION_CONFIRMED=YES /bin/sh \
```

## 実行結果 — PASS

2026-09-11 22:21 JSTにproduction構成で実行した。baseline Job 402、GRES要求Job 403、
GRESなしJob 404はすべて`testuser`（UID/GID 3001:3001）で実行され、jobとbatchは
`COMPLETED 0:0`となった。全job stdout/stderr、`sacct`、barrier時のqueue/node/job、
worker log、終了後のnode/processを保存した。

生Evidence: [`SMD-204-pass.txt`](SMD-204-pass.txt)

### 同時実行と資源割当

barrier解放前にJob 403とJob 404は同じPC-210上で同時に`RUNNING`だった。

```text
403|RUNNING|PC-210|PC-210
404|RUNNING|PC-210|PC-210
```

この時点のnodeは`MIXED`、`CPUAlloc=4`、`AllocMem=8192`で、Slurm上のGPU割当は
`gres/gpu=1,gres/gpu:apple=1`だけだった。Job 403には
`TresPerNode=gres/gpu:apple:1`があり、Job 404には`TresPerNode`もGPU TRESもなかった。
それでも両jobはepoch 1789132918にMLX処理を開始し、同じApple M5 Maxを使用して完了した。

### MLX結果

| case | GRES要求 | `SLURM_JOB_GPUS` | 実測秒（3回） | 平均秒 | 結果 |
|---|---:|---|---|---:|---|
| baseline / Job 402 | なし | `not-configured` | 0.014467, 0.012046, 0.016292 | 0.014268 | 3/3 PASS |
| concurrent / Job 403 | あり | `0` | 0.012329, 0.017003, 0.017161 | 0.015498 | 3/3 PASS |
| concurrent / Job 404 | なし | `not-configured` | 0.014760, 0.012341, 0.013519 | 0.013540 | 3/3 PASS |

全9回でMLX 0.32.2、`Device(gpu, 0)`、`Apple M5 Max`、4096×4096行列を5 iteration、
`mean_value=1.023572e+03`、`gpu_smoke_test=PASS`を確認した。

baseline比はGRES要求jobが約`+8.62%`、GRESなし同時jobが約`-5.10%`
（driver表示のunmanaged/baseline比`0.949`）だった。ただし各case 3回、kernel時間12～17 msの
短時間測定である。processごとのwarm-up、OS/GPU scheduling、測定揺らぎを分離していないため、
GRES有無や競合による性能改善・劣化とは判定しない。ここで確認できるのは両jobが同時にGPU処理を
成功させた事実と、そのときの短時間参考値までである。

### Accounting差

GRES要求Job 403だけがjobとbatchの割当にgeneric/typed GPU TRESを持った。

```text
403|testuser|COMPLETED|0:0|PC-210|billing=2,cpu=2,gres/gpu:apple=1,gres/gpu=1,mem=4G,node=1|billing=2,cpu=2,gres/gpu:apple=1,gres/gpu=1,mem=4G,node=1
```

GPUを実際に使用したGRESなしJobs 402/404には、`ReqTRES`・`AllocTRES`ともGPUが記録されなかった。
したがって`AccountingStorageTRES`でGPU count accountingを有効にしても、GRES未要求のMetal利用は
GPU使用として追跡されない。

### 終了後の回収

3 jobと全`sacct`のstderrは0 byte。worker logには3 jobのlaunchとstep completionがあり、
試験前後の`slurmstepd`、終了後のpayload/MLX process残留は0件だった。最終nodeは`IDLE`、
`CPUAlloc=0`、`AllocMem=0`、`AllocTRES`空で、slurmd PID 75048とstart timeを維持した。

## 判定と考察

成功条件をすべて満たしたためSMD-204を`PASS`とし、観測分類を
`UNMANAGED_GPU_ACCESS_CONFIRMED`とする。

これはGPU isolationの成功ではなく、現在のApple GPU GRESがSlurm scheduler内の要求job同士には
排他countを提供する一方、Metal device access自体を強制しないことの実証である。
`File=/dev/null`は実GPU deviceを表さないplaceholderであり、GRESなしjobやSlurm外processを
遮断しない。運用上GPU排他と完全なaccountingを必要とする場合、全GPU workloadへGRES要求を
強制するsubmission policy等を別途設計する必要がある。macOS上でLinuxのdevice cgroup相当の
強制隔離が可能であるとは、本試験では確認していない。
