# SMD-125 HealthCheckProgram

## 状態

`PASS`

## 対象と目的

- worker: Apple M5 Max / arm64 / macOS `PC-210`
- Slurm: `26.11.0-0rc1`
- controller: Ubuntu 24.04 / x86-64
- test user: `testuser=3001:3001`（復旧後smokeのみ）
- 対象: macOS `slurmd`による`HealthCheckProgram`起動、timeout、process group回収、
  明示DRAIN、設定復元、後続job

SMD-102のsecurity blockerはユーザー指示により保留中であり、本試験はその判定を変更しない。

## 仕様境界

同梱man pageでは、`HealthCheckProgram`はrootで実行されるが、非0終了だけでnodeを自動DRAIN
するとは定義されていない。DRAINや通知などのactionはprogram自身が明示的に実行する必要がある。
したがって本試験では次を分離する。

1. `success`: root identityと環境を記録し、exit 0。nodeがIDLEを維持することを確認する。
2. `nonzero`: program自身が`State=DRAIN Reason=SMD125_health_nonzero`を設定し、exit 42。
   slurmd error log、DRAIN reason、process終了を確認する。
3. `timeout`: program自身が`State=DRAIN Reason=SMD125_health_timeout`を設定した後に停止せず、
   `HealthCheckTimeout=3`でkillされること、PID=PGIDとprocess group残留なしを確認する。

各phase後にproduction configをbyte-for-byte復元してreconfigureし、必要な場合だけRESUMEする。
最後にtestuserのbatch smokeとaccounting、IDLE、割当ゼロ、queue空、slurmd PID維持を確認する。

## 起動経路

sourceでは、`HealthCheckNodeState=START_ONLY`の場合、通常のslurmd起動後に
`run_script_health_check(HC_HEALTH_UNKNOWN)`が呼ばれる。programには
`SLURMD_NODENAME`が渡り、controller登録前なので`SLURM_NODE_IS_HEALTHY`はunsetとなる。
programは`run_command()`によりrootで起動され、`HealthCheckTimeout`が`max_wait`として
指定される。timeout時のprocess groupにはTERM、続いてKILLが送られる。

同一PIDのreconfigureでは`SLURMD_RECONF=1`により`original=false`となるため、START_ONLY
health checkは実行されない。修正版はSMD-124で検証したlaunchd bootout/bootstrapを使い、
本当の通常起動を発生させる。

本試験はcontroller側の周期scheduler設定を変更せず、workerローカルのSTART_ONLY経路を
測定する。周期実行の時間精度は本試験のPASS範囲に含めない。

## 作成物

- `contribs/macos-tests/smd125_health_check.sh`
  - mode、node、health hint、epoch、EUID/GID、PID/PGIDをroot専用event logへ記録
  - failure phaseだけ明示的にDRAINを要求
- `contribs/macos-tests/smd125_health_check_driver.sh`
  - `success|nonzero|timeout`を個別実行
  - controller UP、node IDLE、割当ゼロ、queue空、slurmd PID、既存設定競合をpreflight
  - 一時設定を配置後、launchd正常停止・bootstrapで通常起動を発生
  - event、node state/reason、slurmd log、process残留を照合
  - production config復元、RESUME、smoke/accounting、最終資源を検証
  - 失敗時はconfigを復元するが、意図的DRAINは調査のため自動解除しない

## Phase A Attempt 1 — `HARNESS_FALSE_NEGATIVE_START_PATH`

2026-09-11 20:09 JST、同一PID 72770へのreconfigureは成功したがevent logは0 byteのまま、
次のguardで停止した。

```text
error: health-check begin event not observed or environment/identity mismatch
```

source確認により、reconfigure childは`SLURMD_RECONF=1`を受けて`original=false`となり、
health check呼出条件`if (original && ...)`を満たさないことを確認した。したがってこれは
HealthCheck failureではなく、START_ONLYがreconfigureでも動くと仮定したハーネス設計不備である。

cleanupはproduction configへ再reconfigureし、PID 72770のままstart time
`2026-09-11T20:10:12`、node `IDLE`へ復元した。backupとproduction configはSHA-256
`a820719e...2167`かつbyte比較0で一致した。Job投入、DRAIN要求、HealthCheck runtime測定は
行われていない。cleanupの「node may remain DRAINED」はsuccess modeには不正確だったため、
修正版でmode別メッセージへ変更した。

修正版は正しいlaunchd service/plist/PID/SACKをpreflightし、candidate config配置後に
bootout/bootstrapする。途中失敗時もproduction configを復元し、launchd serviceとnode応答を
復旧確認する。生Evidenceは
[`SMD-125-phase-a-attempt1.txt`](./SMD-125-phase-a-attempt1.txt)に保存した。
