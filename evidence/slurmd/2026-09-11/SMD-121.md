# SMD-121 Prolog failure/timeout

## 判定

- 状態: `PASS`
- 対象: PC-210 / macOS / arm64 worker上のproduction `slurmd`
- controller: ubuntu2504 / Ubuntu 24.04 / x86-64
- Phase A: Prologがexit 42を返す正常なfailure通知経路
- Phase B: Prologが5秒の`PrologTimeout`を超過するtimeout経路
- 前提: SMD-120の正常Prolog/Epilog lifecycleはJobs 358/359で`PASS`

## 仕様と現行設定

同梱の[`Prolog and Epilog Guide`](../../../doc/html/prolog_epilog.shtml)と
[`slurm.conf(5)`](../../../doc/man/man5/slurm.conf.5)では、compute-node Prologの非0終了またはtimeoutで
nodeをDRAINし、batch jobを可能ならrequeueする。`nohold_on_prolog_fail`が未設定ならrequeue後のjobをholdする。

source上も次の経路を確認した。

- [`src/slurmd/slurmd/req.c`](../../../src/slurmd/slurmd/req.c): Prolog statusを`ESLURMD_PROLOG_FAILED`へ変換し、credentialをrevokeしてcontrollerへ通知する。
- [`src/slurmctld/node_mgr.c`](../../../src/slurmctld/node_mgr.c): `ESLURMD_PROLOG_FAILED`のregistrationでnodeを`Prolog error`としてDRAINする。
- [`src/slurmctld/job_mgr.c`](../../../src/slurmctld/job_mgr.c): launch failureをrequeueし、`nohold_on_prolog_fail`がなければpriority 0のheld jobにする。
- [`src/common/run_command.c`](../../../src/common/run_command.c): timeout時はhookのprocess groupをkillする。

production worker configの関連値は次の通りだった。

```text
Prolog=ABSENT
Epilog=ABSENT
PrologFlags=ABSENT
PrologTimeout=ABSENT
EpilogTimeout=ABSENT
PrologEpilogTimeout=120
SchedulerParameters=requeue_on_resume_failure
nohold_on_prolog_fail=ABSENT
ForceRequeueOnFail=ABSENT
```

## 安全設計

非0終了とtimeoutを同じ実行で連続させない。各phaseは1 jobだけを投入し、次の順序で完結させる。

1. controller UP、PC-210 IDLE・未割当・queue空を確認する。
2. production configに既存hook、PrologFlags、個別timeoutがあれば上書きせず停止する。
3. configをbackupし、Phase Aではexit 42のPrologだけを追加する。
4. Phase Bでは無限loop Prologと`PrologTimeout=5`だけを追加する。
5. failure jobは明示的に`--requeue`とし、payload markerが作られないことを確認する。
6. node stateにDRAIN、reasonにProlog、jobにPENDING・priority 0・Restarts 1以上を確認する。
7. root専用hook logとworker logから、Phase Aではexit 42、Phase Bでは5000 ms timeoutを確認する。
8. held jobだけをcancelし、production configをbyte-for-byte復元して再reconfigureする。
9. DRAIN Evidence採取後に限り、対象nodeをRESUMEする。
10. post-recovery smoke job、accounting、最終IDLE・資源解放を確認する。

途中失敗時はconfigを復元するがnodeを自動RESUMEしない。failure原因を隠さないため、run directoryを確認してから
手動復旧する。

## Phase A Attempt 1 — BLOCKED_SAFE_PRECONDITION

2026-09-11 18:40:24 JSTの初回実行は、意図的なProlog failureを設定する前のIDLE
preflightで停止した。保存されたreadbackはcontroller UP、node
`DOWN+NOT_RESPONDING`、`CPUAlloc=0`、`AllocMem=0`、reason
`Not responding [slurm@2026-09-11T17:18:31]`だった。

power logでは17:05以降にMaintenance SleepとDarkWakeを繰り返し、18:38:50にHID Activityで
FullWakeしている。Attempt 1はFullWakeの約94秒後であり、controller側のnode stateがまだ復旧して
いなかった。18:44時点でlaunchdはPID 310をrunningとして保持し、slurmdはTCP 6818をLISTEN、
Macからubuntu2504:6817への接続も成功している。したがって現時点の分類はSMD-121 failure経路の
FAILではなく、sleep復帰後のprecondition未達である。

run directoryには`slurm.conf.before`、candidate config、job IDがなく、hook event logは0 byte。
production configのSHA-256はSMD-120復旧時と同じ
`a820719e43f0f31acb2be8bceb87c279d79b330dd8e4b817a88adafba6022167`であり、config変更、
failure job投入、意図的DRAINは発生していない。初版cleanupの「node may remain DRAINED intentionally」
はこの停止段階には不正確だったため、driverを次のように修正した。

- preflight failureに実stateを表示する。
- failure job投入前は「intentional failure injection前、job未投入」と明示する。
- failure job投入後だけ、意図的DRAINが残り得る旨を表示する。

修正版driverは`sh -n`が成功し、SHA-256は
`e3d6e28e44d6601868b8927b580c681d50a76435b0b1abc9dbb72d37b59502da`。
生Evidenceは[`SMD-121-attempt1.txt`](./SMD-121-attempt1.txt)に保存した。

18:47:13 JSTに、手動RESUMEやdaemon再起動なしで`IDLE`、`CPUAlloc=0`、`AllocMem=0`へ
自動復旧した。その後にqueue空、PID 310のTCP 6818 LISTENも再確認した。Phase Aは
`READY_TO_RETRY`とする。Phase BはPhase AのEvidence確認まで未着手のまま維持する。

## Phase B実行command

Phase Aとは別に、Prolog timeoutを1 jobだけで確認する。
Phase B実行前の再点検で、timeout logだけではprocess-group cleanupを直接証明できない不足を発見した。
timeout hookがPID/PGIDをroot専用event logへ記録し、driverがPID=PGIDとtimeout後の同PGID process不在を
確認するよう強化した。hookとdriverの`sh -n`、hook invalid-context exit 65、driver approval gate
exit 64、macOSの`ps`出力field順を確認した。current hashはartifact節に記録した。

```bash
sudo env SMD121_PROLOG_FAILURE_CONFIRMED=YES /bin/sh \
  /Users/REDACTED_USER/dev/slurm.26-05/contribs/macos-tests/smd121_prolog_failure_driver.sh \
  timeout
```

成功markerは`SMD121_PHASE_COMPLETE mode=timeout ...`。Phase B完了まではSMD-121全体を
`PASS`にしない。

## Phase B Attempt 1 — HARNESS_FALSE_NEGATIVE

2026-09-11 18:53 JSTのtimeout試験では、Job 362について次を実測した。

- timeoutは5秒で発生し、worker logは`prolog poll timeout @ 5000 msec`、signal 15、
  `prolog failed status=0:15`を記録した。
- timeout hookのPIDとPGIDはいずれも67079。同PGID processはtimeout後とfollow-up時の
  どちらにも残っていなかった。
- nodeは`IDLE+DRAIN`、reasonは`Prolog error`。jobはrequeue後hold、priority 0、Restarts 1。
- payloadは実行されていない。
- cleanupでJob 362をcancelし、production configはbackupとbyte比較0、SHA-256一致で復元した。

一方、driverのlog gateは`timeout after 5000 ms`または`timed out`だけを許可していた。
実際の26.11.0-0rc1出力は`prolog poll timeout @ 5000 msec`だったため、正常なtimeoutを
`worker log lacks Prolog timeout evidence`と誤判定した。これはSlurm本体のfailureではなく、
test harnessの文字列照合不備である。

失敗後の安全方針どおりnodeは`IDLE+DRAIN`のままで、Job 362はqueueから消失しaccountingは
`CANCELLED 0:0`。post-recovery smokeは未実施なのでPhase BをPASSにはしない。

driverへ実測形式`prolog poll timeout @ 5000 msec`を追加した。手動RESUME後にPhase B全体を
再実行する。生Evidenceは
[`SMD-121-phase-b-attempt1.txt`](./SMD-121-phase-b-attempt1.txt)に保存した。
