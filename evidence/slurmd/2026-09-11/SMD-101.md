# SMD-101 複数user実行境界

## 判定

- 状態: `PASS`
- 対象: PC-210 / macOS / arm64 worker上のproduction slurmd
- controller: ubuntu2504 / Ubuntu 24.04 / x86-64
- 目的: 2人の非root userが、それぞれ正しいnumeric UID/GIDとfile ownershipでjobを実行できるか確認する

## 現在確認できたこと

2026-09-11のMac側read-only確認では次のidentityだった。

```text
REDACTED_USER:     uid=501 gid=20(staff)
testuser: uid=3001 gid=3001
```

2026-09-11 10:44:14 JSTのUbuntu側read-only確認により、現在値を次のように確定した。

| user | Ubuntu UID:GID | macOS UID:GID | 判定 |
|---|---:|---:|---|
| `testuser` | `3001:3001` | `3001:3001` | 一致 |
| `REDACTED_USER` | `501:2000` | `501:20` | primary GID不一致 |

Ubuntu側の`REDACTED_USER`には`adm`、`sudo`、`docker`、`libvirt`等、macOS側には`staff`、`admin`、
`localaccounts`等のOS固有supplementary groupがある。このため`REDACTED_USER`はSMD-101の「一致した第2 user」
として使用しない。`testuser`に加えて、同名・同一numeric UID・同一primary GIDを持つ非root userが
もう1人必要である。

macOS固有の`everyone`、`localaccounts`等とLinux固有groupは完全一致しないため、全supplementary groupの
文字列一致は成功条件にしない。代わりに、両OSで作成する試験専用supplementary groupのnumeric GIDと
membershipを一致させ、OS固有groupは差分Evidenceとして記録する。

workerは`IDLE`かつ未割当であり、cluster状態は試験可能である。ただし一致する第2 userがないため、

## 次のpreflight

専用候補`testuser2`のUID/GID 3002と、両test userへ追加する試験専用group候補`smdtest`のGID 3100が
両nodeで未使用かをread-onlyで確認する。空き確認後も、明示承認を受けるまではuser/groupを作成しない。

Ubuntu:

```bash
getent passwd 3002
getent group 3002
getent group 3100
id testuser2
```

macOS:

```bash
dscacheutil -q user -a uid 3002
dscacheutil -q group -a gid 3002
dscacheutil -q group -a gid 3100
id testuser2
```

Mac側では2026-09-11に上記を実行し、UID 3002、GID 3002、GID 3100のqueryはいずれも結果なし、
`id testuser2`は`no such user`だった。Ubuntu側でも2026-09-11に同じ候補を確認し、3つの`getent`
queryはすべて無出力、`id testuser2`は「そのようなユーザは存在しません」だった。したがって両nodeで
UID/GID 3002、supplementary GID 3100、user name `testuser2`は未使用である。

```text
ubuntu_getent_passwd_3002=EMPTY

ubuntu_id_testuser2=NO_SUCH_USER
```

次は両nodeへの`testuser2=3002:3002`と`smdtest` GID 3100の作成であり、OSのuser/group databaseと

- `testuser2`をUID/GID 3002、password login無効で作成
- `smdtest`をGID 3100で作成
- `testuser`と`testuser2`を`smdtest`へ追加
- Ubuntuは`/home/testuser2`、macOSは`/Users/testuser2`をmode 0700で作成

## Provisioning実行結果と初回macOS failure

Ubuntu側は承認済みscriptをroot実行し、次を確認した。

```text
testuser=3001:3001 groups=3001,3100
testuser2=3002:3002 groups=3002,3100
smdtest=3100 members=testuser2,testuser
home=/home/testuser2 identity_mode=3002:3002:700
password_login=LOCKED
SMD101_UBUNTU_PROVISION_COMPLETE
```

macOS側の初回実行は`dseditgroup`から次のerrorを返し、rc 40で停止した。

```text
<main> attribute status: eDSPermissionError
<dscl_cmd> DS Error: -14120 (eDSPermissionError)
SMD101_MACOS_PROVISION_INCOMPLETE rc=40
```

停止後のreadbackでは、削除や再作成をせず次の部分状態を確認した。

```text
testuser2=uid:3002 primary_gid:3002 home:/Users/testuser2 shell:/bin/bash
primary_group=testuser2:3002
shared_group=smdtest:3100
home_/Users/testuser2=ABSENT
testuser2_supplementary_gid_3100=ABSENT
```

したがってgroup/user record作成は成功済みで、失敗範囲はその後の明示group membership追加または
home作成より前である。初版は新userをprimary groupへ`dseditgroup -o edit`で重複追加した後、2 userを
`smdtest`へ追加していたため、どのeditで停止したかをstdoutだけから一意に確定できない。

retry版ではprimary groupへの明示追加を除去した。primary membershipはuser recordの
`PrimaryGroupID=3002`で成立している。supplementary groupは、各userの`GeneratedUID`をreadbackしてから
Directory Serviceの`GroupMembership`と`GroupMembers`へ`dscl -merge`する。`-merge`は既存値を重複させず、
部分作成済み状態から再実行できる。また各mutation前に`step=`を出力し、今後の停止箇所を特定可能にした。

retry版のlocal静的確認:

```text
macos_script_sh_n=PASS
approval_gate_without_env_exit=64
macos_script_retry_sha256=dbed54ab7c5d9a557486494993ca2f378068b77cf135a4939f90632c1334e539
```

この時点ではmacOS側のmembership、HOME、最終identityは未確認であり、SMD-101 job本体へは進まない。

## macOS provisioning retry結果

修正版をrootで再実行し、部分作成済みrecordから不足分だけが適用された。

```text
step=merge_group_member group=smdtest member=testuser
step=merge_group_member group=smdtest member=testuser2
step=create_home path=/Users/testuser2
created (/Users/testuser2)
step=verify
uid=3001(testuser) gid=3001 groups=3001,3100(smdtest),12,61,100,701
uid=3002(testuser2) gid=3002(testuser2) groups=3002,3100(smdtest),12,61,100,701
home=/Users/testuser2 identity_mode=3002:3002:700
password_login=DISABLED
hidden_from_login_window=YES
SMD101_MACOS_PROVISION_COMPLETE testuser=3001:3001 new_user=3002:3002 shared_group=smdtest:3100
```

`createhomedir`実行中に次の警告が1回出たが、直後に`created (/Users/testuser2)`となり、script内の
directory存在、numeric owner、mode検証も通過した。

```text
shell-init: error retrieving current directory: getcwd: cannot access parent directories: Permission denied
```

これはroot shellの開始directoryをhome作成処理のsubprocessが参照できなかった警告であり、今回の
HOME作成失敗を示すものではない。ただし再現性のため、現行版scriptはDirectory Service処理前に
`cd /tmp`するよう修正した。成功実行時のscript hashと、警告抑止を加えた現行hashを区別して残す。

```text
macos_executed_retry_sha256=dbed54ab7c5d9a557486494993ca2f378068b77cf135a4939f90632c1334e539
macos_current_sha256=f9c0bcda452c268204b84ba1b46baba58d5954f44f92fd9ba286633b5248ca8a
macos_current_sh_n=PASS
provisioning_result=BOTH_NODES_COMPLETE
```

### Evidence訂正: password無効・login window非表示

成功時の`password_login=DISABLED`と`hidden_from_login_window=YES`は、当時のscriptが状態を独立に
readbackして判定した値ではなく、設定後に出した固定文字列だった。このため、この2つのsecurity propertyは
`NOT_VERIFIED`へ訂正する。macOS上でJobs 355/356が正しいUID/GID・supplementary group・所有権で実行され、
相互隔離、accounting、資源解放まで通ったSMD-101本体の`PASS`判定には影響しない。

```text
smd101_functional_result=PASS
macos_password_login_disabled=NOT_VERIFIED
macos_login_window_hidden=NOT_VERIFIED
```

SMD-102では`pwpolicy -authentication-allowed`とloginwindowの`HiddenUsersList` readbackが実機で成立した。
ただしSMD-101の`testuser2`にはまだ同じreadbackを実施していないため、この2属性は引き続き
`NOT_VERIFIED`とし、SMD-102完了後の別試験で再検証する。

## SMD-101本体試験設計

両userをMac側client identityとして同時に`sbatch`し、Mac workerで次を機械判定する。

1. job内のuser名、UID、primary GIDがそれぞれ`testuser=3001:3001`、`testuser2=3002:3002`である。
2. 両jobのsupplementary groupにGID 3100がある。
3. stdout、stderr、job生成markerのnumeric ownerが投入userのUID:GIDと一致する。
4. markerはmode 0600で、他方のuserからread不能である。
5. 各user用run directoryはmode 0700で、他方のuserからwrite不能である。
6. `sacct`のjobおよびbatch recordが`COMPLETED 0:0`になる。
7. 終了後にnodeが`IDLE`、`CPUAlloc=0`、`AllocMem=0`、queue空へ戻る。

## 本体試験 Attempt 1 — BLOCKED_INFRASTRUCTURE

2026-09-11 11:05:52 JST、Mac上でroot driverを開始したが、controller preflightで停止した。

```text
run_dir=/tmp/slurm-smd101-20260911T110552
error: controller ping failed
```

driverが保存した生出力は次のとおりだった。

```text
Slurmctld(primary) at ubuntu2504 is DOWN
*****************************************
** RESTORE SLURMCTLD DAEMON TO SERVICE **
*****************************************
```

`jobs.tsv`は作成されておらず、job投入数は0である。したがって、このattemptはSMD-101の複数user
実行結果ではなく、前提infraでの停止である。

Mac側の追加read-only確認ではlaunchd serviceは`running`、slurmd PID 310は生存し、commandはproduction
prefixとconfigを使用していた。`ubuntu2504`は`192.168.10.180`へ解決したが、TCP 6817はtimeout、ICMPは
`Host is down`かつ2 packet中応答0だった。このEvidenceだけではUbuntu host停止、network path断、packet
filterのどれかを一意に確定できない。少なくともMac上のslurmd停止やSMD-101 identity検証失敗ではない。

生Evidence: [`SMD-101-attempt1-20260911T110552.txt`](./SMD-101-attempt1-20260911T110552.txt)

driverはpreflight failure時に保存済みcontroller出力をstderrへ表示し、`no jobs were submitted`を明記する
よう修正した。

```text
driver_current_sh_n=PASS
driver_current_sha256=d06eac5e923003004ba9e23883b2f9b300ca431c9233dcfc34a241c626a2a89b
next_action=RESTORE_AND_VERIFY_CONTROLLER
```

## 本体試験 Attempt 3 — PASS

nodeを`IDLE`へ復旧後の2026-09-11 11:12 JST、Jobs 355、356を投入して全成功条件を満たした。

| user | job | job内UID:GID | GID 3100 | file owner | marker mode | sacct |
|---|---:|---:|---|---:|---:|---|
| `testuser` | 355 | `3001:3001` | 有 | `3001:3001` | `600` | job/batch `COMPLETED 0:0` |
| `testuser2` | 356 | `3002:3002` | 有 | `3002:3002` | `600` | job/batch `COMPLETED 0:0` |

各user用mode 0700 directoryへの他方userのwriteと、各mode 0600 markerへの他方userのreadはいずれも
拒否された。両job終了後はnode `IDLE`、`CPUAlloc=0`、`AllocMem=0`、queue空へ戻った。`cwd=/private/tmp`は
macOSで`/tmp`の実体pathが表示されたもので、指定workdirからの逸脱ではない。

```text
directory_isolation=PASS
marker_isolation=PASS
SMD101_MULTI_USER_COMPLETE jobs=2 final_state=IDLE CPUAlloc=0 AllocMem=0
```

Raw Evidence:

- [`SMD-101-final-20260911T111221.txt`](./SMD-101-final-20260911T111221.txt)

```text
raw_evidence_sha256=ee668bdda9e0a69df5af4b865051fe7cc9b50aab9ac9c200c98f6a943760135a
```

以上によりSMD-101は`PASS`とする。確認できたのはUID/GIDが両nodeで一致する構成であり、意図的に
不一致とした場合のfail behaviorはSMD-102へ分離する。

## 次の停止条件

- 承認済みの`testuser2`、primary group、`smdtest`以外を作成・変更しない。
- 実在userのUID/GIDを変更しない。
- 本体driverが途中失敗した場合はjob、process、node、accountingを保存し、SMD-102へ進まない。
- SMD-102は隔離account作成と意図的なID不一致を伴うため、ID空き確認と明示承認前に変更しない。
