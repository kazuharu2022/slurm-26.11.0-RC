# SMD-120 Prolog/Epilog正常系

## 判定

- 状態: `PASS`
- 対象: PC-210 / macOS / arm64 worker上のproduction `slurmd`
- controller: ubuntu2504 / Ubuntu 24.04 / x86-64
- 目的: node `Prolog`と`Epilog`が1 jobにつき各1回、root権限、規定順序で実行され、設定復元後に無効化されることを確認する
- 前提: SMD-102は`FAIL_OPEN_PAYLOAD_EXECUTED`のEvidenceを保持したまま、ユーザー指示で修正・再試験をスキップする

## source・同梱文書で確認した仕様

同梱の[`Prolog and Epilog Guide`](../../../doc/html/prolog_epilog.shtml)と
[`slurm.conf(5)`](../../../doc/man/man5/slurm.conf.5)では、次の動作が定義されている。

- `Prolog`はcompute node上で`slurmd`が`SlurmdUser`（通常root）として、allocationの最初のjob step直前に実行する。
- `Epilog`はcompute node上でallocation解放時に実行する。
- `PrologFlags=Alloc`を指定しない既定動作では、stepが一度も起動しないallocationのPrologは実行されない。
- hookの標準出力・標準エラーは通常保存されないため、必要なEvidenceはhook自身が安全な場所へ書く。
- hookは短時間で終了させ、内部から`squeue`、`scontrol`等のSlurm commandを呼ばない。
- 複数hookは逆辞書順で実行される。本試験はProlog/Epilogを各1本だけ設定する。

実装経路も確認した。

- [`src/slurmd/slurmd/req.c`](../../../src/slurmd/slurmd/req.c): 最初のstep起動前に`run_prolog()`、job終了時に`run_epilog()`を呼ぶ。
- [`src/slurmd/common/slurmd_common.c`](../../../src/slurmd/common/slurmd_common.c): prep plugin経由でhookを実行し、実行時間を監視する。
- [`src/plugins/prep/script/prep_script_slurmd.c`](../../../src/plugins/prep/script/prep_script_slurmd.c): `SLURM_JOB_ID`、`SLURM_JOB_UID/GID`、`SLURM_JOB_USER`、`SLURMD_NODENAME`、`SLURM_SCRIPT_CONTEXT`等を構築し、configured scriptを実行する。

production worker configのread-only確認では、`Prolog`、`Epilog`、TaskProlog/TaskEpilog、
HealthCheckProgramは未設定だった。共通timeoutは`PrologEpilogTimeout=120`が設定済みである。
この既存timeoutは変更せず、Prolog/Epilogだけを一時追記してbyte-for-byte復元する。

## 試験設計

SMD-120は正常系だけを扱う。failure、timeout、DRAIN/requeueはSMD-121/122へ分離する。

1. PC-210が`IDLE`、未割当、queue空、controller `UP`であることを確認する。
2. production `slurm.conf`に既存Prolog/Epilog関連設定がないことを再確認し、あれば上書きせず停止する。
3. root所有・mode 0555のProlog/Epilogと、root所有・mode 0600の専用event logを`/tmp`のrun directoryへstageする。
4. 既存`PrologEpilogTimeout=120`を安全上限として確認し、production configを保存してProlog/Epilogだけを一時追加し、parse確認する。
5. `scontrol reconfigure`後、slurmd PID維持、新しい`SlurmdStartTime`、3回連続IDLEを確認する。
6. UID/GIDが両nodeで一致している`testuser=3001:3001`から、2秒の単一batch payloadを実行する。
7. 対象Job IDだけをfilterし、Prolog/Epilog各1回、hook `euid=0 egid=0`、payload `3001:3001`、時刻順序を検証する。
8. jobとbatchの`COMPLETED 0:0`、stderr空、event logの`0:0:600`を確認する。
9. configをbyte-for-byte復元して再reconfigureし、post-restore smoke jobではSMD-120 hookが実行されないことを確認する。
10. 最終`IDLE`、CPUAlloc=0、AllocMem=0、queue空を確認する。

event logへ保存するのはevent種別、Job ID、epoch、hook実効UID/GID、Slurmが設定したcontextだけで、
job environment全体、command line、token、key、任意のuser変数は記録しない。

## Attempt 1 — BLOCKED_SAFE

初回実行はjob投入・config変更前に安全停止した。

```text
run_dir=/tmp/slurm-smd120-20260911T123115
error: production config already has Prolog/Epilog settings; refusing to replace them
```

原因は実際の既存hook競合ではなく、driverのpreflight条件が既存
`PrologEpilogTimeout=120`まで拒否対象に含めたtest-harness不備だった。read-only確認では
`Prolog=`と`Epilog=`は存在しない。run directoryにはhook/payloadのstageと空のevent logだけがあり、
config backup/candidate、job output、accounting fileはない。したがってproduction config変更とjob投入は0件である。

修正版は次の条件に変更した。

- 既存`Prolog=`または`Epilog=`だけを競合として拒否する。
- 個別`PrologTimeout`/`EpilogTimeout`はeffective timeoutの曖昧さを避けるため拒否する。
- `PrologEpilogTimeout`がちょうど1件、整数、1～300秒であることを確認する。
- 現行値120秒を維持し、candidateにはProlog/Epilogだけを追加する。

## failure時の扱い

- driverは対象jobだけをcancelし、可能な限りproduction configを復元して再reconfigureする。
- hook failureでnodeがDRAINした場合、原因確認前に自動RESUMEしない。
- recovery messageが出た場合は次のSMD-121へ進まず、run directory、controller log、worker logを保存する。
- `/tmp`のrun directoryはEvidence採取が終わるまで削除しない。
