# SMD-203 GRES accounting

- 状態: `PASS`
- 対象: Ubuntu 24.04 / x86-64 の `slurmctld`・`slurmdbd` と、macOS / arm64 の `slurmd`
- Slurm: `26.11.0-0rc1`
- production設定変更: Ubuntu/macOS双方へ`AccountingStorageTRES=gres/gpu,gres/gpu:apple`を追加済み

## 既に観測できている事実

SMD-126、SMD-201、SMD-202では、`gpu:apple:1`を要求したjobがscheduler上で排他制御され、
payloadには`SLURM_JOB_GPUS=0`が渡され、既存MLX 0.32.2がApple M5 Max上で動作した。
一方、保存した`ReqTRES`と`AllocTRES`には`gres/gpu`が含まれていない。

直近のSMD-202 crash再試験でも、Job 398はSIGSEGV後にGRESを解放し、後続Job 399は同じ
GPUを取得して完走したが、accountingは次のとおりだった。

```text
398|testuser|FAILED|0:11|PC-210|billing=1,cpu=1,mem=256M,node=1|billing=1,cpu=1,mem=256M,node=1
398.batch||CANCELLED|0:11|PC-210||cpu=1,mem=256M,node=1
399|testuser|COMPLETED|0:0|PC-210|billing=1,cpu=1,mem=256M,node=1|billing=1,cpu=1,mem=256M,node=1
399.batch||COMPLETED|0:0|PC-210||cpu=1,mem=256M,node=1
```

この結果は、scheduler-visibleなGRES lifecycleが正常でも、accounting対象にGPU TRESが
登録されていることを意味しない。

## 同梱source・documentによる根拠

- `doc/man/man5/slurm.conf.5`と`doc/html/tres.shtml`は、既定のaccounting TRESにGRESを
  含めず、GPUを記録するには`AccountingStorageTRES`へ追加する必要があると説明している。
- typed GRESを追跡する場合も、genericな`gres/gpu`を併記することが推奨されている。
- `src/common/read_config.c`は、設定がなければ`DEFAULT_ACCOUNTING_TRES`だけを使用し、設定が
  ある場合にその値を既定値へ追加する。
- `AccountingStorageTRES=gres/gpu`によって追加される`gres/gpumem`と`gres/gpuutil`の実測は、
  同梱`doc/html/gres.shtml`上ではNVML使用時のNVIDIA GPUとRSMI使用時のAMD GPUに限定される。
  Apple Metal GPUについて使用率・使用メモリまで記録できるとは判定しない。

macOS側の`/opt/slurm/26.11.0/etc/slurm.conf`には、初回preflight時点で
`GresTypes=gpu`と`SelectType=select/cons_tres`はあるが、`AccountingStorageTRES`はなかった。
ただし、このファイルはcontrollerの権威設定ではないため、原因確定にはUbuntu側の実効設定を
読み戻す必要がある。

## 現時点の仮説

第一仮説は、Ubuntu controllerで`AccountingStorageTRES`に`gres/gpu`および
`gres/gpu:apple`が設定・登録されていないことである。これは設定由来の可能性が高く、現時点で
macOS plugin不具合とは判定しない。

## preflight判定

- 実効`AccountingStorageTRES`とDBのTRES一覧に`gres/gpu`・`gres/gpu:apple`がない:
  設定不足仮説を支持する。controller設定変更案とrestart/retest手順を別途作成する。
- 実効設定とDBの双方に対象TRESがあるのにJob 398/399へ記録されない:
  設定不足では説明できないため、job requestのpack/unpack、controller、slurmdbd経路を調査する。
- genericだけ、またはtypedだけがある:
  要求形式`gpu:apple:1`との対応を確認し、同梱documentの推奨どおり両方を追跡する案を評価する。

## preflight結果 — `PREFLIGHT_PASS_CONFIG_GAP_CONFIRMED`

2026-09-11 21:58 JST、Ubuntu controller上で上記の読み取り専用preflightを実行した。

実効設定は次の既定8 TRESだけだった。

```text
AccountingStorageTRES   = cpu,mem,energy,node,billing,fs/disk,vmem,pages
```

static `slurm.conf`にも`AccountingStorageTRES`行はなく、DB登録TRESもID 1～8の
`cpu,mem,energy,node,billing,fs/disk,vmem,pages`だけだった。`GresTypes=gpu`と
`SelectType=select/cons_tres`は有効だが、これらはGPUをaccounting対象へ追加しない。

Jobs 398/399の`ReqTRES`・`AllocTRES`も既定TRESだけで、preflight前に観測したaccounting gapを
再確認した。以上から、GPU TRES欠落の直接原因をUbuntu controllerの
`AccountingStorageTRES`未設定と判定する。macOS `slurmd`のGRES解放不具合を示す結果ではない。

生Evidence: [`SMD-203-preflight.txt`](SMD-203-preflight.txt)

## 修正案（未適用）

Ubuntu controllerの`/usr/local/slurm/26.11.0/etc/slurm.conf`へ、次を1行追加する。

```ini
AccountingStorageTRES=gres/gpu,gres/gpu:apple
```

genericとtypedの両方を指定するのは、`gpu:apple:1`という明示type要求と、typeを限定しない
GPU要求の双方を追跡可能にするためである。同梱documentが推奨する構成とも一致する。

TRESは`slurmctld`起動時にDBへ登録されるため、変更前にqueue/node/controllerを確認して設定を
backupし、`slurmctld`をrestartする。`slurmdbd`とmacOS `slurmd`の設定変更・restartは行わない。
restart後はcontroller UP、PC-210 IDLE、DB登録TRESを確認してから、新規GPU jobを投入する。
既存Jobs 398/399のrecordが遡及更新されることは成功条件にしない。

この変更はcontroller状態を変更するため、明示承認前には実行しない。

2026-09-11 22:05 JST、Ubuntu controllerのstatic configへ修正案を追加し、`slurmctld`を
再起動した。22:07 JSTの読み戻しではserviceは`active`、MainPID 41123、controller pingはUP。

`gres/gpumem` ID 1003、`gres/gpuutil` ID 1004が登録された。PC-210は`IDLE`、割当0で、
`CfgTRES`にも`gres/gpu=1,gres/gpu:apple=1`が現れた。queue出力は空だった。

これによりcontroller設定とDB登録は`PASS_PHASE_CONFIG`とする。`gpumem/gpuutil`のTRES登録は、
Apple Metalから使用量を収集できることを証明しない。SMD-203全体の`PASS`には、新規GPU jobの
`ReqTRES`・`AllocTRES`と終了状態を保存する必要がある。

## macOS側同期preflight — `READY_TO_RUN_PHASE_JOB`

Mac側static configにも`AccountingStorageTRES=gres/gpu,gres/gpu:apple`が追加されている。
Mac clientから読み戻したcontroller実効設定にはgeneric/typed GPUと自動追加された
`gres/gpumem,gres/gpuutil`があり、PC-210は`IDLE`、割当0、queue空だった。

以上からjob投入前提は`PASS`とし、既存MLX 0.32.2 jobを利用する専用driverを作成した。
driverはproduction configを変更せず、UID/GID 3001の`testuser`として
`--gres=gpu:apple:1`を要求する1 jobを投入する。次を成功条件とする。

- MLXがarm64 / Apple M5 Max / `Device(gpu, 0)`で`gpu_smoke_test=PASS`
- jobとbatchが`COMPLETED 0:0`
- jobの`ReqTRES`と`AllocTRES`にgeneric `gres/gpu=1`とtyped
  `gres/gpu:apple=1`が両方記録される
- 最終nodeが`IDLE`・割当0、queue・slurmstepd・payload process残留0
- slurmd PIDが維持される

## 最終job結果 — `PASS`

2026-09-11 22:14 JST、既存MLX jobを利用してJob 400を実行した。MLX 0.32.2は
arm64のApple M5 Maxを`Device(gpu, 0)`として使用し、4096×4096行列、5 iterationを
0.014538秒で完了した。`SLURM_JOB_GPUS=0`、`gpu_smoke_test=PASS`、stderrは0 byteだった。

job accountingは次のとおりである。

```text
400|testuser|COMPLETED|0:0|PC-210|billing=2,cpu=2,gres/gpu:apple=1,gres/gpu=1,mem=4G,node=1|billing=2,cpu=2,gres/gpu:apple=1,gres/gpu=1,mem=4G,node=1
400.batch||COMPLETED|0:0|PC-210||cpu=2,gres/gpu:apple=1,gres/gpu=1,mem=4G,node=1
```

jobの`ReqTRES`・`AllocTRES`とbatchの`AllocTRES`にgeneric/typed GPUが記録された。
worker logにはlaunchと正常completionがあり、最終nodeは`IDLE`、CPU/memory割当0、queue空。
slurmstepd、MLX Python、test processの残留はなく、slurmd PID 75048とstart timeは維持された。
関連stderrと残留一覧はすべて0 byteだった。

controller設定不足だったBefore Jobs 398/399と、設定反映後Job 400の差から、
`AccountingStorageTRES=gres/gpu,gres/gpu:apple`がGPU count accountingを有効化したと判断し、
SMD-203を`PASS`とする。

`gres/gpumem`・`gres/gpuutil`はDB登録されたが、Apple Metalの使用量値は今回得ていない。
またcancel/timeout/signal/crash後のGPU TRES recordは設定反映後に再実行していない。
これらはSMD-203のGPU要求・割当count成功条件には含めず、制約として残す。
