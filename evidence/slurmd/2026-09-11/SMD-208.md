# SMD-208 MLX/Metal数値correctness

- 状態: `PASS`
- 対象: Apple M5 Max / arm64 / macOS上の`slurmd`・MLX/Metal
- Slurm: `26.11.0-0rc1`
- MLX: `0.32.2`（既存uv環境）
- production設定変更: なし
- 新規package導入: なし

## Research Question

Slurmの`gpu:apple:1` GRESを割り当てたjob内で、MLX/Metalによるfloat32行列積は、
同一のfloat32入力からPython標準ライブラリで求めたCPU float64参照値に対し、
実行前に定義した誤差範囲内の値を返すか。

SMD-207は30回のjobが同じmean値を返すことを確認したが、同じ誤りを再現している可能性は
排除していない。そのため反復安定性と数値correctnessを別試験にする。

## 仮説

MLX/Metalのfloat32行列積が正常なら、非2冪分母から生成してbinary32へ量子化した入力でも、
CPU側で同じ量子化済み値を`math.fsum`によりbinary64集積した参照値との差は、下記の固定閾値内に
収まる。backend、dtype、shape、indexing、結果転送のいずれかに大きな不整合があれば、
非finite値、要素単位の混合許容誤差超過、最大または平均絶対誤差超過として検出される。

## 実験設計

### 固定条件

- 実行user: `testuser`（UID/GID 3001:3001）
- GPU要求: `--gres=gpu:apple:1`
- backend: `Device(gpu, 0)` / Apple M5 Max
- GPU dtype: float32
- CPU参照: Python binary64の積を`math.fsum`で集積
- 入力: 決定的な整数式を37および41で除算し、`struct.pack/unpack`でbinary32へ量子化
- shape: `7x31 @ 31x11`、`13x64 @ 64x9`、`5x127 @ 127x7`
- 比較要素数: 77 + 117 + 35 = 229

NumPy等は追加しない。既存のMLX 0.32.2とPython 3.14.6標準ライブラリのみを使う。
payloadはjob用の`/tmp`配下へcopyし、`testuser`所有にしてから実行する。

### 実行前に固定した成功条件

1. 全要素がfiniteである。
2. 全要素で `abs(GPU - CPU) <= 5e-5 + 5e-5 * abs(CPU)` を満たす。
3. 各caseおよび全体の最大絶対誤差が`1e-3`以下である。
4. 各caseおよび全体の平均絶対誤差が`2e-5`以下である。
5. stdoutに3 caseとoverall、固定閾値、MLX/device情報、PASS markerが残る。
6. stderrが空で、jobとbatchが`COMPLETED 0:0`、generic/typed GPU TRESが記録される。
7. 終了後にnodeが`IDLE`・割当0、queue・`slurmstepd`・payload processが残らない。
8. production config、payload、batch scriptのhashとslurmd PIDが変化しない。

結果を見て閾値を緩和しない。閾値超過時はSMD-208をFAILとしてEvidenceを保持し、case、要素、
backend、入力量子化、CPU参照の順に切り分ける。

### 補助計算（実GPU結果ではない）

実行前の閾値妥当性確認として、同じbinary32入力をPython上で積・逐次加算の各段階にbinary32へ
丸める保守的なserial accumulationで試算した。最大絶対誤差は内積長31で`8.279255077e-07`、
64で`1.754873262e-06`、127で`2.565600305e-06`だった。最大scaled errorは0.024861未満である。

これはMetalの実測ではなく、閾値を実行後に選んでいないことを示す設計Evidenceである。

## Attempt 1 — 既定の低精度経路を検出

2026-09-11 23:47 JST、Job 445を実行した。GPU割当、Apple M5 Max、MLX 0.32.2、
`Device(gpu, 0)`、229要素の比較までは実行できたが、全3 caseが事前閾値を超えた。
全体最大絶対誤差は`1.198998928e-02`、全体平均絶対誤差は`2.450096443e-03`、
最大scaled errorは`63.20940650`だった。payloadは設計どおりexit 1となり、jobとbatchは
`FAILED 1:0`、generic/typed GPU TRESを記録した。

driverが成功時の`COMPLETED 0:0` accountingを数値出力より先に確認したため、terminalには
本質的な`numerical correctness criteria failed`ではなく`accounting mismatch`が出た。
これはエラー報告順序のハーネス不備である。ただし数値FAIL自体は実測であり、誤判定ではない。

生Evidence: [`SMD-208-attempt1.txt`](SMD-208-attempt1.txt)

## 原因調査と修正

MLX 0.32.2同梱の`mlx/include/mlx/utils.h`では、`enable_tf32()`が環境変数
`MLX_ENABLE_TF32`を既定値1で読む。MLX公式の
[Numerical Precision](https://ml-explore.github.io/mlx/build/html/usage/precision.html)も、専用行列演算器を
持つhardwareではfloat32入出力のままmatmul等を低精度実行する場合があり、完全なfloat32には
process起動時に`MLX_ENABLE_TF32=0`を指定すると説明している。M5で同種の誤差が報告された
[MLX Issue #3534](https://github.com/ml-explore/mlx/issues/3534)とも誤差規模と条件が整合する。

したがってAttempt 1はSlurm、GRES、CPU referenceの失敗ではなく、MLX/M5の既定低精度経路を
float32精度試験へ使用した実験条件不足と判定する。既定動作で事前閾値を満たさない事実は削除しない。

修正版は次を行う。

- batch scriptがPython起動前に`MLX_ENABLE_TF32=0`をexportする
- payloadもimport前に値0を必須確認し、stdoutへ記録する
- 事前定義した入力、3 shape、229要素、全誤差閾値は一切変更しない
- driverは数値FAIL時にstdout、stderr、FAILED accountingを先に表示し、原因をmaskしない
- full-float32成功時だけ`COMPLETED 0:0` accountingと最終資源回収を確認する

これにより補助RQを「M5のfull-float32明示時に事前閾値を満たすか」へ追加する。元のRQに対する
既定モードの答えはFAILとして保持し、full-float32再試験をAttempt 2とする。

## 結論

SMD-208は`PASS`とする。ただし結論は条件付きである。M5 Max上のMLX 0.32.2既定モードは
float32入出力でも今回のfull-float32閾値を満たさず、`MLX_ENABLE_TF32=0`をprocess起動前に
明示した場合に同じ入力・閾値でPASSした。したがって高精度を必要とするSlurm GPU jobでは、
dtype表示だけで精度を判断せず、この環境変数をjob scriptで固定し、数値検証を別途行う必要がある。
