# SMD-123 TaskProlog/TaskEpilog

## 判定

- 状態: `PASS`
- 対象: PC-210 / macOS / arm64 worker上のproduction `slurmd`・`slurmstepd`
- controller: ubuntu2504 / Ubuntu 24.04 / x86-64
- 前提: SMD-120～SMD-122は`PASS`

## 仕様と検証仮説

同梱の[`Prolog and Epilog Guide`](../../../doc/html/prolog_epilog.shtml)と
[`slurm.conf(5)`](../../../doc/man/man5/slurm.conf.5)では、`TaskProlog`と`TaskEpilog`はcompute
nodeの`slurmstepd`が各taskについてjob user権限で実行する。`TaskProlog`標準出力の
`export NAME=value`、`unset NAME`、`print ...`はtask環境・標準出力へ反映される。

sourceでは[`src/slurmd/slurmstepd/task.c`](../../../src/slurmd/slurmstepd/task.c)が
`TaskProlog`をtask起動前に実行して出力をtask環境へ反映する。
[`src/slurmd/slurmstepd/mgr.c`](../../../src/slurmd/slurmstepd/mgr.c)はtask終了後に
`SLURM_SCRIPT_CONTEXT=epilog_task`を設定して`TaskEpilog`をjob userとして実行する。

仮説は、2 taskの各々について次が成立することである。

- TaskProlog、payload、TaskEpilogが各1回、合計2回ずつ実行される。
- hookとpayloadのEUID/EGIDは`testuser=3001:3001`になる。
- `SLURM_PROCID`/`SLURM_LOCALID`は0と1で一意になる。
- TaskPrologのexport値が対応するpayloadだけに入り、指定変数はunsetされる。
- TaskEpilogは対応するpayload marker作成後に実行される。
- job/stepは`COMPLETED 0:0`となり、設定復元後のsmokeも成功する。

反証条件は、回数不一致、root実行、ID重複、environment未反映、Epilog先行、job失敗、
設定不一致、最終資源残留のいずれかとする。

## 安全設計

driverはcontroller UP、node IDLE・未割当・queue空、`testuser` UID/GIDを確認する。production
configに既存`TaskProlog`/`TaskEpilog`があれば上書きせず停止する。hookとpayloadはroot所有・0555、
event/payload directoryはtestuser所有・0700として、任意userによるhook改ざんや他userの読取りを防ぐ。

一時configを`slurmd -C`でparseしてから適用し、2-taskの`srun`を1回だけ実行する。検証後は
production configをbyte完全復元し、hook環境を渡さないsmoke jobでhookが残っていないこと、
accounting、最終IDLE・資源解放を確認する。途中失敗でもconfig復元と既知jobの取消を試みる。

## Attempt 1 — HARNESS_FAILURE

2026-09-11 19:16 JSTの初回実行では、Job 369のallocation後、task起動前にMac上の`srun`が
`_fwd_tree_get_addr: can't find address for host PC-210`で停止した。client rcは244、accountingは
job `FAILED 0:116`、step `CANCELLED 0:116`だった。TaskProlog、payload、TaskEpilogのfileは
すべて0件であり、SMD-123のhook機能はまだ測定されていない。

Macのhostnameは`PC-210.local`、en0の実測IPv4は`192.168.10.128`。`PC-210.local`は同IPv4を
解決できるが、production `NodeName=PC-210`に明示的`NodeAddr`はなく、controller readbackも
`NodeAddr=PC-210`だった。これはSMD-001でも発生したMacローカル`srun`のshort-name解決問題であり、
今回のTask hook実装failureではなくtest harnessの前提不足と分類する。

driverを修正し、実行時にen0 IPv4と`PC-210.local`のreadback一致を確認する。その値を明示した
driver専用client configを作成し、ローカル`srun`だけがそれを使用する。production configと
slurmdの一時Task hook configにはNodeAddr変更を加えない。初回cleanupでproduction configは
backupとbyte比較0で復元され、nodeは`IDLE`、割当0、queue空、PID 310を維持した。

生Evidenceは[`SMD-123-attempt1.txt`](./SMD-123-attempt1.txt)に保存した。修正版の静的検証後に
Attempt 2を実行するまで、SMD-123は`FIX_BUILT_AWAITING_RETEST`とする。

## Attempt 2 — PASS

2026-09-11 19:20 JSTに修正版driverを実行し、driver専用client configの
`NodeAddr=192.168.10.128`を使ってJob 370の2-task stepを完了した。production configへ
NodeAddrは追加していない。

| 確認項目 | 実測 |
|---|---|
| client config | candidate/clientともparse成功、numeric NodeAddrは192.168.10.128 |
| TaskProlog | procid/localid 0,1で各1回、合計2回 |
| payload | 各task 1回、合計2回、UID/GID 3001:3001 |
| TaskEpilog | 各payload marker作成後に1回、合計2回 |
| environment | task別export、unset、printをすべて確認 |
| Job 370 | job/stepとも`COMPLETED 0:0`、srun rc 0、stderr空 |
| config復元 | backupとproductionのbyte比較0、SHA-256一致 |
| daemon | PID 310を維持 |
| Job 371 | job/batchとも`COMPLETED 0:0` |
| 最終状態 | `IDLE`、`CPUAlloc=0`、`AllocMem=0`、queue空 |

event/payload directoryはtestuser所有0700のため現在のREDACTED_USER sessionから直接readできないが、rootで
実行したdriverがprocid 0/1についてProlog、payload、Epilogの全6 fileを完全一致で検証した。
readableな`srun.out`、`srun.err`、`sacct`、config hash、node readbackも別途照合した。

Attempt 1のshort-name解決failureはTask hook実行前のharness failureとして残し、Attempt 2でのみ
SMD-123本体の成功条件を満たした。生Evidenceは
[`SMD-123-attempt2.txt`](./SMD-123-attempt2.txt)に保存した。以上によりSMD-123を`PASS`とする。
