# SMD-122 Epilog failure/timeout

## 判定

- 状態: `PASS`
- 対象: PC-210 / macOS / arm64 worker上のproduction `slurmd`
- controller: ubuntu2504 / Ubuntu 24.04 / x86-64
- Phase A: payload正常終了後、Epilogがexit 42
- Phase B: payload正常終了後、Epilogが`EpilogTimeout=5`を超過
- 前提: SMD-120正常系とSMD-121 Prolog failure/timeoutは`PASS`

## 仕様と仮説

同梱の[`Prolog and Epilog Guide`](../../../doc/html/prolog_epilog.shtml)は、Epilogが非0終了すると
nodeをDRAINにすると説明する。Prolog failureと異なり、完了jobをrequeue/holdするとは規定していない。
また[`slurm.conf(5)`](../../../doc/man/man5/slurm.conf.5)は、EpilogまたはSPANK epilogのtimeoutで
nodeをDRAINし、errorをlogへ記録すると説明する。

sourceでは[`src/slurmd/slurmd/req.c`](../../../src/slurmd/slurmd/req.c)がEpilogのwait statusを
`ESLURMD_EPILOG_FAILED`へ変換し、controllerへ`epilog_complete`を通知する。
[`src/slurmctld/job_mgr.c`](../../../src/slurmctld/job_mgr.c)はreturn codeが非0ならnodeを
`Epilog error`でDRAINし、その後もjob completion処理を進める。
[`src/common/run_command.c`](../../../src/common/run_command.c)はtimeout時にscript process groupへ
TERM、続けてKILLを送る。

仮説は次の通り。

- payloadとjob/batchは`COMPLETED 0:0`になる。
- Epilogだけが非0またはtimeoutとなり、nodeは`DRAIN`、reasonは`Epilog error`になる。
- timeout hookのPID=PGIDとなり、timeout後に同PGID processは残らない。
- production config復元とRESUME後、smoke jobが`COMPLETED 0:0`となる。

反証条件は、payload未実行、job requeue/hold、nodeがDRAINしない、Epilog process残留、設定不一致、
後続job失敗、最終資源残留のいずれかとする。

## 安全設計

各phaseは1 jobだけを投入する。driverはcontroller UP、node IDLE・未割当・queue空を確認し、
既存hook、`PrologFlags`、個別timeoutがあれば上書きしない。一時configをparseしてから適用し、
failure Evidence採取後にproduction configをbyte完全復元する。

途中失敗ではconfigとactive jobをcleanupするが、意図的DRAINを自動RESUMEしない。run directoryを
確認してから管理者が復旧する。正常経路だけがDRAIN Evidence採取後にRESUMEし、smokeと最終資源を
確認する。

## Phase A — PASS_PHASE_A

2026-09-11 19:03 JSTに`nonzero` modeを実行し、failure Job 365と復旧後smoke Job 366を
完了した。

| 確認項目 | 実測 |
|---|---|
| payload | Job 365内で実行、driverがmarkerのUID/GID `3001:3001`を検証 |
| failure hook | root専用eventをdriverが検証、worker logは`epilog failed: rc:42`、`status=42:0` |
| Job 365 | job/batchとも`COMPLETED 0:0`。Epilog failureは完了jobをrequeue/holdしなかった |
| node | `IDLE+DRAIN`、`Reason=Epilog error`、CPU/memory割当0 |
| config復元 | backupとproductionのbyte比較0、SHA-256一致 |
| daemon | PID 310を維持 |
| Job 366 | job/batchとも`COMPLETED 0:0` |
| 最終状態 | `IDLE`、`CPUAlloc=0`、`AllocMem=0`、queue空 |

root専用event logとpayload output directoryはpermission設計どおり現在の非root検証sessionから
直接readできなかったが、rootで動作したdriverがeventのjob ID、EUID/EGID、context、exit codeと
payload markerのidentityを厳密照合してから完了markerを出している。readableなworker log、node、
accounting、config hashは別途再照合した。

一時config適用時の既知のconmgr interrupt pipe `EBADF`、macOS非対応core-spec、HTTP parser
plugin不在は今回も記録されたが、Epilog failure通知、DRAIN、復旧、後続jobを阻害しなかった。
生Evidenceは[`SMD-122-phase-a.txt`](./SMD-122-phase-a.txt)に保存した。
