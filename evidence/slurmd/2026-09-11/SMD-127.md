# SMD-127 slurmd log rotation

## 状態

`PASS`

## 対象と目的

- worker: Apple M5 Max / arm64 / macOS `PC-210`
- Slurm: `26.11.0-0rc1`
- controller: Ubuntu 24.04 / x86-64
- daemon: launchd管理下のproduction `slurmd`
- log: `/var/log/slurm/slurmd.log`
- test user: `testuser=3001:3001`

実行中jobを維持したままlogをrenameし、公式のlogrotate用signalで新fileへreopenできるか、
旧log FD、欠落したjob lifecycle、daemon restart、資源・process残留が発生しないかを検証する。

## 仕様確認

同梱[`slurmd(8)`](../../../doc/man/man8/slurmd.8)は`SIGUSR2`を、log levelを再読込して
log fileをreopenするlogrotate用signalと定義する。一方`SIGHUP`はconfiguration reloadである。
sourceの[`slurmd.c`](../../../src/slurmd/slurmd/slurmd.c)でも、`SIGUSR2` handlerは
`update_slurmd_logging()`と`update_stepd_logging(false)`を呼ぶ。

したがって、本試験はlog rotationに`SIGUSR2`を使う。SIGHUPまたは
`scontrol reconfigure`によるconfig再読込はSMD-012で別に検証済みであり、rotation中に重ねない。

## 試験設計

[`smd127_log_rotation_driver.sh`](../../../contribs/macos-tests/smd127_log_rotation_driver.sh)は
次を実行する。

1. controller UP、node IDLE、割当0、queue空、slurmd PIDをpreflightする。
2. active logのUID/GID/mode/inode/sizeとslurmdのFDを保存する。
3. testuserの15秒batchを開始し、ready markerを待つ。
4. active logをtimestamp付きpathへrenameし、同じUID/GID/modeで新しいactive logを作る。
5. rename直後はslurmd FDが旧inodeのrotated pathを指すことを確認する。
6. PIDへ`SIGUSR2`を送り、FDが新active logだけを指すまで待つ。
7. rotated logにjob launchとSIGUSR2境界、新logにjob completionがあることを確認する。
8. job/batch `COMPLETED 0:0`、payload完了、stderr空を確認する。
9. PID維持、log固有FD 1本、rotated FD 0、node IDLE、割当0、queue空を確認する。

## 安全境界

- production `slurm.conf`、launchd plist、spool、SACKは変更しない。
- active logの内容を削除せず、`slurmd.log.smd127-<timestamp>`として保持する。
- 新active logは実行直前に取得したownership/modeを引き継ぐ。
- failure時もactive logを作成して`SIGUSR2`を再送し、rotated logを上書きしない。
- 本試験はlog rotationを実際に行うため、明示的な環境変数gateを必須とする。
- rotated logの圧縮・世代削除は実施せず、運用policyの検証範囲外とする。

## Attempt 1 — `HARNESS_FALSE_NEGATIVE_PATH_CANONICALIZATION`

2026-09-11 21:00 JSTの初回実行は、job投入とlog renameより前のFD preflightで停止した。
保存された`lsof-before.txt`には、PID 75048のwrite FDが実際には1本存在する。

```text
slurmd  75048 root    3w   REG  ...  12907220 /private/var/log/slurm/slurmd.log
```

macOSの`/var`は`/private/var`へのsymlinkであり、`lsof`は物理pathを表示する。しかし初版driverは
`$NF == "/var/log/slurm/slurmd.log"`という完全一致で数えたため、1本を0本と誤判定した。

停止後の確認ではactive logがinode 12907220、owner `0:1002`、mode `600`、size 717613 byteで
存在し、`slurmd.log.smd127-20260911T210008`は存在しなかった。jobは未投入、SIGUSR2未送信、
production config未変更である。初回の`rotated log is preserved`表示は実態と異なるcleanup message
だった。

修正版はfile操作用の`/var/log/...`とFD照合用の`/private/var/log/...`を分離した。またrotation開始前に
停止した場合は`production log was not renamed`と表示する。保存済み`lsof-before.txt`に対する同じ
完全一致検査は、論理path 0件、物理path 1件となることを確認した。

詳細Evidence: [`SMD-127-attempt1.txt`](SMD-127-attempt1.txt)

Attempt 1はruntime経路に到達していないため、SMD-127はまだ`PASS`ではない。同じcommandで
修正版を再実行し、SIGUSR2 reopen、job継続、accounting、FD解放を実測する。

## Attempt 2 — `PASS`

2026-09-11 21:05 JST、path照合修正版で実行中jobを維持したlog rotationを完了した。

```text
submitted test_job=382
job_ready job_id=382
log_reopened pid=75048 wait_seconds=0 old_inode=12907220 new_inode=13560036
job_gone job_id=382 wait_seconds=16
SMD127_LOG_ROTATION_COMPLETE job_id=382 slurmd_pid=75048 fd_before=13 fd_final=13 old_size=717613
```

FDは次のように遷移した。

| 時点 | FD | inode | path |
|---|---:|---:|---|
| rename前 | `3w` | 12907220 | `/private/var/log/slurm/slurmd.log` |
| rename後 | `3w` | 12907220 | `/private/var/log/slurm/slurmd.log.smd127-20260911T210502` |
| SIGUSR2後 | `10w` | 13560036 | `/private/var/log/slurm/slurmd.log` |
| 最終 | `10w` | 13560036 | `/private/var/log/slurm/slurmd.log` |

rename直後も旧inodeへのFDを維持し、`SIGUSR2`後は新inodeへ即時に切り替わった。最終的に
rotated logを指すFDは0、process全体のdescriptor数は13→13で、FD leakは観測されなかった。
旧logのlaunch行とSIGUSR2境界、新logの`382.batch`完了行はroot driver内の必須検査を通過した。

payloadは15回のheartbeatを最後まで出力し、`rotation_complete`へ到達した。PID 81942は終了後に
存在せず、stdout/stderrのうちstderrは0 byteだった。accountingは次のとおり。

```text
382|testuser|COMPLETED|0:0|PC-210
382.batch||COMPLETED|0:0|PC-210
```

再照合時もqueueは空、nodeは`IDLE`、`CPUAlloc=0`、`AllocMem=0`、`Gres=gpu:apple:1`だった。
slurmd PID 75048と`SlurmdStartTime=2026-09-11T20:30:02`は変化していない。新旧logはともに
owner `0:1002`、mode `600`で、old inodeはrotated logに保存された。

以上によりSMD-127を`PASS`とする。これはdaemon自身のSIGUSR2 reopen、実行中jobの継続、
accounting、FD解放の実測である。圧縮、世代削除、外部logrotateとの統合は今回の範囲外で、
別途運用試験が必要である。
