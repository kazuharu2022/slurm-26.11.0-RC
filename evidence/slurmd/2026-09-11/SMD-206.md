# SMD-206 daemon restart後のGRES

- 状態: `PASS`
- 対象: Apple M5 Max / arm64 / macOSのlaunchd管理`slurmd`
- Slurm: `26.11.0-0rc1`
- production設定変更: なし

## Research Question

GPU count 1を登録したPC-210で、idle時または`gpu:apple:1`割当中にslurmdをrestartしても、
controllerのconfigured/allocated GRESが二重計上・消失せず、既存jobの追跡と後続GPU再割当が
正常に完了するか。

## Phase A: idle時restart — PASS（SMD-205 Evidence再利用）

SMD-205 Phase Bはnode `IDLE`、queue空、CPU/memory割当0から開始し、launchd slurmdを
PID 75048→91700→91811と2回clean restartした。1回目は意図したGPU報告0件による
`INVALID_REG+DRAIN`、2回目はproduction `gres.conf`復元後の正常登録だった。

復元後は`Gres=gpu:apple:1`、CfgTRESの`gres/gpu=1`と`gres/gpu:apple=1`を確認し、
Job 409がApple M5 Maxで完了した。終了後はnode IDLE、AllocTRES空、queue 0、slurmstepdなしで、
`slurmd -G`もCount 1だった。したがって、idle restart後のGRES二重計上・永久占有なしという
SMD-206 Phase A成功条件は同じproduction runtimeの直接Evidenceで満たしている。不要なdaemon
restartを追加せず、Phase Aを`PASS_PHASE_IDLE`とする。

Evidence: [`SMD-205-pass.txt`](SMD-205-pass.txt)

## Phase B: GPU job実行中restart

Phase Bでは既存MLX 0.32.2を実行済みの長時間`gpu:apple:1` jobを1件維持し、同じGRESを
要求する後続jobが`PENDING Resources`であることを確認してから、launchd管理slurmdを1回だけ
clean restartする。

成功条件は次のとおり。

1. restart前後でtarget jobがRUNNINGを維持し、heartbeatが進む。
2. restart前後ともCfgTRESとAllocTRESのgeneric/typed GPU countが各1で、二重計上しない。
3. 後続GPU jobは先行jobの割当中に`PENDING Resources`を維持する。
4. 先行job cancel後にprocess/accountingが回収され、後続jobがApple M5 Maxで完了する。
5. 最終状態がIDLE、AllocTRES空、queue/step/process残留0で、GRES configured countは1である。
6. production `slurm.conf`、`gres.conf`、launchd plistのhashが不変である。

driverとpayload:

```text
contribs/macos-tests/smd206_gpu_job_restart_driver.sh
SHA-256: da52623abd9a754d6fc52290fa6842b74731cd7270381be0cc693f807bbd39bf
contribs/macos-tests/smd206_restart_survivor_payload.sh
SHA-256: fb96050dfda25f98cde8718ee396284ccac5d535ac801d4231a57b882d1a8301
```

実行にはGPU job実行中のslurmd clean restart、先行jobのcancel、後続GPU jobの実行を含む。
失敗trapは対象2 jobをcancelし、必要ならproduction launchd serviceをbootstrapして再登録を試みる。
次のcommandは別途明示承認後だけ実行する。

```bash
sudo env SMD206_GPU_JOB_RESTART_CONFIRMED=YES /bin/sh \
  /Users/REDACTED_USER/dev/slurm.26-05/contribs/macos-tests/smd206_gpu_job_restart_driver.sh
```

`/bin/sh -n`、payloadの`/bin/bash -n`、approval gateのexit 64、production write scope、
`git diff --check`を確認した。この記述はdriver作成時点の状態であり、その後のruntime結果は
以下のAttempt履歴に記録する。

## Phase B承認後preflight — PASS

ユーザーの明示承認後、2026-09-11 23:01 JSTに読み取り専用preflightを行った。
controller 6817接続とpingはUP、PC-210はIDLE、CPU/memory割当0、AllocTRES空、queue 0、
slurmstepdなしだった。launchdとpidfileはPID 91811で一致し、last exitなし。configured GRESは
generic/typedとも各1だった。artifact hashと構文も計画時の値に一致した。

状態を`READY_TO_RUN_PHASE_RUNNING_USER_ROOT_SHELL`とし、PC-210 root shellでのdriver実行を待つ。

Evidence: [`SMD-206-phase-b-preflight.txt`](SMD-206-phase-b-preflight.txt)

## Phase B Attempt 1 — HARNESS_FALSE_NEGATIVE_PENDING_REASON_SOURCE

23:02 JSTにJob 410を起動し、Apple M5 MaxでMLXを実行してheartbeatを開始した。nodeは
`MIXED`、configured/allocated generic/typed GPUはすべて各1だった。後続Job 411を投入したが、
旧driverのPENDING判定が60秒でtimeoutし、restart前に安全停止した。

旧driverは表示用`squeue -o %R`をliteral `Resources`と比較しながらpoll値を保存していなかった。
そのため、実際に返った表示文字列は後から復元できず、canonical reasonの判定としてEvidence不足だった。
一方、accountingではJob 410が23:02:06～23:03:16、Job 411はcleanupで先行jobを解放した
23:03:16に初めてStartとなり、同時刻に終了、Elapsed 0、stdout 0 byteだった。Job 411は先行jobと
同時実行されておらず、GPU排他のfailureではない。

`restart_started=1`より前に停止したためbootout/bootstrapは行っておらず、slurmd PIDは91811のまま。
cleanup後の独立readbackはlaunchd running、node IDLE、割当0、queue 0、slurmstepdなし、production
hash不変だった。このAttemptはrestart機能を測っていないため`PASS`にはしない。

修正版は、SMD-201で実績のある`scontrol -o show job`のcanonical `Reason=`を使用し、全pollを
`probe-pending-before-restart.txt`と`probe-pending-after-restart.txt`へ保存する。またtarget
RUNNING、probe PENDING、Reason Resourcesを同時に3回要求し、probeがRUNNINGになれば即時停止する。
修正版driverのSHA-256は`da52623abd9a754d6fc52290fa6842b74731cd7270381be0cc693f807bbd39bf`。

生Evidence: [`SMD-206-phase-b-attempt1.txt`](SMD-206-phase-b-attempt1.txt)

## Phase B Attempt 2承認後retest preflight — PASS

ユーザーからAttempt 2再実行の明示承認を得た。2026-09-11 23:10 JSTの読み取り専用preflightでは、
実際のlaunchd target `system/org.schedmd.slurmd`がrunning、PID/pidfileは91811で一致し、
controller 6817接続とpingはUPだった。PC-210はIDLE、CPU/memory割当0、AllocTRES空、queue 0、
slurmstepdなしで、configured generic/typed GPUは各1だった。

修正版driverとpayloadの構文およびhashも再確認した。driverは
`da52623abd9a754d6fc52290fa6842b74731cd7270381be0cc693f807bbd39bf`、payloadは
`fb96050dfda25f98cde8718ee396284ccac5d535ac801d4231a57b882d1a8301`である。

最初のobserver commandは誤った旧ラベル`system/org.schedmd.slurm.slurmd`を照会して
`Could not find service`となったが、installed plist、driver、system domain上の実サービスはすべて
`org.schedmd.slurmd`で一致した。正しいラベルでrunning/PID 91811を再確認しており、これは
daemonやproduction設定を変更していないobserver側のラベル誤りである。

状態を`READY_TO_RUN_PHASE_RUNNING_RETEST_USER_ROOT_SHELL`とし、PC-210 root shellでの
承認済みdriver再実行を待つ。

Evidence: [`SMD-206-phase-b-retest-preflight.txt`](SMD-206-phase-b-retest-preflight.txt)

## Phase B Attempt 2 — PASS

2026-09-11 23:11 JST、修正版driverをPC-210 root shellから実行した。先行Job 412は
`gpu:apple:1`を要求してRUNNINGとなり、nodeはMIXED、CfgTRES/AllocTRESのgeneric/typed GPUは
restart前にすべて各1だった。後続Job 413はcanonical reason `Resources`を3回連続で記録した。

launchdのclean restartによりslurmdはPID 91811から94504へ交代した。Job 412はrestart後も
RUNNINGを維持し、heartbeatは1から10へ進んだ。nodeのCfgTRES/AllocTRESはrestart後も
generic/typed GPU各1で、Job 413も`PENDING Resources`を3回維持した。GPU countの消失、二重計上、
後続jobの早期起動は観測されなかった。

Job 412をcancelするとjobは`CANCELLED by 0`、batchは`CANCELLED 0:15`となり、job/batch双方に
generic/typed GPU TRESが残った。解放後、Job 413はApple M5 Max上でMLX 0.32.2を実行し、
4096×4096行列を5回計算して`gpu_smoke_test=PASS`、job/batchは`COMPLETED 0:0`となった。

最終状態はlaunchd running/PID 94504、controller UP、node IDLE、CPU/memory割当0、AllocTRES空、
queue 0、slurmstepd・対象process残留なしだった。`slurmd -G`はroot driver内でrestart前後とも
`gpu:apple:1 Count=1 File=/dev/null`を返し、production `slurm.conf`、`gres.conf`、plistのhashも
前後一致した。

独立readback時に非rootで追加実行した`slurmd -G`はroot所有のlog/keyを読めず失敗したため、
成功Evidenceには使用しない。root driverの前後2回の成功結果とproduction hash一致を採用する。
これはobserver権限差であり、running daemonやjob結果のfailureではない。

SMD-205で確認済みのidle restart Phase Aと、本AttemptのGPU job実行中restart Phase Bが揃ったため、
SMD-206全体を`PASS`とする。

Evidence: [`SMD-206-pass.txt`](SMD-206-pass.txt)

## 残る制約

- 今回確認したのはclean restart 1回であり、連続restartやSIGKILL restart時のGPU job生存は未確認
- `File=/dev/null`はscheduler allocation用placeholderで、未管理processからのMetal device isolationは証明しない
- Apple GPUのgpumem/gpuutil実使用量accountingは未確認
