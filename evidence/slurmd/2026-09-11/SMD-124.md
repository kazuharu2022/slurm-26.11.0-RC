## 対象と分離

- 対象: Apple M5 Max / arm64 / macOS worker `PC-210`
- Slurm: `26.11.0-0rc1`
- controller: Ubuntu 24.04 / x86-64上の`slurmctld`
- test user: `testuser=3001:3001`
- Phase A: Mac上の`slurmd` load、local `srun`、remote `slurmstepd`、job-script context

## 根拠

同梱`doc/man/man8/spank.8`では、local contextは`init`、`init_post_opt`、
`local_user_init`、`exit`、remote contextはtask前後を含むcallback、job-script
contextは`job_prolog`と`job_epilog`を実行すると定義される。また、SPANK設定は
Job起動ごとに再読込される。このためPhase Aはproduction `slurm.conf`へ一時的な
`PlugStackConfig`だけを追加し、daemon PIDを維持したまま測定する。

`ProctrackType=proctrack/pgid`では失敗時の`task_post_fork`にtimeout caveatがあるが、
Phase Aは全callbackが成功を返す正常系である。failure pathは本試験のPASS根拠に
含めない。

## Phase A Attempt 1 — `HARNESS_FALSE_NEGATIVE`

2026-09-11 19:32 JST、Job 372で`spank_config_active`となり、2-task `srun`自体は
rc 0だった。しかし、直後のcallback照合で`job_epilog`が0回だったためdriverは停止した。
cleanup開始時の実測stateは`COMPLETING`であり、Epilog完了前に照合していた。

その後のread-only確認では、Job 372と`.0` stepはともに`COMPLETED 0:0`、PC-210は
`IDLE`・`CPUAlloc=0`・`AllocMem=0`・queue空だった。production configとbackupは
SHA-256 `a820719e...2167`かつbyte比較0で一致した。smoke Jobはdriver停止位置より後なので
未投入であり、Attempt 1をPASSにはしない。

原因はSPANK callback failureではなくdriverの順序不備と判定する。`srun` rc 0だけでは
allocation Epilog完了を意味せず、実際にJobはまだ`COMPLETING`だった。修正版は次の順序にする。

1. `srun` rcとJob IDを取得する。
2. Jobが`squeue`から消えるまで待つ。
3. 全18 callbackを照合する。
4. jobと`.0` stepの`COMPLETED 0:0`をpollする。
5. configを復元してsmokeを実行する。

さらに成功・失敗の両経路でevent logをroot所有0444の
`spank-events-evidence.txt`へsnapshotする。修正版driver SHA-256は
`c406943f4118c9394060982f799f8ac802e4fe823234df34bff47e477a73212f`、`sh -n`と
承認なしexit 64、plugin再compileを確認した。生Evidenceは
[`SMD-124-attempt1.txt`](./SMD-124-attempt1.txt)に保存した。
