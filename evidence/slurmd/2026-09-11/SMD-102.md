# SMD-102 UID/GID不一致時のfail behavior

## 判定

- 状態: `PASS`（2026-09-22 production candidate runtime）
- release readiness: `PARTIAL`（clean-source rebuildとLinux分離buildは完了。広範なLinux runtime regressionとcommit provenanceは未実施）
- 対象: PC-210 / macOS / arm64 worker上のproduction slurmd
- controller: ubuntu2504 / Ubuntu 24.04 / x86-64
- 目的: controllerとworkerで同名userのnumeric UID/GIDが異なるとき、誤ったidentityでjobを実行しないか確認する

## SMD-101からの分離

SMD-101は両nodeで一致する2 userを使い、Jobs 355/356で正しいidentity、所有権、相互隔離、accounting、
資源解放を確認して`PASS`した。SMD-102は正常系を繰り返さず、意図的なID不一致だけを変更変数とする。

## ソースから確認できたこと

現行sourceでは、job credential作成時にcontroller側のpasswd/group情報を`identity_t`へ格納し、UID、GID、
user名、HOME、shell、supplementary GIDをpackする。

- [`src/interfaces/cred.c`](../../../../src/interfaces/cred.c): `fetch_identity(arg->uid, arg->gid, ...)`
- [`src/common/identity.c`](../../../../src/common/identity.c): passwd/groupからidentityを構築してpack

workerのslurmstepdではcredentialのnumeric UID/GIDをそのままstep recordへ設定する。

- [`src/slurmd/slurmstepd/slurmstepd_job.c`](../../../../src/slurmd/slurmstepd/slurmstepd_job.c):
  `step->uid = cred_arg->uid`、`step->gid = cred_arg->gid`
- [`src/slurmd/common/privileges.c`](../../../../src/slurmd/common/privileges.c):
  `setegid(step->gid)`、`setgroups(...)`、`seteuid(step->uid)`

確認した経路には、workerのlocal passwdで`pw_name`を引き直してcredentialのUID/GIDと一致確認する処理は
見つからなかった。これは「不一致jobが必ず実行される」という実測結果ではなく、fail-openの可能性を示す
source上の仮説である。

## Research Questionと仮説

RQ: controllerではUID/GID 3201、workerでは同名だがUID/GID 3202の隔離userからjobを投入した場合、
macOS slurmdはjobを拒否するか、controller由来のraw numeric IDで実行するか。

- H1（望ましい結果）: local identity不一致を検知し、payload実行前に明確なerrorでfail closedする。
- H2（sourceから懸念する結果）: workerにUID 3201のpasswd entryがなくても`seteuid(3201)`が成立し、raw UID/GID
  3201でpayloadが実行される。
- 反証条件: payloadの実UID/GID、終了code、slurmd log、sacctのいずれかが仮説と一致しなければ仮説を棄却する。

## 隔離設計

候補accountは既存の`testuser`、`testuser2`、`REDACTED_USER`を変更せず、SMD-102専用とする。

| node | user名 | UID:GID | password | HOME |
|---|---|---:|---|---|
| ubuntu2504 controller | `smdmismatch` | `3201:3201` | locked | `/home/smdmismatch` |
| PC-210 worker | `smdmismatch` | `3202:3202` | disabled、login window非表示 | `/Users/smdmismatch` |

安全条件:

1. workerのUID/GID 3201は未使用のままにし、controller credentialの3201が実在する別userへ対応しないようにする。
2. controllerのUID/GID 3202も未使用であることを確認する。
3. payloadは`/tmp`でnumeric UID/GIDとname解決結果を出力するだけにし、HOMEや既存fileへ書き込まない。
4. 1 job、1 task、1分以内とし、失敗時は次項目へ進まない。
5. fail-openを実測した場合はSMD-102を成功扱いにせず、macOS側のlocal identity照合修正を設計する。

## SMD-102本体試験driver

[`smd102_uid_gid_mismatch_driver.sh`](../../../../contribs/macos-tests/smd102_uid_gid_mismatch_driver.sh)を
Ubuntu controller上でrootから実行する。Mac clientから投入するとclient UID 3202が起点になり独立変数が
変わるため、controller上の`smdmismatch=3201:3201`として1件の`srun`だけを投入する。

固定条件と測定項目:

1. controller、node、queue、CPU/memory割当が正常か事前確認する。
2. Ubuntu上の`smdmismatch=3201:3201`と、Ubuntu上の3202未使用を再確認する。
3. `--nodes=1 --ntasks=1 --cpus-per-task=1 --mem=128M --time=00:01:00 --chdir=/tmp`に固定する。
4. payloadはfileを作成せず、固有marker、Job ID、Job user、実UID/GID、name解決、HOME、cwdだけをstdoutへ出す。
5. payloadが実行された場合は意図的にexit 86とし、通信失敗や通常成功と区別する。
6. stdout、stderr、`sacct`、終了後のIDLE・CPUAlloc=0・AllocMem=0・queue空を保存する。
7. 対象job nameを実行ごとに一意化し、失敗時cleanupもそのjobだけに限定する。

- markerあり: `FAIL_OPEN_PAYLOAD_EXECUTED`。実UID/GIDを確認し、Slurm側のlocal identity照合修正へ進む。
- markerなし: `PAYLOAD_NOT_EXECUTED_PENDING_ERROR_REVIEW`。stderr、slurmd log、`sacct`から拒否理由が明確か確認する。

## 2026-09-22 fail-closed修正とproduction runtime再試験 — PASS

Job 357のfail-open Evidenceを保持したまま、macOSに限定してcredentialのuser名をlocal Directory
Serviceで解決し、credential UID/GIDとlocal UID/primary GIDが一致しない場合はpayload起動前に
