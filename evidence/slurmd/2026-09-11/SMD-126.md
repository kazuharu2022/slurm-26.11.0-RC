# SMD-126 Mach-O plugin inventory and configured-context load

## 状態

`PASS`

## 対象と目的

- worker: Apple M5 Max / arm64 / macOS `PC-210`
- macOS: `26.5.1` / Darwin `25.5.0`
- Slurm: `26.11.0-0rc1`
- install prefix: `/opt/slurm/26.11.0`
- controller/database: Ubuntu 24.04 / x86-64
- 対象: installed Mach-O pluginの構造、依存関係、既知のweak import、実際のclient/
  `slurmd`経路によるconfigured context生成

SMD-102のsecurity blockerはユーザー指示により保留中であり、本試験はその判定を変更しない。

## Research Question

macOS向けにbuild/installしたSlurm plugin群は、arm64 Mach-Oとして必要なplugin metadataと
依存関係を保持し、実際に設定されたclient・accounting・MPI・topology・GRES経路で
`symbol not found`やplugin context初期化failureを起こさず利用できるか。

## 判定境界

全pluginを汎用processから単独`dlopen`することは成功条件にしない。
[`src/common/plugin.c`](../../../src/common/plugin.c)は`RTLD_LAZY`を使い、srunやslurmdなど
特定entityだけが提供するsymbolをpluginが参照できる設計である。そのため、Mach-O bundleの
undefined symbolが0件であること自体は正しい期待値ではない。

今回問題になったcontroller専用stateは、client/slurmdから同じbundleをloadしてもfatalに
ならないよう、次のweak dynamic lookupとして残ることを個別に検証する。

- `accounting_storage_slurmdbd.so`: `assoc_cache_cond`、`assoc_cache_mutex`、`running_cache`
- `topology_flat.so`: `idle_node_bitmap`

Phase AのPASSは「installed全pluginの静的棚卸し」と「現在の構成で到達できる代表的runtime
context」の合格を意味する。未設定・Linux専用・外部依存が必要なpluginまでruntime動作済みとは
扱わない。全77 pluginの全operationを実行する試験ではないため、SMD-126全体の`PASS`とは分ける。

## Phase A試験設計

[`smd126_plugin_inventory.sh`](../../../contribs/macos-tests/smd126_plugin_inventory.sh)は
production設定を変更せず、次をread-onlyで確認する。

1. `/opt/slurm/26.11.0/lib/slurm/*.so`を全件列挙する。
2. 各fileが`Mach-O 64-bit bundle arm64`であることを確認する。
3. Slurm loaderが必須とする`plugin_name`、`plugin_type`、`plugin_version` exportを確認する。
4. `otool -L`で依存関係を保存し、absolute `/opt/...` dependencyの欠落を検査する。
5. `nm -m -u`の全結果と集計を保存し、上記4 symbolがweak dynamic lookupであることを確認する。
6. 次の9 probeをproduction binary/configで実行し、終了code、stdout、stderrを個別保存する。

   - `sinfo`
   - `squeue`
   - `scontrol show config`
   - `scontrol show node PC-210`
   - `sacct -j 379`
   - `sacctmgr ping`
   - `srun --mpi=list`
   - `slurmd -C -f ...`
   - `slurmd -G -f ...`

7. controller/accounting/node/GRESの期待文字列を照合し、全probeからloader failure patternを検索する。

成功条件はarchitecture、metadata、absolute `/opt` dependency、undefined-symbol scan、
known weak symbol、9 probe、期待文字列、loader error countがすべて0 failureになることとする。

## Phase B — configured runtime job/step context

Phase Bはproduction設定を変更せず、現在のworker runtimeに対して次を確認する。

1. controller UP、node IDLE、割当0、queue空、slurmd PID、`gpu:apple:1`をpreflightする。
2. 実測en0 IPv4を使うdriver専用client configを作り、既知のshort-name問題を試験対象から分離する。
3. testuser `3001:3001`で2-task `srun --mpi=none`を実行し、task ID、identity、job/step accountingを照合する。
4. testuserで`--gres=gpu:apple:1`のbatchを実行し、`SLURM_JOB_GPUS=0`、job/batch accountingを照合する。
5. 試験期間のslurmd log差分とclient/job stderrからplugin loader errorを検索する。
6. queue空、node IDLE、割当0、slurmd PID維持、slurmstepd/test payload残留なしを確認する。
