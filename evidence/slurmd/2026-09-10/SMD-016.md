# SMD-016 macOS slurmd 24時間連続運転

## 判定

- 状態: `PASS`（2026-09-10 10:23:46～2026-09-11 10:23:46 JST、288 jobを完走）
- worker: PC-210 / macOS 26.5.1 / arm64 / slurmd 26.11.0-0rc1
- controller: ubuntu2504 / Ubuntu 24.04 / x86-64
- 実行時間: 86,400秒以上
- job投入間隔: 300秒（約288 job/24時間）

## Research Question

macOS上でlaunchd管理されるslurmdを24時間連続稼働させ、5分ごとに短いbatch jobを投入したとき、
daemon restart、job失敗、controller登録断、資源残留、FDまたはRSSの持続的増加が発生しないか。

## 仮説と反証条件

SMD-001～015で修正したsocket、mutex、signal、process cleanup、SACK、launchd、sleep/wake経路が
定常運転でも安定していれば、同一slurmd PIDで約288件が`COMPLETED 0:0`へ収束する。

次のいずれかを反証条件とする。

- boot epoch、slurmd PID、`SlurmdStartTime`が変わる
- controller ping失敗、nodeがIDLE以外のまま残る、または外部jobが混入する
- test jobまたはbatchが`COMPLETED 0:0`以外になる
- job終了後にCPUまたはmemory allocationが残る
- 先頭・末尾12 sampleのRSS平均差が16 MiBを超える
- FD最終増加が2、または一時最大増加が8を超える
- slurmd logにfatal、mutex、protocol、registration、not responding、abort系errorが出る

RSSとFDの閾値は「絶対に1 byte/1 FDも変動しない」という非現実的な条件を避けつつ、明らかな
単調リークを検出するための試験判定値である。PASS後もraw sampleの推移を記事に掲載する。

## 試験方式

[`smd016_soak.sh`](../../../contribs/macos-tests/smd016_soak.sh)をrootで起動する。macOS標準の
`caffeinate -ims`をrunnerの親に置き、試験中だけidle/system/disk sleepを抑止する。恒久的な
`pmset`設定変更は行わない。

各iterationではtestuserとして128 MiB、1 CPU、1分制限のjobを投入する。payloadはhostname、UID/GID、
開始・終了epochを記録して2秒で終了する。jobとbatchのaccounting、node IDLE、CPUAlloc/AllocMem解放を
確認してから次のiterationへ進む。外部jobを検出した場合は結果混同を避けるためfail closedする。

## 現在のEvidence

3回のtest-harness不備を修正した後、2026-09-10 10:23:46 JSTに24時間試験を開始した。
2026-09-11 10:23:46 JSTに288件のjobを失敗ゼロで完走し、最終`verify`も成功した。
現在の状態は`PASS`である。

### 初回start — BLOCKED

初回startはjob投入とmarker作成より前に、次のメッセージで停止した。

```text
error: launchd and pidfile slurmd identity mismatch
error: no active SMD-016 marker
```

独立したread-only確認では、launchdは`state=running`、PID 310、pidfileの内容も`310\n`で一致していた。
旧driverは「launchd PIDとpidfileが異なる」場合と「`kill -0`が失敗した」場合を同じ条件とメッセージへ
まとめていたため、この出力だけでは実際のidentity不一致を証明できなかった。job、marker、soak processは
作られておらず、cluster state変更もない。

修正版では次を個別に保存・判定する。

- `launchctl print`全体と`state=running`
- launchd PIDとpidfile PID、およびpidfileのbyte列
- PIDが指す`/opt/slurm/26.11.0/sbin/slurmd`のcommand line

root shellのcwdは`/var/root`（mode 750）であり、background runnerがこれを継承した。`sudo -u testuser`で
実行された`sbatch`はremote job用の`--chdir=/tmp`を適用する前にlocal `getcwd()`へ失敗した。このため
Slurm job IDは作成されず、active markerも残っていない。失敗markerとrun directoryはEvidenceとして
保持され、nodeの資源割当もゼロである。

修正版はbackground起動直前とrunner開始直後の両方で`/tmp`へ移動し、継承cwdと有効cwdを保存する。
またrunner早期終了時には`result`、`reason`、failed markerをterminalへ直接表示する。さらに
`/Users/REDACTED_USER`がmode 750であるため、payloadをrun directoryへmode 755でコピーし、testuserは
repo内ファイルではなくこのコピーを読む。HOME directoryの権限は変更しない。
