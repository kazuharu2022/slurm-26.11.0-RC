# SMD-015 macOS idle sleep/wake

## 判定

- 状態: `PASS`（idle Phase A=`PASS`、job実行中Phase B=`PASS`）
- worker: PC-210 / macOS 26.5.1 / arm64 / slurmd 26.11.0-0rc1
- controller: ubuntu2504 / Ubuntu 24.04 / x86-64
- 対象: jobなしのidle sleep/wake（Phase A）と、job実行中のshort sleep/wake（Phase B）

## Research Question

launchd管理下のslurmdを停止せずMacを短時間sleep/wakeした場合、同一processのままcontrollerへ
再接続し、nodeがIDLEへ戻り、後続jobを実行して資源を解放できるか。

## 試験を二段階に分ける理由

sleepはMac全体のnetworkとexecutionを停止し、remote sessionも切断する。最初からjob実行中に
試すと、controller timeout、task signal、process追跡、accountingの複数要因が同時に変化する。
そこでPhase Aはqueue空のidle sleep/wakeだけを対象とし、成功後にPhase Bとしてjob実行中の
sleep/wakeを設計する。

## 両端ログ・source照合

08:29 JSTのUbuntu側確認では`PC-210`は引き続き`DOWN+NOT_RESPONDING`だったが、名前解決は
`192.168.10.128`で正しく、同addressの6818/TCPへ接続できた。Mac側でも同一PID 310が
`TCP *:6818`をLISTENしていた。従ってF/W、名前解決、listen socket消失は除外できる。

```text
Mac: slurmd PID 310, TCP *:6818 LISTEN
Ubuntu: PC-210 -> 192.168.10.128
Ubuntu -> PC-210:6818 = SUCCEEDED
F/W_or_DNS_failure=EXCLUDED
```

source上では、[`_registration_engine()`](../../../src/slurmd/slurmd/slurmd.c)は最初の登録が成功して
`sent_reg_time`が非0になると終了する。一方、[`ping_nodes()`](../../../src/slurmctld/ping_nodes.c)は
`DOWN+NO_RESPOND` nodeへの通常pingを停止するが、`MAX_REG_FREQUENCY=20` pingごとに定期的な
registration requestを送る。controllerのping intervalは`SlurmdTimeout/3`である。

```text
SlurmdTimeout=300 seconds
ping_interval=300/3=100 seconds
MAX_REG_FREQUENCY=20
periodic_registration_upper_interval≈2000 seconds (33m20s)
driver_wait=180 seconds
```

従って今回証明したのは「180秒以内の自動復帰失敗」であり、定期registration window内の自動復帰は
未測定である。driverの180秒判定だけでmacOS timer不具合とは断定できない。次はcontrollerから
`State=RESUME`を発行し、slurmdを再起動せず同一PIDで即時回復するか確認する。成功すれば通信経路と
daemonは正常で、長時間sleep後の復旧待ち時間・運用policyが原因と確定できる。

分析記録: [`SMD-015-post-wake-registration-analysis.txt`](SMD-015-post-wake-registration-analysis.txt)

```text

```

## 明示RESUME初回 — DIAGNOSTIC_REQUIRED

完全sleep/wake後、Ubuntu controller上で次を実行したところ、状態遷移要求は拒否された。

```console
root@ubuntu2504:~# scontrol update NodeName=PC-210 state=resume
slurm_update error: Invalid node state transition
```

このメッセージだけではslurmd停止とは判定できない。直前の独立確認ではMac上のslurmd PID 310が
`*:6818`をLISTENし、Ubuntuから`PC-210:6818`へのTCP接続も成功している。

[`_valid_node_state_change()`](../../../src/slurmctld/node_mgr.c)では`RESUME`は基底状態が`DOWN`または
`FUTURE`、あるいは`DRAIN`、`FAIL`、reboot要求flagを持つ場合に許可される。一方、通常の`IDLE`から
`RESUME`は無効である。従って、要求時点までに定期registrationでnodeが自動的に`IDLE`へ戻っていた
可能性と、裸の`scontrol`が想定した26.11.0-0rc1 clientではない可能性を先に切り分ける。

未取得のEvidenceは次のとおりである。

- 要求直後の`show node`による現在state
- controllerログの`Invalid node state transition requested ... from=... to=...`
- `command -v scontrol`およびclient/controller version
- 同時点のMac launchd PID、process、6818 listener

これらを取得するまではdaemon restart、追加のstate変更、Phase Bのjob実行中sleepを行わない。

## 現在の判断

物理wake accessはuser-confirmedで、production terminalの`prepare`と独立readbackは`PASS`した。
idle Phase Aは`PASS`した。完全sleep/wake、同一slurmd PID、wake後約19分47秒での定期registration、

## job実行中sleep/wake Phase B — READY_TO_RUN

### Research Question

test jobがRUNNING中に、`SlurmdTimeout=300`未満の60～120秒だけMacをsleep/wakeした場合、同じslurmd、
batch、child processが生存し、wake後にjob heartbeatを再開して正常終了できるか。

### 仮説と反証条件

macOS sleep中はslurmdとjob processの実行が一時停止するが、短時間であればcontroller timeout前にwakeし、
同じPIDで通信とheartbeatを再開できると予想する。次のいずれかが起きれば仮説を反証する。

- boot epoch、slurmd PID、`SlurmdStartTime`のいずれかが変わる
- 保存したbatchまたはchild PIDが消失する
- heartbeatがwake後に進まない
- heartbeatから推定した停止時間が30秒未満、または`SlurmdTimeout`以上
- jobまたはbatchが`COMPLETED 0:0`以外になる
- 終了後にprocess、queue、CPU、memory割当が残る

### 試験設計

[`smd015_job_sleep_wake.sh`](../../../contribs/macos-tests/smd015_job_sleep_wake.sh)を`prepare`と`verify`の
二段階で実行する。heartbeat workloadは
[`smd015_job_sleep_payload.sh`](../../../contribs/macos-tests/smd015_job_sleep_payload.sh)である。

`prepare`はidle Phase A completed marker、queue空、node IDLE、launchd、PID/pidfile、controller、固定IP、
`SlurmdTimeout`を確認してから30分制限の専用Jobを投入する。batch/child PIDとheartbeatをroot所有markerへ
保存するが、sleep自体は実行しない。

物理consoleではScreen Sharingを切断し、`pmset sleepnow`後60～120秒でwakeする。`verify`はsleep count、
同一boot/slurmd/job PID、RUNNING state、heartbeat再開と推定停止時間を検証する。その後finish markerでjobを
正常終了させ、jobとbatchのaccounting、process消失、最終IDLEと資源解放を確認する。

sleep countが増えていない状態でverifyした場合、RUNNING jobとmarkerを維持して再試行可能とする。
完全sleep後の検証に失敗した場合はtest jobをfinish/cancelして残留を防ぐ。
