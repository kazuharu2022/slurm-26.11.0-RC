# SMD-301 `task/affinity` negative test

## 判定

`PASS_EXPECTED_UNSUPPORTED`

macOS nodeではLinux互換のstrict CPU pinningは行われない。`--cpu-bind`指定は
`SLURM_CPU_BIND` / `SLURM_CPU_BIND_LIST`というrequest metadataとしてpayloadへ渡るが、
Slurmがprocessを指定CPUへ拘束したことを示す成功messageは出なかった。Jobの
`COMPLETED 0:0`はpayload実行の成功であり、CPU binding成功のEvidenceではない。

## 問いと成功条件

問いは、Mac workerへCPU bindを要求したときに、Linux同等のpinningが行われたと
誤表示されないかである。

- controlの`--cpu-bind=none`が正常に動く。
- `map_cpu:0`、`map_cpu:1`、2-taskの`cores`を個別に実行する。
- payload内でstrict affinity APIの有無とMach affinity readbackを観測する。
- bind成功を示すSlurm messageがないことをdaemon/client出力で確認する。
- 最終的にnode IDLE、queue空、同一launchd PID、production artifact不変となる。

仮説は、macOSでは`SLURM_CPU_BIND*` metadataは設定されてもLinux互換のpinningは
行われず、Slurmもmaskを設定したとは表示しない、である。反証条件は、
strict affinity symbolの存在、`sched_setaffinity`成功、または`cpu-bind ... set`等の
成功messageである。

## 環境

- Mac worker: Apple M5 Max、arm64、18 logical CPU、Darwin 25.5.0
- Slurm: 26.11.0-0rc1
- controller: Ubuntu x86-64、`192.168.10.180`
- test identity: `testuser=3001:3001`
- 実行前: PC-210 `IDLE`、`CPUAlloc=0`、`AllocTRES`空、queue空
- Mac launchd: production `slurmd` PID 70710
- controller profile: `TaskPlugin=task/affinity`

dependency追加、production config変更、daemon再起動は行っていない。

## 実装契約の確認

[`src/common/xsched.c`](../../../src/common/xsched.c)のApple分岐は
`xsetaffinity()`で`errno=ENOTSUP`、return `-1`とする。`task` pluginとこの移植層に
`thread_policy_set`利用はなく、Machのaffinity hintへ置き換えた実装でもない。

実probeでは`dlsym()`により`sched_setaffinity` / `sched_getaffinity` symbolが
どちらも`ABSENT`だった。`thread_policy_get(THREAD_AFFINITY_POLICY)`は
`KERN_NOT_SUPPORTED(46)`であり、affinity tagはreadback不能だった。なおMachの
`THREAD_AFFINITY_POLICY`自体も同一tagのthreadを可能なら同じL2 cacheへ寄せるhintで、
特定CPUへ拘束するLinuxのstrict affinityと同義ではない。

## 実測

最初の直接probeでJob 666は`--cpu-bind=verbose,map_cpu:0`を指定して
`COMPLETED 0:0`となり、payloadに`bind=verbose,map_cpu:0 list=0`が渡った。
一方、bind成功messageはなかった。この観測を固定driverへ拡張した。

| case | Job | request metadata | probe結果 | accounting |
|---|---:|---|---|---|
| control | 671 | `quiet,none` | strict symbolなし、Mach readback非対応 | `COMPLETED 0:0` |
| map CPU 0 | 672 | `verbose,map_cpu:0` / list `0` | 同上 | `COMPLETED 0:0` |
| map CPU 1 | 673 | `verbose,map_cpu:1` / list `1` | 同上 | `COMPLETED 0:0` |
| 2-task cores | 674 | `verbose,cores`、local rank 0/1 | 2 processとも同上 | `COMPLETED 0:0` |

client出力とlaunchd log deltaには`cpu-bind ... set`、`affinity ... set`、
`sched_setaffinity`がなかった。したがってmetadataの存在をbinding成功とは扱わない。

## 失敗履歴

1. Attempt 1は`xcrun --find`で得たclangを直接呼び、SDK include pathが失われて
   `dlfcn.h`を見つけられずJob投入前に停止した。`xcrun --sdk macosx clang`へ修正した。
2. Attempt 2はprobeが0755でも`mktemp`親directoryが0700だったため、Jobs 667〜670が
   `execve ... Permission denied`、`FAILED 13:0`になった。affinity結果ではない。
   Evidence directoryを0711、payload subdirectoryを0755へ分離した。
3. 再試験前にPID 70710、node IDLE、queue空を再確認した。失敗Jobも削除せず保持した。

## 制約

これはmacOSでCPU pinningが非対応であり、metadataをenforcementと誤認してはいけない
ことのnegative Evidenceである。P-core/E-core配置、core migration、NUMA相当の性能、
advisory affinityの将来実装は確認していない。Linuxの`task/affinity`と同等に動作したとは
扱わない。
