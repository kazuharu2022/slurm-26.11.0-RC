# SMD-303 cgroup device/process隔離 negative test

## 判定

`PASS_EXPECTED_UNSUPPORTED`

macOS buildで`proctrack/cgroup`、`task/cgroup`、および
`CgroupPlugin=cgroup/v2` + `ConstrainDevices=yes`を個別に選択した3つの隔離候補は、
すべて1秒未満で非0終了し、選択したplugin名とcontext生成失敗を明示した。
候補daemonがno-opで起動成功する経路はなかった。

production daemon、設定、plugin、launchd plistは変更していない。試験前後で
`slurmd` PID 70710、node `IDLE`、CPU/memory割当0、queue空、対象5 fileのSHA-256一致を
確認した。

## Research Questionと仮説

RQは「Linux cgroupがないmacOS buildでcgroup process/task/device制御を選択したとき、
成功したように見せず、利用者が原因を特定できる形で停止するか」である。

仮説は次のとおり。

1. `ProctrackType=proctrack/cgroup`は`proctrack_cgroup.so`不在を明示して停止する。
2. `TaskPlugin=task/cgroup`は`task_cgroup.so`不在を明示して停止する。
3. `CgroupPlugin=cgroup/v2`と`ConstrainDevices=yes`は`cgroup_v2.so`不在を明示し、
   device制約を適用したふりをせず停止する。

## 前提確認

実測buildは`config.h`で`WITH_CGROUP`未定義、`config.status --config`で
`--disable-cgroupv2`だった。installed plugin directoryには次の4 fileが存在しなかった。

- `cgroup_v1.so`
- `cgroup_v2.so`
- `proctrack_cgroup.so`
- `task_cgroup.so`

`src/interfaces/cgroup.c`は`WITH_CGROUP`未定義時の既定値を
`CgroupPlugin=disabled`相当にする。一方、明示的にcgroup pluginを選ぶと、
`cgroup_g_init()`、`proctrack_g_init()`、`task_g_init()`はcontext生成失敗を返す。

## 安全な隔離条件

再実行用driverは
[`smd303_cgroup_negative_driver.sh`](../../../contribs/macos-tests/smd303_cgroup_negative_driver.sh)
である。候補はすべてUID 501の`tera`としてsudoなしで実行した。

- controller addressは`127.0.0.1`、portは26817/26827/26837。
- worker portは26818/26828/26838。
- pid file、spool、state、logはrun directory内へ分離。
- productionの6817/6818、`/var/run/slurmd.pid`、production spoolを候補に使用しない。
- 10秒以内に失敗しなければ候補を終了し、silent/no-op startupとしてFAILにする。
- candidate PID fileとlistenerの残留を各case後に検査する。
- jobは投入しない。

## 実測結果

| case | 意図した設定 | rc | 観測した拒否 |
|---|---|---:|---|
| process | `ProctrackType=proctrack/cgroup` | 1 | `cannot create proctrack context for proctrack/cgroup` |
| task | `TaskPlugin=task/cgroup` | 1 | `cannot create task context for task/cgroup` |
| device | `CgroupPlugin=cgroup/v2`, `ConstrainDevices=yes` | 1 | `cannot create cgroup context for cgroup/v2` |

3 caseとも最後に`slurmd initialization failed`を出し、candidate pid file、worker portの
listenerは残らなかった。canonical run directoryは
`/private/tmp/slurm-smd303-20260923T191136.Nucfhz`である。

生出力、driver hash、production hash、node readbackは
[`SMD-303-runtime-evidence.txt`](SMD-303-runtime-evidence.txt)へ保存した。

## ハーネス失敗の保持

driver初回は候補を起動する前に`production slurmd pid 70710 is not running`で停止した。
原因は、非root processからroot所有processへの`kill -0`が、生存中でも権限エラーになる点を
生存失敗と誤判定したことだった。生存確認をread-onlyの`ps`照合へ変更した。

この初回停止ではcandidate未起動、job未投入、production変更なしである。失敗を
cgroup結果には数えず、修正版の全工程だけを最終判定に用いた。

## production不変の確認

試験前後で次を確認した。

- launchd管理の`slurmd` PIDは70710で不変。
- `PC-210`は`IDLE`、`CPUAlloc=0`、`AllocMem=0`、`AllocTRES`空。
- queueは空。
- production `slurm.conf`、`slurmd`、`proctrack_pgid.so`、`task_affinity.so`、
  launchd plistのSHA-256は前後一致。
- 3候補のpid fileとTCP listenerは残留なし。

## 結論と限界

SMD-303の成功条件である「cgroup pluginを選ぶと明確に非対応となり、no-op成功しない」は、
process、task、deviceの3経路で成立した。したがって状態を
`PASS_EXPECTED_UNSUPPORTED`へ更新する。

これはcgroup機能の成功ではない。kernel強制隔離、cgroup付きjob、Linux cgroup v2との同等性は
確認しておらず、macOSにはCPU・memory・deviceのcgroup隔離がないという制約を維持する。
次の未完了negative testはSMD-304のjob accounting metricsである。
