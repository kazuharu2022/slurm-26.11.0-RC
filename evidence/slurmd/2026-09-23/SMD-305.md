# SMD-305 core specialization / CPU frequency negative test

## 判定

`PASS_EXPECTED_UNSUPPORTED`

macOS production workerではcore specializationもSlurmのLinux cpufreq制御も機能しないが、
要求が有効化されたように見える状態、daemon停止、job失敗、資源残留にはならなかった。

- `--core-spec=1`は`AllowSpecResourcesUsage=no`により明示的にignoreされ、Job 681は
  `CoreSpec=*`、`NumCPUs=1`、`Exclusive=NO`のcontrol相当で完了した。
- `srun --cpu-freq=performance`はStep 682.0の`Governor=Performance`とpayload環境
  `SLURM_CPU_FREQ_REQ=Performance`へ要求metadataを渡したが、MacにはSlurmが使用する
  `/sys/devices/system/cpu/cpu0/cpufreq`がなく、実装は`cpu_freq_count=0`でsetter前に戻る。
- control、core-spec、CPU-frequencyのJobs 680〜682と全batch/stepは
  `COMPLETED 0:0`。最終nodeは`IDLE`、割当0、queue空、`slurmd` PID 70710、
  production 5 artifactのSHA-256は不変だった。

## Research Questionと仮説

RQは「macOSで非対応のcore specializationとLinux cpufreq制御を要求したとき、利用者へ
制約を示しつつ、daemon、job、資源状態を整合したまま維持できるか」である。

仮説は次のとおり。

1. macOSの`_core_spec_init()`は非対応logを出すが成功を返し、daemon起動を妨げない。
2. `AllowSpecResourcesUsage=no`では`--core-spec`を明示的にignoreし、job recordから
   specializationをclearする。
3. CPU-frequency要求はstep metadataへ残るが、Linux cpufreq sysfsがないためSlurmの
   frequency setterはno-opとなる。
4. control、core-spec、CPU-frequencyの3 caseは完了し、nodeと資源は回収される。

## 環境と一次情報

実測環境はApple M5 Max / arm64 / macOS 26.5.1、Slurm 26.11.0-0rc1である。
controllerの実効設定は次だった。

```text
AllowSpecResourcesUsage = no
CpuFreqDef              = Unknown
CpuFreqGovernors        = OnDemand,Performance,UserSpace
LaunchParameters        = (null)
SelectType              = select/cons_tres
TaskPlugin              = task/affinity
TaskPluginParam         = (null type)
```

同梱の公式`doc/html/core_spec.shtml`は、core specializationには`select/cons_tres`と
`task/cgroup`が必要で、他構成ではjobのcore specialization optionをclearするとしている。
今回のworkerは`task/affinity`であり、SMD-303で`task/cgroup`とcgroup pluginの欠落も
確認済みである。

source対応は次のとおり。

- `src/slurmd/slurmd/slurmd.c:3232-3236`はApple buildで
  `_core_spec_init: not supported on macOS`を出し、`SLURM_SUCCESS`を返す。
- `src/common/slurm_opt.c:5297-5301`は`AllowSpecResourcesUsage=no`時に`-S`をignoreする。
- `src/slurmctld/job_mgr.c:8987-8992`はASRU無効時にjobの`core_spec`を`NO_VAL16`へclearする。
- `src/common/cpu_frequency.c:63`はLinux sysfsを固定pathとして使い、同297-300はpathが
  なければ`CPU frequency setting not configured for this node`を出して初期化を終了する。
- 同436-481のtask/affinity経路と同1155-1162のsetterは`cpu_freq_count=0`ならreturnする。

したがって`AveCPUFreq=0`だけを根拠にせず、実path不在、startup log、sourceの早期return、
step metadataを組み合わせて「SlurmのLinux cpufreq setterは動かない」と判定した。

## 失敗履歴

### Attempt 1: 出力directory権限

run directory `/private/tmp/slurm-smd305-20260923T214019.hmZRfD`では、control Job 676の
出力とmarkerをmode 0711の親directory直下へ置いたため、testuserが作成できなかった。
payload未実行、Job 676は`FAILED 0:53`、batchはdriver cleanupにより`CANCELLED 0:53`となった。
nodeは`IDLE`、割当0へ回収された。

これは機能結果ではなくharness failureである。書込専用`job-output` directoryをmode 0777で
分離し、payloadとdriverの構文・差分検査後に再実行した。

### Attempt 2: sleep交絡

run directory `/private/tmp/slurm-smd305-20260923T214503.e9TBB2`のJobs 677〜679は機能上
すべて`COMPLETED 0:0`だった。しかし電源logはJob実行中の21:45:14と21:46:28に
Maintenance Sleep、21:47:42〜21:52:43に通常Sleepを記録した。control Job 677の
`ElapsedRaw=39`も12秒payloadと整合しない。

起床後、controllerは21:53:24にPC-210を`DOWN+NOT_RESPONDING`へ移した。PID 70710、
launchd、controller service、networkは生存しており、ユーザーが21:56:16にPID 70710へ
SIGHUPを送ると、PIDを変えずに`IDLE`へ復帰した。この結果をSMD-305の機能失敗には数えず、
sleep交絡として保持した。

driverを`caffeinate -is`配下で自己実行するよう修正し、Attempt 3をcanonical resultとした。

## Attempt 3 canonical runtime

canonical run directoryは`/private/tmp/slurm-smd305-20260923T215730.1AY62Z`である。
21:57:30〜21:58:39に`caffeinate` assertionが保持され、この区間にSleep eventはない。

| case | Job/step | 要求とlive readback | 終了結果 |
|---|---|---|---|
| control | 680 / batch | `CoreSpec=*`, `NumCPUs=1`, CPU freq環境なし | 両方`COMPLETED 0:0`, 13秒 |
| core specialization | 681 / batch | submit時に`Ignoring -S...`、`CoreSpec=*`, `NumCPUs=1`, `Exclusive=NO` | 両方`COMPLETED 0:0`, 12秒 |
| CPU frequency | 682 / batch / 682.0 | step `Governor=Performance`、payload `cpu_freq_req=Performance` | 全て`COMPLETED 0:0`, 13秒、step `AveCPUFreq=0` |

core-spec caseはcontrolと同じ1 CPU、128 MiBを割り当て、specialized coreも暗黙の全node排他も
記録しなかった。CPU-frequency caseは要求metadataを保存したが、物理周波数を変更した証拠はなく、
上記source経路からSlurm setterは実行されない。

生出力、source対応、全accounting、hash、sleep/recovery履歴は
[`SMD-305-runtime-evidence.txt`](SMD-305-runtime-evidence.txt)へ保存した。

## production不変と最終状態

- `slurmd` PIDは全工程後も70710、PPID 1、launchd state `running`。
- PC-210は`IDLE`、`CPUAlloc=0`、`AllocMem=0`、`AllocTRES`空、queue空。
- `slurmd`、`slurmstepd`、`task_affinity.so`、`slurm.conf`、launchd plistのSHA-256は
  canonical run前後と独立readbackで一致。
- canonical log deltaはJobs 680〜682のbatch launchとStep 682.0 launchだけで、
  daemon failureはない。
- production config変更、launchd restart、package追加は実施していない。

## 結論と限界

SMD-305の成功条件である「非対応warningだけでdaemon/jobが不整合状態にならない」は、
sleep交絡を除去したcanonical runtimeで成立した。状態を`PASS_EXPECTED_UNSUPPORTED`へ更新する。

これはcore isolationやCPU frequency制御の成功ではない。`AllowSpecResourcesUsage=yes`や
`CoreSpecCount`/`CPUSpecList`をproductionへ導入する試験、Apple固有APIでの周波数制御、
物理周波数の独立測定、性能差比較は行っていない。core specializationには公式上
`task/cgroup`が必要で、現行macOS構成では利用できない。

これでSMD-301〜306のmacOS固有negative testは全件runtime確認済みとなる。
