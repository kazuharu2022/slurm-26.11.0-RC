# SMD-011 controller restart — 試験記録

## 判定

- 日時: 2026-09-09 19:45 JST–
- 状態: `PASS`
- worker: PC-210 / macOS / arm64 / slurmd 26.11.0-0rc1
- controller: ubuntu2504 / Ubuntu 24.04 / x86-64 / systemd slurmctld

## Research Question

PC-210でjob processが実行中のままprimary slurmctldを正常restartしたとき、macOS版
slurmd/slurmstepdはjobを継続して追跡し、controller復旧後に同じjobを自然終了させ、
さらに新規jobを受け付けられるか。

## 仮説と反証条件

仮説は、controller restart中もworker上のjob heartbeatと親子PIDが維持され、復旧した
controllerへnode/job stateが再同期されることである。次を反証条件とする。

- slurmd、slurmstepd、job processのいずれかが意図せず終了する。
- controller再起動後に実行中jobが消失、重複、または不正なstateになる。
- heartbeatが停止する。
- job自然終了後にcontroller/accountingが`COMPLETED 0:0`へ収束しない。
- process、allocation、credential、SACKが残留する。
- 後続GRES付きjobを起動できない。

## 実験方式

Macからubuntu2504へ非対話SSH接続できないことを確認したため、誤ってSSH認証やcontroller
設定を変更せず、二端末で実施する。

1. PC-210でobserverを起動する。
2. observerが`SMD011_WAITING_FOR_CONTROLLER_RESTART`を表示するまで待つ。
3. ubuntu2504のroot shellで`systemctl restart slurmctld`を1回だけ実行する。
4. PC-210 observerがcontrollerの`sdiag Data since`変更を検知する。
5. heartbeat進行、同一PID、job RUNNINGを確認後、jobへ正常終了markerを渡す。
6. Job/accounting、後続GRES job、node resource、processを確認する。

controller再起動の検知は接続失敗の瞬間だけに依存しない。再起動前後の`sdiag`先頭にある
`Data since ... (epoch)`が変わったことを必須条件にする。

## 成功条件

1. controllerのMainPID、ActiveEnterTimestamp、`sdiag Data since`が更新される。
2. 6817 listenerと`scontrol ping=UP`が復旧する。
3. Jobはrestart前後でRUNNING、heartbeat countが増加する。
4. slurmd、batch、child PIDがrestartをまたいで維持される。
5. finish marker後、job/stepが`COMPLETED 0:0`になる。
6. 後続GRES付きhostname jobが`COMPLETED 0:0`になる。
7. queue、job process、CPU/memory allocationが残らない。
8. 最終行に`SMD011_ROOT_RUN_COMPLETE`が表示される。

## 安全策と停止条件

- PC-210にactive jobがあればobserverはrestart依頼前にexit 75で停止する。
- test jobはexclusive、最大15分で、observerからfinish markerを受けて自然終了する。
- controller restartが検知できなければ、observerはtest jobだけをcleanupする。
- `systemctl restart`以外のcontroller config/database変更は行わない。
- controllerが復旧しない場合は再restartを繰り返さず、ubuntu2504でservice status、journal、
  6817 listenerを確認してSMD-012へ進まない。

## 初回試験 — `BLOCKED`

初回のobserverは2026-09-09 19:48:57 JSTに開始した。Job 50は19:48:57から
RUNNINGとなり、batch PID 91822、child PID 91823、heartbeat count 0を記録した。
observerはcontrollerの旧`Data since=1788918618`をattempt 0～59の60回確認し、最後の
`sdiag`は19:50:01（epoch 1788951001）だった。その後19:50:02に試験harnessのcleanupが
Job 50をcancelした。

ubuntu2504側で確認した再起動直前の時刻は19:49:56で、Job 50はRUNNINGだった。しかし
`systemctl restart slurmctld`完了は19:50:12であり、observerのcleanupより10秒後だった。
controllerはMainPID 428169から449767へ変わり、6817 listenerと`scontrol ping=UP`も回復した。
再起動後の`sdiag Data since`は19:50:13（epoch 1788951013）へ更新されている。

したがって、controller再起動自体は成功したが、Job 50は再起動前にharnessがcancelしており、
「実行中jobがcontroller restartをまたいで継続するか」は未判定である。再起動後にqueueから
Job 50が消えていたことも、controller restartによる消失の証拠ではなくharness cleanupの結果である。

会計はJob 50=`CANCELLED 143:0`、batch step=`FAILED 143:0`。最終確認時のworkerは
slurmd PID 85145を維持し、node=`IDLE`、`CPUAlloc=0`、`AllocTRES=`だった。

## 原因と修正

原因はSlurmではなく試験harnessの観測時間不足である。observerはrestart依頼を表示してから
約60秒でtimeoutしたが、手動操作を含むcontroller restartは表示から約75秒後に完了した。

修正内容:

- controller restart検知を60回から300回（通常時は約5分）へ延長。
- observerに観測回数を明示表示。
- test jobのtime limitを10分から15分へ延長。
- survivor workloadの待機上限を540秒から840秒へ延長。

Slurm source、production binary、production config、稼働中slurmdは変更していない。

## 2回目試験 — `PASS`

修正版observerでJob 51を投入した。Jobはbatch PID 94026、child PID 94027で起動し、
controller restart前後にheartbeatが0から19へ進んだ。slurmd PID 85145と起動時刻は
試験前後で変わっていない。

controller restart中の`sdiag`は、旧`Data since=1788951013`、接続拒否、一時的な
`Data since=0`の順に遷移した。安定した非zeroの新epochはこの試行中には保存できていないが、
統計のreset、直後のnode registration応答、既存jobの認識、新規job dispatchにより、
controllerの停止・再起動・service復帰を確認した。

slurmdは20:00:42にnode registrationを処理し、その際にJob 51をapparently runningとして
報告した。同じJob 51はfinish markerを受けて20:00:42に正常終了し、jobとbatch stepは
ともに`COMPLETED 0:0`となった。続くGRES要求付きJob 52も`PC-210.local`を出力し、jobと
batch stepが`COMPLETED 0:0`となった。

最終状態はnode=`IDLE`、`CPUAlloc=0`、`AllocTRES=`、Jobs 51/52のqueue残留なしである。
したがって、controller restart中の既存job継続、復旧後のnode再登録、job完了通知、
新規job受付を確認できたためSMD-011を`PASS`とする。

### observer検知ロジックの補正

2回目のobserverはcontroller初期化中の`Data since=0`を「旧epochと異なる値」として早期に
受理した。この値だけでは安定復旧の根拠にならない。ただし、同じ試験の後続確認でJob 51の
RUNNING維持、slurmd再登録、正常完了、Job 52成功を独立に確認したため、
製品動作の判定には影響しない。

今後の誤検知を防ぐため、observerは空値、非数値に加えてepoch 0も受理しないよう修正した。
これは試験harnessだけの変更であり、Slurm source/binary/configには変更していない。
