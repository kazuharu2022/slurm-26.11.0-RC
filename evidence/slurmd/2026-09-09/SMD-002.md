# SMD-002 対話PTY — 試験計画とEvidence

## 判定

- 日時: 2026-09-09 16:16–16:42 JST
- 状態: `PASS_STAGING`
- 前提: SMD-001はstaging構成で `PASS_STAGING`
- 対象: 対話shell、stdin/stdout、PTY割当、terminal resize、Ctrl-C、終了時の
  local terminal設定復元
- 初回試験: Job 20で `--pty` がmacOS非対応として無視され、対話shellにならず失敗

## 成功条件

1. 対話bashのpromptが表示され、入力したcommandが実行される。
2. `hostname` が `PC-210.local`、`id` が `testuser` を示す。
3. `tty` が `not a tty` ではなくPTY device pathを返す。
4. resize前後の `stty size` が異なり、SIGWINCH/terminal sizeが転送される。
5. `sleep 60` だけがCtrl-Cで終了し、bash promptへ戻る。
6. `ctrl_c_rc=130` を返す。
7. `exit 0` 後、local shellへ戻り `srun_rc=0`、`tty_restore=PASS` となる。
8. job/stepが終了し、`srun`、`slurmstepd`、`sleep`、対話bashが残らない。

いずれか一つでも満たさない場合はSMD-003へ進まず、client、controller、slurmdの
状態を採取してSMD-002を `FAIL` または `BLOCKED` とする。

## 実測結果

### Job 20: FAIL

ユーザーが2026-09-09 16:19 JSTに試験を開始した直後、次のerrorが出た。

```text

```

対話promptは現れず、Ctrl-Cはtask shellではなく `srun` のinterrupt handlerが
受け取った。複数回のCtrl-C後にstepを強制終了した。

```text

...
^Csrun: sending Ctrl-C to StepId=20.0

srun: Job step aborted: Waiting up to 32 seconds for job step to finish.
```

slurmd logではtask 0がSIGINT（signal 2）で終了し、I/O handlerとstep cleanupは
完了した。

```text

[2026-09-09T16:20:52.304] [20.0] get_exit_code task 0 died by signal: 2
[2026-09-09T16:20:52.322] [20.0] stepd_cleanup: done with step (step_rc: 2, slurm_rc: 0 - No error)
```

controller/databaseの記録:

```text

20     bash     testuser  CANCELLED+  2026-09-09T16:19:27  2026-09-09T16:20:52 00:01:25 0:0       PC-210
```

終了後はqueueが空で、PC-210は `CPUAlloc=0`、`State=IDLE`、`AllocTRES`空へ
復帰した。`srun`、`slurmstepd`、Job 20のbashは残っていなかった。process名
`sleep` は別のroot所有installerがJob 20終了後に生成したPIDであり、Job 20由来
ではないことをparent PIDと開始時刻で分離した。

PTY割当、terminal resize、task shellへのCtrl-C、terminal設定復元は一つも
成立していないため、Job 20は明確に `FAIL` とする。

## 原因

configureの実測は次のとおりだった。

```text
checking for pty.h ... no ('pty.h' file not found)
checking for cfmakeraw ... yes
checking for openpty in -lutil ... yes
```

macOSではLinuxの `<pty.h>` ではなく `<util.h>` が `openpty()` と
`login_tty()` を提供する。このsource treeの `slurmstepd` は既に
`__APPLE__` の場合に `<util.h>` をincludeして `HAVE_PTY_API` を有効化するよう
修正済みであり、installed `slurmstepd` にも `_openpty` と `_login_tty` の参照が
存在した。

一方、`src/srun/opt.c` のoption検証とhelp表示は `HAVE_PTY_H` だけを条件にして
いた。したがって、worker側にはmacOS PTY実装があるのに、client側がlaunch前に
optionを捨てていた。Job 20の直接原因はこのcapability判定の非対称である。

## 修正

`src/srun/opt.c` の2箇所を、`pty.h` があるplatformまたはmacOSならPTYを有効に
する条件へ変更した。

```c
#if defined(HAVE_PTY_H) || defined(__APPLE__)
```

対象は次の2箇所である。

1. `_opt_verify()` の `--pty` option検証。
2. `_help()` の `--pty` help表示。

stepd側の既存macOS `openpty()` 実装は変更していない。

### 判定

確認できた項目:

- PTY optionが保持され、remote bash promptが表示された。
- PTY上で `stty size` が値を返した。
- `exit 0` 後にlocal shellへ戻った。
- `srun_rc=0`。
- `tty_restore=PASS`。
- job終了後のqueue/process cleanup。

未確認または不合格の項目:

- `hostname`、`id`、`tty` の出力が今回の提供ログにない。
- resize前後の `stty size` が1値しかなく、SIGWINCH転送を判定できない。
- `ctrl_c_rc=0` のため、`sleep` がSIGINTで終了した証拠がない。Ctrl-C未入力、
  入力timing、signal未配送のどれかは現時点では区別できない。
- 対話開始から途中報告を挟み、3分のtime limitを超えたためjobは `TIMEOUT`。

したがってSMD-002全体は `PASS` にせず、`PARTIAL_RETEST_REQUIRED` とする。
source修正のPTY有効化効果は確認できたため、追加source修正は行わず、10分の
time limitで操作を中断せず再試験する。

## 第2再試験成功: Job 22

ユーザー提供の対話session出力:


最初のresize確認では値が変わらなかったが、さらにresizeした後の再確認で
`41x89` から `34x100` へ変化した。従って、SIGWINCHによるwindow size転送は


### 最終判定

PTY割当、stdin/stdout、正しいuser identity、PTY device、terminal resize、
Ctrl-C、shellの正常終了、local terminal設定復元、job/step正常終了、queueと
process cleanupをすべて確認した。SMD-002を `PASS_STAGING` とする。

ただし、修正版 `srun` はstaging artifactでありproduction install前である。
