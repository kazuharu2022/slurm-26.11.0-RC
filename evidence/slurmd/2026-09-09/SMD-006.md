# SMD-006 time limit — 試験計画とEvidence

## 判定

- 日時: 2026-09-09 17:31 JST–
- 状態: `PASS_STAGING`
- 前提: SMD-001～SMD-005はstaging構成で `PASS_STAGING`
- 対象: job time limit到達時のSIGTERM、state、process cleanup

## Research Question

macOS上の `slurmd` / `slurmstepd` は、実行中jobがtime limitへ到達したとき、
controllerからの終了要求をprocessへ配送し、jobを`TIMEOUT`として記録してprocessと
resourceを回収できるか。

## 仕様と固定条件

source tree付属の `sbatch(1)` は、time limit到達時に各taskへSIGTERMを送り、
必要なら`KillWait`後にSIGKILLを送ると説明している。またtime limitの分解能は1分で、
秒指定は次の1分へ切り上げられる。このため5秒試験にはせず、最小の1分を使う。

- job time limit: `00:01:00`
- workload: `sleep 180`
- resource: 1 CPU、1 GiB
- config: `KillWait=30`、既定の`OverTimeLimit=0`
- staging: `/tmp/slurm-smd001-fixed`

workloadはbatch shellとchild `sleep`のPIDを記録し、TERMを受けた場合は時刻と
batch PIDをstdoutへ記録してexit 124する。driverはこのjobへ`scancel`を送らず、
time limitによる自然な終了だけを待つ。

## 安全範囲

- workloadは180秒で自然終了し、jobには1分のtime limitがある。
- driverが異常終了した場合だけ、作成した正確なjob IDをEXIT trapでcancelする。
- PID指定のsignal、daemon操作、controller操作、config変更は行わない。
- 全メモリ要求を避けるため`--mem=1G`を明示する。

## 実行方法

Macの`testuser` sessionで実行する。time limitの分解能により約1分かかる。

```bash
/tmp/slurm-smd001-fixed/smd006_time_limit_driver.sh
```

表示された全出力、job ID、`run_dir`を保存する。完了後に`sacct`、queue、node、
記録PIDを独立照合する。

## 成功条件

1. time limit前にbatch shellとchild processが存在する。
2. driverが通常経路で`scancel`せず、jobが約1分でqueueから消える。
3. `sacct`のjob stateが`TIMEOUT`になる。
4. stepの終了code/signalとworkloadのTERM観測が矛盾しない。
5. timeout後に記録したPIDが消え、関連`slurmstepd`が残らない。
6. PC-210が`IDLE CPUAlloc=0`へ戻り、次jobを受け付けられる。

stateが`CANCELLED`/`FAILED`となる、time limitを大きく超過する、PIDが残る、nodeが
DRAINになる場合はSMD-007へ進まず、SMD-006をFAILとして原因を調査する。

## 実測結果

2026-09-09 17:35～17:36 JSTにJob 35を実行した。

| 確認対象 | 観測結果 |
|---|---|
| 起動前提 | batch PID=72278、child PID=72280、PGID=72278 |
| workload開始 | epoch=1788942931 |
| TERM受信 | epoch=1788943000。開始から69秒後 |
| driver待機 | `wait_seconds=64 wall_seconds=69` |
| job accounting | Job 35=`TIMEOUT`、`Timelimit=00:01:00`、`Elapsed=00:01:10` |
| step accounting | `35.batch=FAILED ExitCode=124:0`。TERM trapのexit 124と一致 |
| process cleanup | PID 72278/72280はtimeout後に不在。関連process残留なし |
| resource cleanup | queueにJob 35なし。PC-210=`IDLE CPUAlloc=0 AllocTRES=(empty)` |

time limit到達時のSIGTERMはworkloadへ配送され、trapがexit 124を返した。一方、job
全体はcontrollerにより`TIMEOUT`と記録された。1分制限に対する約10秒の差は今回の
controllerによる終了判定・配送までを含む観測値であり、複数試行による分布測定は
まだ行っていない。

6つの成功条件をすべて満たしたため、SMD-006を`PASS_STAGING`と判定する。
