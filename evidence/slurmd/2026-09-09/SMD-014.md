# SMD-014 launchd常駐化 — 初回試験と修正

## 判定

- 日時: 2026-09-09（SMD-013完了後）
- 状態: `PASS`
- worker: PC-210 / macOS / arm64 / slurmd 26.11.0-0rc1
- controller: ubuntu2504 / Ubuntu 24.04 / x86-64 / systemd slurmctld
- 対象: macOS workerの`slurmd`だけ。controller daemonは対象外

## Research Question

修正版slurmdをsystem domainのlaunchd serviceとして管理し、boot時起動、正常stop/start、
異常終了後の自動再起動、controller再登録、log、PID、後続job実行を一貫して行えるか。

### Ubuntu側read-only確認 — 原因確定

Ubuntu controllerで名前解決と6818/TCP到達性を比較した結果、`PC-210`は再起動前の
`192.168.10.127`へ解決され、接続はtimeoutした。一方、再起動後のworker address
`192.168.10.128`にはpingと6818/TCPの両方で到達できた。

```text
getent PC-210=192.168.10.127
nc PC-210:6818=TIMEOUT
ping 192.168.10.128=PASS
nc 192.168.10.128:6818=PASS
```

これにより、再起動後の停止原因はmacOS Application Firewallではなく、DHCP address変更後も
Ubuntu側の`PC-210`名前解決が旧IPを指していたことで確定した。SMD-014を完了させる次の一手は、
まずcontrollerのruntime `NodeAddr`だけを`.128`へ更新して再登録とpost-reboot jobを確認すること
である。恒久対策は、worker IPをDHCP reservation等で固定したうえで、名前サービスまたは正本
`slurm.conf`の`NodeAddr`をcontroller/workerで一貫させる。現在IPだけを恒久設定して再びDHCPで
変化させる構成は採用しない。

```bash
# ubuntu2504: SMD-014を継続するためのruntime-only更新
sudo /usr/local/slurm/26.11.0/bin/scontrol update \
  NodeName=PC-210 NodeAddr=192.168.10.128 State=RESUME
```

runtime更新の実測では`NodeAddr=192.168.10.128`、`State=IDLE`となり、`NOT_RESPONDING`が
消えた。`BootTime=2026-09-10T00:08:18`もcontrollerへ登録され、`CPUAlloc=0`、
`AllocTRES`空である。これにより原因とruntime修正効果は確認済みとなった。

```text

controller_to_slurmd_response=RESTORED
NodeAddr=192.168.10.128
State=IDLE
BootTime=2026-09-10T00:08:18
post_reboot_smoke_job=READY_TO_RUN
```
