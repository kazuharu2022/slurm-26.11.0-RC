# SMD-012 local config reconfigure — 試験計画

## 判定

- 日時: 2026-09-09 20:10 JST–
- 状態: `PASS_STAGING`
- worker: PC-210 / macOS / arm64 / slurmd 26.11.0-0rc1
- controller: ubuntu2504 / Ubuntu 24.04 / x86-64 / systemd slurmctld

## Research Question

`-f /opt/slurm/26.11.0/etc/slurm.conf`でlocal configを指定してforeground起動している
macOS版slurmdは、`scontrol reconfigure`を受信したとき、PIDを変えずにlocal configを
再読込し、再登録と後続job実行を正常に行えるか。

## source確認と試験値の選択

`src/slurmd/slurmd/req.c::_rpc_reconfig()`はreconfigure RPCを受けてslurmd自身へSIGHUPを
送る。`src/slurmd/slurmd/slurmd.c::_try_to_reconfig()`は、非daemon・非systemdの場合に
現在のbinaryとargvを`execve()`する。現在のargvには`-f`が残るためlocal configが再読込
され、同一processへのexecなのでPIDは維持される想定である。

現在のslurmdは`-Dvvv`で起動しているため、configの`SlurmdDebug=info`を変更してもcommand
lineのdebug levelが優先される。このため、観測可能で安全な試験値として`SlurmdLogFile`を
一時的にrun directory内のlogへ変更する。

## 実験方式

1. cluster全体にactive jobがないこととPC-210=`IDLE`を確認する。
2. production `slurm.conf`をbyte-for-byte backupし、SHA-256を保存する。
3. `SlurmdLogFile`だけを`/tmp/slurm-smd012-*/slurmd-alternate.log`へ変更する。
4. candidate configを`slurmd -C -f`でparse確認する。
5. `scontrol reconfigure`を実行し、alternate log作成、再登録時刻更新、PID維持を確認する。
6. production configを復元して再度reconfigureし、元logへの復帰とconfig完全一致を確認する。
7. GRES要求付きhostname jobを実行し、会計・queue・resourceを確認する。

`scontrol reconfigure`はcontrollerと他workerにも配信され得るため、active jobが1件でもあれば
状態変更前にexit 75で停止する。

  SHA-256、slurmd PID、controller statusを確認し、SMD-013へ進まない。
- `/var/log/slurm/slurmd.log`自体は削除・truncateしない。

## SACK socket消失の原因

追加のslurmd logでは、20:13:15の新processに`fatal`、`Protocol not available`、
`conmgr rejected socket`はない。代わりに次の順序が記録されている。

1. 新slurmdが`auth/slurm`を初期化してkeyをloadする。
2. 新slurmdが`killing old slurmd[85145]`を出す。
3. 旧slurmdがSIGTERMを受け、shutdownする。
4. 新slurmdがcontrollerから8 TRESを受信して登録を完了する。

sourceでは`_slurmd_init()`内の`auth_g_init()`がmain loop側の
`_wait_on_old_slurmd(true)`より先に実行される。auth/slurmの
`init_sack_conmgr()`は`_prepare_run_dir()`で既存の`sack.socket`をunlinkし、同じpathへ
新socketをbindする。その後に終了する旧processのconmgrは、listener close時にpathの
所有者を確認せず同じpathをunlinkしていた。

したがって今回の時系列は次の競合と一致する。

```text
new: unlink(old path) -> bind(new socket) -> kill(old slurmd)
old: shutdown -> close_con() -> unlink(same path, now owned by new)
```

これにより、新slurmd PID 95911とcontroller登録は維持される一方、client認証に必要な
`/var/run/slurm/sack.socket`だけが消えた。F/W、controller TCP、key load失敗ではない。

## source修正とbuild確認

`src/conmgr/con.c`と内部connection構造体`src/conmgr/mgr.h`を修正した。

- named UNIX listenerの登録時に、socket pathを`lstat()`してfilesystemのdevice/inodeを保存する。
- listener終了時は現在のpathを再度`lstat()`し、保存値と一致する場合だけunlinkする。

## 約187秒停止の原因分析 — `FIX_BUILT_AWAITING_RETEST`

Mac側の追加logにより、次の2経路でほぼ同じ遅延を確認した。

| 経路 | 開始 | 次に進んだ時刻 | 実測遅延 |
|---|---|---|---:|
| slurmd reconfigure | 20:47:53.407 | 20:51:00.082 | 186.675秒 |
| Job 54 slurmstepd起動 | 20:51:04.094 | 20:54:11.060 | 186.966秒 |

reconfigureは`_try_to_reconfig()`の`execve()`直前に`closeall_except()`を呼ぶ。slurmstepd起動は
`_forkexec_slurmstepd()`の`execvp()`直前に`closeall()`を呼ぶ。macOSには`close_range()`がなく、
両方とも`src/common/fd.c`のdescriptor番号を上限まで1件ずつ`close()`するfallbackを通る。

soft `RLIMIT_NOFILE=unlimited`では、macOSの`sysconf(_SC_OPEN_MAX)`は
`9223372036854775807`を返す。元コードはこの値を`int`へ変換し、結果を`INT_MAX`として扱うため、
約21億回の`close()`を実行する。1,048,572回の単独probeは0.093918秒であり、同じ速度で
`INT_MAX-3`回を実行する推定値は192.345秒だった。実機の2回の約187秒と整合する。

Job 54のJWTは20:52:04に期限切れとなり、slurmstepdが20:54:11に初めてrequestを読んだため、
`decode_jwt: token expired`、`Malformed RPC`、slurmstepd fatalとなった。JWT実装やF/Wが一次原因
なのではなく、exec前のFD close loopによる二次的な期限切れである。

PID 4170が失敗時に継承していたlimitそのものは事前採取できていないため、修正版で遅延が消える
ことを最終的な因果確認gateとする。

### source修正

`src/common/fd.c`を修正し、macOSでlimitがinfinityまたは`int`に収まらない場合は、起動時に
`sysctlbyname("kern.maxfilesperproc")`を読み、実際のkernel per-process上限をfallback走査上限に
使う。現在値は245,760である。post-forkではなく`closeall_init()`中に取得する。

明示的にsoft limitをunlimitedへ設定した修正版probeは245,757回を0.037036秒で終了した。
`fd.lo`、`libcommon.la`、`slurmd`、`slurmstepd`のbuildは成功した。production installとdaemon
置換は未実施である。

再試験driverも、candidateを`ulimit -n unlimited`で起動し、smoke batch jobと両reconfigureを
各30秒以内とする回帰条件へ更新した。
