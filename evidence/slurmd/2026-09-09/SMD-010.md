# SMD-010 controller通信断 — 実測結果

## 判定

- 日時: 2026-09-09（SMD-009完了後）
- 状態: `PASS`
- 対象: idle時およびjob終了通知時のPC-210からcontroller TCP/6817への一時通信断
- preflightと本試験を完了

## Research Question

macOS compute nodeからSlurm controllerのTCP/6817だけが一時的に到達不能になった際、
slurmd/slurmstepdが停止・abortせず、既存job processを追跡し続け、通信復旧後に終了通知、
node登録、resource解放、新規job受付が収束するか。

## 仮説

6817通信断中はregistrationまたはjob完了通知の再送errorが記録されるが、daemonとjob
processは維持される。遮断解除後は保留された通知がcontrollerへ届き、nodeはIDLE、
allocationは空となり、新規jobを受け付ける。

## なぜpreflightを先に行うか

macOS PFの操作にはroot権限が必要で、現在のPF有効状態とenable referenceは一般user
から読めない。既存rulesetを壊したり、試験後にPF全体を誤って無効化したりしないため、
最初に次を読取専用で保存する。

1. controller `192.168.10.180:6817`へのrouteとinterface。
2. PFの有効状態とenable reference token。
3. main rulesetの`com.apple/*` anchor参照と既存anchor/rule。
4. SMD-010用anchor名`com.apple/slurm-smd010`が未使用であること。
5. nodeがIDLEかつactive jobなしで、6817へ接続できること。

## 本試験driverへ課す安全条件

- main rulesetをflush/reloadしない。
- `com.apple/slurm-smd010`専用anchorだけを使用する。
- 宛先`192.168.10.180`、TCP port 6817、確認済みinterfaceだけをblockする。
- PFが無効なら`pfctl -E`のreference tokenを保持し、cleanupで同じtokenを`-X`する。
- PFが既に有効でも全体を`-d`しない。
- EXIT/HUP/INT/TERM trapで専用anchorを空にし、接続回復を確認する。
- active jobがある場合は遮断前に停止する。
- 対象job ID/PID以外をsignalしない。

## 未確認事項

- root権限でのPF状態、enable reference、既存anchorはpreflightで取得済み。
- 5分の`SlurmdTimeout`を超える長時間断と、controllerがnodeをDOWNにした後の回復は未確認。
- inbound TCP/6818、DNS、経路全体の切断は今回の対象外。
- 単一job・単一nodeで1回の検証であり、複数job中の断線は未確認。


成功するまでPFを有効化しない。

## 本試験の固定条件

```text
interface=en0
source=192.168.10.127
destination=192.168.10.180
protocol=tcp
destination-port=6817
anchor=com.apple/slurm-smd010
```

実際にloadするruleは次の1行だけである。

```pf
block drop out quick on en0 inet proto tcp from 192.168.10.127 to 192.168.10.180 port 6817 label "SMD010-controller-6817"
```

## 本試験の流れ

1. route、node IDLE、active jobなし、slurmd PID、PF Disabled/referenceなしを再確認する。
2. ruleを`pfctl -n`で検査する。
3. `pfctl -E`でPFを有効化し、返されたreference tokenを保存する。
4. idle phaseで専用anchorへruleをloadし、6817が失敗することとslurmd PID維持を確認する。
5. anchorだけをclearし、6817接続とnode IDLEを確認する。
6. 8秒のexclusive Jobを投入し、RUNNINGと親子PIDを保存する。
7. job phaseのruleをloadし、6817遮断中にworkloadを完了させ、さらに5秒待つ。
8. slurmd PID維持とPF counterを保存後、anchorをclearする。
9. controller側jobが`COMPLETED 0:0`へ収束し、親子PIDが消えることを確認する。
10. GRES付きhostname smoke jobを実行する。
11. node IDLE、allocation空を確認し、専用anchorを空にする。
12. 保存したtokenだけを`pfctl -X`で解放し、PF Disabled/referenceなしへ戻す。

## 成功条件

- idle/job両phaseで6817への新規接続が失敗し、解除後に成功する。
- 両phaseを通してslurmd PIDとPID fileが変化しない。
- job payloadが遮断中に正常終了し、復旧後にjob/step=`COMPLETED 0:0`へ収束する。
- job process、queue、CPU/memory allocationが残らない。
- 復旧後のGRES付きhostname jobが`COMPLETED 0:0`となる。
- 専用anchorにruleが残らない。
- PFが試験前と同じDisabled/referenceなしへ戻る。
- 最終行に`SMD010_ROOT_RUN_COMPLETE`が表示される。

## 実測結果 — PASS

- run directory: `/tmp/slurm-smd010-20260909T193353`
- slurmd PID: 85145（試験前後で不変）
- target: Job 48
- post-recovery smoke: Job 49
- PF token: `1956188963478615880`

| 確認点 | 観測結果 |
|---|---|
| baseline 6817 | 接続成功 |
| idle phase | 6817 timeout、slurmd PID維持、解除後接続成功、node IDLE |
| job phase開始時PF | 11 packets / 688 bytes |
| job phase終了直前PF | 31 packets / 1968 bytes |
| Job 48 payload | 遮断中に8秒workloadをrc=0で完了 |
| Job 48 Slurm通信 | 6817接続が2回timeout後、解除直後にSACK接続・終了処理 |
| Job 48 accounting | job/batchとも`COMPLETED / 0:0` |
| Job 49 | job/batchとも`COMPLETED / 0:0`、`PC-210.local` |
| 最終node | `IDLE`、`CPUAlloc=0`、`AllocTRES`空 |
| 最終process | Job 48/49の残留なし |
| PF復元 | 専用anchor空、token解放、`Disabled`、referenceなし |

PF counterはjob phaseの接続確認直後から終了直前までに20 packets、1280 bytes増えた。
同じ時間帯のslurmstepdログには次の実測が残った。

```text
task 0 (89630) exited with exit code 0.
JobId=48 ... completed with slurm_rc = 0, job_rc = 0
connect to 192.168.10.180:6817 in 2s: Operation timed out
Error connecting slurm stream socket at 192.168.10.180:6817: Operation timed out
connect to 192.168.10.180:6817 in 2s: Operation timed out
_sack_connect: connected to /var/run/slurm/sack.socket
done with step
```

したがって、単に`nc`だけが遮断されたのではなく、Job 48の終了通知経路でも実際に
6817 timeoutが発生した。その間もpayloadはrc=0で終了し、slurmdは同一PIDを維持した。
rule解除後、Job 48は15秒経過としてcontroller/SlurmDBDへ`COMPLETED 0:0`で収束した。

## 確認できた事実・考察・限界

### 確認できた事実

- TCP/6817限定の短時間通信断でslurmdは停止・再起動しなかった。
- idle時はnode IDLEを維持し、解除後にcontrollerへ再接続できた。
- job終了通知がtimeoutしてもslurmstepdは直ちにabortせず、通信復旧後に終了処理を完了した。
- job、step、process、CPU/memory allocationはすべて回収された。
- PF設定は試験前と同じ無効状態へ戻った。

### 考察

今回の修正版では、短時間のcontroller TCP/6817断に対して、local task完了とcontroller
通知が分離され、後者が再接続後に収束した。これは通信断中のjob processが未追跡で
残ったり、slurmd自体が通信errorで終了したりする挙動ではない。ただし5分以上の断線、
controller側node DOWN遷移、6818を含む完全分断まで同じ結果になるとは断定できない。
