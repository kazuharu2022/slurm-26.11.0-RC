# SMD-013 spool/SACK recovery — 試験計画

## 判定

- 日時: 2026-09-09（SMD-012完了後）
- 状態: `PASS_STAGING`
- worker: PC-210 / macOS / arm64 / slurmd 26.11.0-0rc1
- controller: ubuntu2504 / Ubuntu 24.04 / x86-64 / systemd slurmctld
- production `/opt/slurm/26.11.0`: source fix未導入
- test対象: `/tmp`へstagingする修正版candidate

## Research Question

macOS版slurmdは、production spoolを壊さずに隔離した`SlurmdSpoolDir`で、破損した
`cred_state`、vestigial job directory、stale SACK pathnameを安全に処理し、通常jobを実行した後、
production spoolへ復帰できるか。

## source確認

- `cred_state_init()`は`-c`なしの起動で`SlurmdSpoolDir/cred_state`を読み込む。
- `_cred_context_unpack()`は破損データを復元できない場合にwarningを記録し、初期化処理は空の
  credential listを作成して継続する。
- `save_cred_state()`は`cred_state.new`へ書いた後、linkによって`cred_state`を更新する。
- `slurmd -c`はcredential stateを復元せず、stepd socketと`job[0-9]*` directory内の
  `slurm_script`をcleanupする。
- `auth/slurm`の`_prepare_run_dir()`はbind前に既存の`/var/run/slurm/sack.socket`をunlinkする。

## read-only preflight

production spoolは`/var/spool/slurmd`で、現在は62-byteの`cred_state`だけが存在する。
production spool、production `cred_state`へ破損データは書き込まない。

現在のPID 19107はstaging candidate、SACKはdevice/inode=`16777233:13043942`、controllerはUP、
PC-210は`IDLE`、`CPUAlloc=0`、`AllocTRES=`、queueは空である。この状態は実行直前にdriverでも
再検査する。

Evidence: `SMD-013-files/preflight1.txt`

## 実験設計

driverは修正版slurmdと`libslurmfull.dylib`をrun directoryへ固定し、production configから
`SlurmdSpoolDir`だけを`/tmp/slurm-smd013-*/spool`へ変更した隔離configを作る。production config
自体は編集しない。

### Phase A: corrupt credential state

1. 隔離spoolへ意図的に不正な`cred_state`と`job99999/slurm_script`を作成する。
2. 現slurmdをTERMでclean stopする。
3. stale SACK pathnameとしてregular fileを配置する。clean stop後にpathnameが残っていれば、
   その既存entryをstale entryとして使う。
4. `-c`なしで隔離configのcandidateを起動する。
5. SACKがsocketとして再作成され、破損stateのwarningを出しつつnodeがIDLEになることを確認する。
6. GRES要求付きhostname jobが`COMPLETED 0:0`になることを確認する。
7. clean stop後、`cred_state`が正常形式で再保存されたことをmetadataで記録する。

### Phase B: clean start cleanup

1. 再度stale SACK pathnameを用意する。
2. `slurmd -c`で隔離configのcandidateを起動する。
3. `job99999/slurm_script`とdirectoryが削除され、purge logが出ることを確認する。
4. GRES要求付きhostname jobが`COMPLETED 0:0`になることを確認する。

### production spoolへの復帰

1. Phase B daemonをclean stopする。
2. 同じ修正版candidateをproduction configで起動する。
3. SACK、controller登録、node IDLEを確認する。
4. 最終GRES jobを実行し、accounting、queue、resource回収を確認する。

失敗時は、稼働中のtest daemonをPID確認後にclean stopし、同じ修正版candidateをproduction configで
再起動する。production configとproduction spoolはtest dataで上書きしない。

## 成功条件

1. production spoolとproduction configへtest用破損内容を書かない。
2. Phase Aで破損`cred_state`の復元warningを記録し、slurmdはfatal終了しない。
3. 両Phaseでstale SACK entryをsocketへ置換し、client認証が成功する。
4. Phase Bでvestigial `job99999` directoryを削除する。
5. Phase A、Phase B、production復帰後の3 jobがjob/batchとも`COMPLETED 0:0`になる。
6. 最終daemonがproduction config・production spoolで稼働する。
7. node=`IDLE`、`CPUAlloc=0`、`AllocTRES=`、queue・process残留なしとなる。
8. 最終行に`SMD013_ROOT_RUN_COMPLETE`が表示される。

## 既知の影響と停止条件

- PC-210のslurmdを3回clean stop/startするため、その間はnodeが一時的に応答不能になる。
- local config hash warningは、隔離spool使用中の想定差分としてartifactへ残す。
- active jobまたは非IDLEを検出した場合はdaemon停止前にexit 75とする。
- 復旧処理がproduction configでdaemonを起動できなければ、再実行せずrun directoryとcontroller
  状態を採取して停止する。
- 成功後も稼働binaryは`/tmp`のcandidateである。production installは別工程とする。

## 未確認事項

- 実行中jobを含むspool復元はSMD-009で別途観測しており、本試験では破損stateとclean startに限定する。
- filesystem full、permission denied、I/O errorはSMD-113で扱う。
- production install後、launchd経由、Mac再起動後の復元は未確認である。

## 初回試験 — `BLOCKED`

controller側でqueueが空、PC-210が`IDLE`であることを確認後、driverを実行した。現slurmd
PID 19107はclean stopし、stale SACK fixtureとしてregular fileを作成した。Phase A candidate
PID 23141はnode readyにならず、driverの復旧処理がproduction configのcandidate PID 23395を
起動した。

Phase A logのfatalは次のとおりである。

```text
fatal: auth/slurm: cannot stat '/tmp/slurm-smd013-20260909T221055/slurm.key':
No such file or directory
```

Slurmの`get_extra_conf_path()`はmain configのdirectoryを補助設定の探索基準にする。隔離configを
`/tmp/slurm-smd013-*/slurm.conf.isolated-spool`へ配置したため、`auth/slurm`も同じdirectoryの
`slurm.key`を探した。driverはproduction keyの明示パスを渡していなかった。また、Phase Aが
auth初期化を越えた場合でも、同じ理由でproduction `gres.conf`が見えずGPU GRESが欠落する可能性が
あった。

この試験はauth初期化で停止したため、破損`cred_state`の復元、vestigial job directoryの削除、
job実行は未到達であり、結果を失敗または成功とは判定しない。production configとproduction spool
にはtest fixtureを書いていない。

復旧後の独立確認では、PID 23395がproduction configで稼働し、SACKはregular fileからsocket
（device/inode=`16777233:13046739`）へ再作成された。controllerはUP、PC-210は`IDLE`、
`CPUAlloc=0`、`AllocTRES=`、queueは空である。復旧後jobはこのrunでは投入していない。

## 原因修正

driverを次のように補正した。

1. candidate起動時に`SLURM_SACK_KEY=/opt/slurm/26.11.0/etc/slurm.key`を明示する。
2. secretをcopyせず、run directoryへproduction `gres.conf`だけをsymlinkする。
3. production keyとGRES sidecarの存在をdaemon停止前に検査する。
4. candidateが終了した場合は60秒待たず、2秒後に失敗を検知して復旧へ移る。
5. 復旧時にPID fileが別daemonを指した場合は、そのprocessを停止せずduplicate startもしない。

補正版は`/bin/sh -n`を通過し、非root実行は状態変更前にexit 77となった。SHA-256は
`bb9ca555561286c5a461ab6ff3ae2438cec6acc9e7f427ca10c624e4771ecef2`である。

Evidence: `SMD-013-files/run1-blocked.txt`

## 第2回試験 — `PASS_STAGING`

補正版driverを実行し、Phase A、Phase B、production復帰の全工程が完走した。

```text
run_dir=/tmp/slurm-smd013-20260909T222246
phase_a=PASS pid=24985 job_id=57
phase_b=PASS pid=25054 job_id=58
production_restore=PASS pid=25124 job_id=59
SMD013_ROOT_RUN_COMPLETE current_pid=25124 phase_a_job=57 phase_b_job=58 final_job=59
```

Phase Aではregular fileとして置いたstale SACK entry（inode 13047728）を置換して起動し、
意図的に破損させたcredential stateに対して次のwarningを記録した。fatal終了せず、隔離spoolの
`cred_state`を62 byte、mode `0600`の正常stateとして再保存した。

```text
[2026-09-09T22:22:48.086] warning: _cred_context_unpack: failed to restore job state from file
```

Phase Bでは再度regular fileとして置いたstale SACK entry（inode 13047817）を置換し、`-c`起動で
次のcleanup logを記録した。実行後、隔離spoolの`job99999/slurm_script`と`job99999` directoryは
存在しない。

```text
[2026-09-09T22:22:53.682] _stepd_cleanup_batch_dirs: Purging vestigial job script /tmp/slurm-smd013-20260909T222246/spool/job99999/slurm_script
```

各phaseで`--gres=gpu:apple:1`を明示したJobs 57～59を投入した。3 jobと各batch stepはすべて
`COMPLETED 0:0`、stdoutは`PC-210.local`、stderrは空だった。各phaseのnode情報でも
`Gres=gpu:apple:1`と`State=IDLE`を確認した。ただし、このclusterのaccounting出力では
`ReqTRES`/`AllocTRES`にGPUが表示されないため、GPU TRESのaccounting記録自体は本試験の証拠に
含めない。

最終daemon PID 25124はproduction config `/opt/slurm/26.11.0/etc/slurm.conf`とproduction spool
`/var/spool/slurmd`を使って稼働している。最終SACKはsocket（inode 13047845）、controllerはUP、
nodeは`IDLE`、`CPUAlloc=0`、`AllocTRES=`、queueは空である。独立した事後確認でもJobs 57～59と
各batch stepは全て`COMPLETED 0:0`であり、対応する`slurmstepd`、job directory、job scriptの
processは検出されなかった。

以上から、破損credential stateからの安全な初期化、stale SACK pathnameの置換、`-c`による
vestigial job directory削除、production spoolへの復帰は、staging candidateで成功条件を満たした。
SMD-013を`PASS_STAGING`と判定する。

現在稼働中なのはrun directory内の修正版candidateであり、production prefixへのinstall、launchd、
Mac再起動後の復元は未確認である。

Evidence: `SMD-013-files/run2-pass.txt`
