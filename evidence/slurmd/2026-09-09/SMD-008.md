# SMD-008 idle時のslurmd restart — 試験計画

## 判定

- 日時: 2026-09-09 18:18 JST–
- 状態: `PASS`
- 前提: SMD-001～SMD-007はstaging構成で`PASS_STAGING`
- 対象: idle状態のslurmdを正常停止・再起動した後のcontroller再登録とjob実行

## Research Question

macOS上で手動管理している`slurmd`をidle時にTERMで正常停止し、同じinstalled binary
とconfigで再起動したとき、PID fileとSACKを再構築してcontrollerへ自動再登録し、
新しいGPU GRES付きjobを正常実行・回収できるか。

## 現在の前提

read-only事前確認では次を観測した。

- `/var/run/slurmd.pid`のPID 7462がrootで稼働中。
- commandは`/opt/slurm/26.11.0/sbin/slurmd -Dvvv -f /opt/slurm/26.11.0/etc/slurm.conf`。
- Jobs 42～44終了後、PC-210は`IDLE CPUAlloc=0 AllocTRES=(empty)`。
- `system/org.schedmd.slurmd`はlaunchdへ登録されておらず、
  `/Library/LaunchDaemons/org.schedmd.slurmd.plist`も存在しない。

したがってSMD-008はlaunchd service試験ではなく、現在と同じ手動管理方式のdaemon
restart試験とする。launchd常駐化はSMD-014で別に検証する。リポジトリに残る
`etc/launchd/`の雛形はprefixが`/opt/slurm/26.05`、NodeNameが`pc210`であり、
現行環境には使用しない。

## 試験artifact

```text

sha256=ca0d0a579cba20e5d6c59b342682742c799099ddb7f91942d972b2d5f536e040
```

`/bin/sh -n`はexit 0。scriptが参照するinstalled binary、config、macOS標準command、
testuserの存在をread-onlyで確認済み。

## 実行内容

scriptはroot権限で次を逐次実行する。

1. PC-210にactive jobがなく、nodeがIDLEであることを確認する。
2. PID fileとprocess commandを照合して停止対象を一意にする。
3. 対象PIDへTERMを送り、最大30秒で終了することを確認する。
4. 同じinstalled binary/configを`nohup`付きforeground modeで再起動する。
5. processとPID fileが新PIDへ収束し、最大60秒でnodeがIDLEとなり、
   `SlurmdStartTime`が旧値から更新されることを確認する。
6. testuserで1 CPU、1 GiB、`gpu:apple:1`のhostname batch jobを投入する。
7. stdout、accounting、queue、node allocation、slurmd processとlogを保存する。

途中で失敗してslurmd processが存在しない場合は、EXIT trapが同じcommandで1回だけ
復旧起動を試す。新しい起動候補が生存している場合は二重起動しない。作成したsmoke
jobがqueueに残っている場合は、その正確なjob IDだけをcancelする。

## 実行方法

この操作は現在のslurmdを一度停止する。Macの管理者sessionで実行する。

```bash
sudo /bin/sh \
  /Users/REDACTED_USER/dev/slurm.26-05/contribs/macos-tests/smd008_idle_restart.sh
```

## 成功条件

1. 実行開始時にactive jobがなく、PC-210がIDLEである。
2. 旧PIDがTERMから30秒以内に終了する。
3. 新しいPIDのslurmdが稼働し、PID fileと一致する。
4. controller上のPC-210が60秒以内にIDLEへ戻り、`SlurmdStartTime`が更新される。
5. restart後のhostname jobが`COMPLETED 0:0`で、PC-210のhostnameを出力する。
6. job終了後にqueueが空、`CPUAlloc=0`、`AllocTRES=(empty)`となる。
7. SACK、registration、plugin、credentialに新しいfatal errorがない。
8. 最終行に`SMD008_ROOT_RUN_COMPLETE`が表示される。

失敗時はSMD-009へ進まず、表示された`run_dir`、`slurmd-foreground.log`、
`slurmd-recovery.log`の有無、`/var/log/slurm/slurmd.log`を確認する。

## 原因と修正

rootでdriverを起動したため、`sudo -H -u testuser`はrootのcurrent working directoryを
そのまま継承した。`-H`が変更するのはHOMEでありcwdではない。rootのcwdをtestuserが
参照できず、`sbatch`はoption処理の初期化中に`getcwd()`で`EACCES`となった。

source上でも`src/common/slurm_opt.c`の`arg_reset_chdir()`は、`--chdir`の設定処理とは
別に初期cwdを`getcwd()`で取得し、失敗すると終了する。したがって
`--chdir=/tmp`だけでは、この初期化時の失敗を回避できない。

smoke job投入のcommand substitution内で先に`cd /tmp`し、その後にtestuserへ切り替えて
`sbatch`を実行するようdriverを修正した。これによりtestuserが参照可能なcwdから
option初期化を開始できる。Slurm source、binary、config、新slurmd PID 79927には変更を
加えていない。

修正後のscriptは`/bin/sh -n`を通過した。再試験でhostname job、accounting、resource
cleanup、最終markerまで確認するまでは`FIX_BUILT_AWAITING_RETEST`とする。

## 2回目試験 — PASS

2026-09-09 18:41 JSTに修正済みdriverを実行した。旧PID 79927はTERMで正常終了し、
新PID 82165で同じinstalled binary/configが起動した。controller上の
`SlurmdStartTime`は18:24:36から18:41:50へ更新され、PC-210はIDLEへ自動再登録された。

| 確認項目 | 観測結果 | 判定 |
|---|---|---|
| process/PID file | root PID 82165、driver終了後はPPID 1、PID fileも82165 | PASS |
| GRES再読込 | `gpu:apple:1 Count=1` | PASS |
| controller登録 | 8 TRES受信、`State=IDLE` | PASS |
| smoke job | Job 45、testuser、hostname=`PC-210.local` | PASS |
| accounting | jobとbatch stepが`COMPLETED 0:0` | PASS |
| cleanup | queue空、`CPUAlloc=0`、`AllocTRES=` | PASS |
| SACK | Job 45終了時にlocal SACK socketへ接続 | PASS |

起動時には既知の`_core_spec_init: not supported on macOS`とhttp_parser未導入の非fatal
errorが再度記録されたが、daemon起動、登録、Job 45の実行・終了を阻害していない。
今回新しく発生したfatal errorはない。

最終行の`SMD008_ROOT_RUN_COMPLETE`まで完走し、独立照合でも同じ状態を確認した。
installed binary `/opt/slurm/26.11.0/sbin/slurmd`とproduction configを使用したため、
SMD-008は`PASS_STAGING`ではなく`PASS`と判定する。
