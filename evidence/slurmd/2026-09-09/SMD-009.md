# SMD-009 job中のslurmd異常終了 — 実測結果

## 判定

- 日時: 2026-09-09 18:56–19:03 JST
- 状態: `PASS`
- 前提: SMD-001～SMD-007は`PASS_STAGING`、SMD-008はproduction構成で`PASS`
- 対象: job実行中にslurmdだけをSIGKILLし、再起動時のjob/process/spool/SACK/GRESを確認

## Research Question

macOS compute nodeでexclusive jobの実行中に`slurmd`が異常終了した場合、既存の
`slurmstepd`とjob processはどの状態になり、同じinstalled binary/configでslurmdを
再起動した後にjobを一貫した状態へ回収し、新規jobを再び実行できるか。

## 仮説と反証条件

仮説は、slurmd再起動後も既存jobがcontroller上で追跡され、継続または明示的な
terminal stateへ遷移し、cancel後に全processとallocationを回収できることである。

次のいずれかがあれば反証とする。

- slurmdが再起動・再登録できない。
- controllerから消えたjob processがMac上に残る。
- cancel後もbatch/child PID、GRES、CPU allocationが残る。
- spool/PID file/SACKの破損により新しいjobを実行できない。
- 対象外jobやprocessを停止する。

再起動直後のtest jobが`RUNNING`を維持するか、別のterminal stateになるかは事前に
成功条件へ固定しない。観測結果とaccountingを保存して判定する。

## 隔離と安全策

- 開始時にPC-210上のactive jobが1件でもあれば、SIGKILL前にexit 75で停止する。
- test jobは`--exclusive`でnodeを占有し、試験中に他jobが同居しないようにする。
- test jobは3分で自然終了する`sleep`だけを実行する。
- driverはPID fileと実commandを照合し、確認したslurmd PIDだけへSIGKILLする。
- jobはbatch/child PIDをmarkerへ保存する。
- 再起動後5秒間の状態を観測した後、queueに残る対象job IDだけをcancelする。
- cancel後30秒残った場合はprocess情報を保存し、記録済みbatch/child PIDだけを
  TERM、必要時はKILLして残留を回収する。
- 途中失敗でslurmdが不在なら同じcommandで1回だけ復旧起動する。既存processが
  生きている場合は二重起動しない。

## 実行内容

1. nodeがIDLEでactive jobがないことを確認する。
2. testuserで3分上限のexclusive jobを投入し、batch/child PIDを保存する。
3. 実行中のslurmdへSIGKILLを送る。
4. 同じ`/opt/slurm/26.11.0` binary/configでslurmdを再起動する。
5. PID fileと`SlurmdStartTime`更新を確認する。
6. test jobのrestart直後と5秒後のstate、batch/child processを保存する。
7. 対象jobをcancelし、terminal accountingとprocess cleanupを確認する。
8. GPU GRES付きhostname jobを新たに投入し、`COMPLETED 0:0`を確認する。
9. queue、node allocation、slurmd process、SACK、logを保存する。

## 実行方法

この試験はjob実行中のslurmdへ意図的にSIGKILLを送る。Macの管理者sessionで、
他利用者がPC-210を使用していないことを確認して実行する。

```bash
sudo /bin/sh \
  /Users/REDACTED_USER/dev/slurm.26-05/contribs/macos-tests/smd009_abnormal_restart.sh
```

## 成功条件

1. exclusive test jobだけがRUNNINGとなり、親子PIDを記録できる。
2. 旧slurmdがSIGKILL後に消え、新PIDとPID fileが一致する。
3. controllerの`SlurmdStartTime`が更新される。
4. test jobの再起動前後state、accounting、process状態を説明できる。
5. cancelまたはterminal遷移後にbatch/child processが残らない。
6. post-restart hostname jobが`COMPLETED 0:0`となる。
7. 最終的にPC-210がIDLE、`CPUAlloc=0`、`AllocTRES=(empty)`となる。
8. slurmd processとPID fileが一致し、SACK経由でjob終了処理が完了する。
9. 最終行に`SMD009_ROOT_RUN_COMPLETE`が表示される。

## 停止条件

driverがerrorを出した場合はSMD-010へ進まない。出力された`run_dir`、controller側の
該当job/node state、`/var/log/slurm/slurmd.log`を保存し、残留processとslurmd復旧を
確認してから原因を修正する。

## 未確認事項

- launchdによる自動復旧ではなく、driverによる明示的な再起動を試した。
- 異常終了後にjobを自然終了させる経路と、複数jobが実行中の回復は未確認。
- controller通信断、controller再起動、Mac本体のsleep/wakeは別試験である。

## 実測結果 — PASS

実行ディレクトリは`/tmp/slurm-smd009-20260909T190245`、対象はJob 46、再起動後の
smoke testはJob 47である。旧slurmd PID 82165へSIGKILLを送り、新PID 85145で
同じinstalled binary/configを起動した。

| 確認点 | 実測 |
|---|---|
| job起動 | Job 46、batch PID 85131、child PID 85132 |
| slurmd再起動 | PID `82165 -> 85145` |
| controller上の開始時刻 | `18:41:50 -> 19:02:46` |
| 再起動直後のJob 46 | `RUNNING` |
| 5秒後のJob 46 | `RUNNING` |
| process継続 | PID 85131/85132が再起動前後で一致 |
| cancel後のprocess | 両PIDとも残留なし |
| Job 46 accounting | parent=`CANCELLED by 0 / 0:0`、batch=`FAILED / 143:0` |
| Job 47 | job/stepとも`COMPLETED / 0:0`、`PC-210.local`出力 |
| 最終node | `IDLE`、`CPUAlloc=0`、`AllocTRES`空 |
| 最終daemon | PID fileとprocessが85145で一致 |

再起動したslurmdはログに次を記録した。

```text
_fill_registration_msg: found apparently running JobId=46
_handle_node_reg_resp: slurmctld sent back 8 TRES.
```

これは、既存slurmstepd/job processを単に放置したのではなく、再起動時のnode登録に
実行中Job 46を含めてcontrollerと整合を取り直したことを示す。明示cancel後には
`_sack_connect: connected to /var/run/slurm/sack.socket`、step cleanup、epilog completeが
記録され、その後Job 47も正常終了した。

Job 46のparent stateが`CANCELLED`、batch stepが`FAILED/143:0`なのは矛盾ではない。
driverが明示的に`scancel`し、job scriptのTERM trapが143で終了したためである。この
試験の判定対象は異常終了をまたいだ追跡、cancel時の回収、後続job受付であり、3点とも
成功条件を満たした。

## 確認できた事実・考察・限界

### 確認できた事実

- slurmdだけをSIGKILLしても、既存slurmstepdとjob processは直ちには終了しなかった。
- 同じproduction構成でslurmdを再起動すると、Job 46はcontroller上でもRUNNINGを維持した。
- 明示cancelで親子process、CPU、memory、GRES allocationを回収できた。
- 再起動後に新規GRES付きJob 47を実行でき、SACK経由の終了通知も完了した。

### 結果から考えられること

この単一job・単一node条件では、macOS移植後のslurmstepd、SACK、process追跡は
slurmdプロセスの異常終了をまたいで回復可能である。ただし1回の成功で長時間運用、
同時複数job、controller障害との複合条件まで保証するものではない。
