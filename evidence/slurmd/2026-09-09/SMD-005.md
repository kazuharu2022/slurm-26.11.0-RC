# SMD-005 process tree終了 — 試験計画とEvidence

## 判定

- 日時: 2026-09-09 17:10 JST–
- 状態: `PASS_STAGING`
- 前提: SMD-001～SMD-004はstaging構成で `PASS_STAGING`
- 対象: `proctrack/pgid` によるbatch、child、grandchild、background processの終了

## Research Question

macOS上の `slurmd` / `slurmstepd` は、batch job内の基本process treeを通常cancelで
すべて終了させ、同じnodeで動く別jobを維持できるか。

## 固定条件

検証用configは `ProctrackType=proctrack/pgid`、`KillWait=30`。修正版clientと
`NodeAddr=192.168.10.127` を持つ `/tmp/slurm-smd001-fixed` のstaging構成を使う。

target jobは次の4 PIDを記録する。

1. batch shell
2. batch shellが起動したchild shell
3. child shellが起動したgrandchild `sleep`
4. batch shellが直接起動したbackground `sleep`

別allocationのcontrol jobを同時に動かし、targetだけをjob ID指定でcancelする。
PIDはcancel前の `ps` で存在とcommandを記録し、targetがqueueから消えた直後に同じ
PIDが存在しないことを確認する。

## 安全範囲

- signalはdriverが作成したtarget job IDへ通常の `scancel` だけを送る。
- control jobは巻き込み有無を確認後、driverが作成したjob IDだけをcancelする。
- 各jobは3分制限、workloadは180秒で自動終了する。
- driverのEXIT trapは、作成したjobがqueueに残る場合だけcancelする。
- PID指定の `kill` は使わず、slurmdや他user processへsignalを送らない。

## 実行方法

Macの `testuser` sessionで次だけを実行する。

```bash
/tmp/slurm-smd001-fixed/smd005_process_tree_driver.sh
```

表示された全出力と末尾の `run_dir` を保存する。実行後にtarget/controlの `sacct`、
queue、node状態、PID残留を独立照合する。

## 成功条件

1. cancel前にbatch、child、grandchild、backgroundの4 PIDがすべて存在する。
2. target cancel後、記録した4 PIDがすべて消える。
3. targetをcancelした時点でcontrol jobは`RUNNING`のまま維持される。
4. target/controlのstateとsignalがaccountingへ一貫して記録される。
5. driver終了後に両jobがqueueから消え、PC-210がIDLEへ復帰する。
6. `slurmstepd`、test workload、client processが残らない。

残留PID、control jobの巻き込み、node DRAIN、driver errorのいずれかがあれば
SMD-006へ進まず、SMD-005をFAILとして原因を調査する。

## 制約

これは通常のshell process treeを対象とする。`setsid`、double-fork、daemon化など
process groupから意図的に離脱するケースはSMD-109で別途検証し、本試験のPASSを
orphan/zombie cleanup全般の証明とはしない。

## 実測結果

### 初回試験 — BLOCKED

2026-09-09 17:11 JST、driver v1
（SHA-256 `1a6bb1fefc222b1b809972e23f1347d4b65478b7c241792e0ff8e219d8c053be`）
を実行した。

- control Job 29は`RUNNING`になった。
- target Job 30は30回の待機中、`PENDING`のままでprocess treeを起動できなかった。
- EXIT cleanupはJob 29と30をどちらもcancelし、queue残留はなかった。
- `sacct`では両jobの`ReqMem=128G`だった。
- Job 29の終了時刻とJob 30の開始時刻はともに17:12:03。controlの解放後にtargetが
  allocationされ、その直後にcleanupでcancelされた。

したがって、初回試験はprocess追跡機能のFAILではなく、targetが試験本体を開始
できなかった `BLOCKED` と判定する。

### 原因と修正

configは `SelectType=select/cons_tres` だが、v1はmemoryを指定していなかった。
実測ではcontrol/targetが各128 GiBを要求し、RealMemory=128 GiBのPC-210で同時に
allocationできなかった。

driverの両job共通optionへ次を追加した。

```text
--cpus-per-task=1
--mem=1G
```

修正後driverを `/bin/sh -n` で確認し、sourceとstagingのSHA-256一致を確認した。

### 2回目試験 — BLOCKED

2026-09-09 17:19 JST、memory修正版で再実行した。

- control Job 31とtarget Job 32は同時に`RUNNING`となり、両方とも`ReqMem=1G`だった。
- Job 32はbatch、child、background、grandchildの4 PIDを記録した。
- `target.out`には`tree_ready`まで出力されていた。
- しかしdriverは10秒後に`error target tree did not become ready`で終了した。
- EXIT cleanupはJob 31/32をcancelした。両jobはqueueから消え、PC-210は`IDLE`、
  記録したPID 69541、69551、69557、69558、69567はすべて消えていた。

target workloadは `target.ready` を作成していたが、サイズは0 byteだった。driverは
`[ -s target.ready ]`、すなわち1 byte以上のfileだけをreadyとしていた。この
producer/consumer条件の不一致により、実際には準備完了していたJob 32を検出できなかった。

したがって2回目もprocess-tree cancelの本試験には進んでおらず、試験ハーネスの
`BLOCKED`と判定する。

### 第2修正

target workloadのmarker生成を0 byteのfile作成から、`ready`と改行を書き込む方式へ
変更した。driverの `-s` 判定と一致し、partial writeも避けられる。

```text
Before: : >"${run_dir}/target.ready"
After:  printf 'ready\n' >"${run_dir}/target.ready"
```

修正後の `smd005_process_tree.sh` は `/bin/sh -n` を通過し、sourceとstagingの
SHA-256はともに
`e15192c42c109252ee764424a0052bf537ca99cb4145adb15398ed2576c1214e`。
Slurm sourceやdaemonは変更していない。この時点では第3回試験は未実施だった。

### 3回目試験 — PASS_STAGING

2026-09-09 17:25 JST、marker修正版でJobs 33/34を実行した。

| 確認対象 | 観測結果 |
|---|---|
| 同時allocation | control Job 33とtarget Job 34がともに`RUNNING`。各`ReqCPUS=1 ReqMem=1G` |
| cancel前process | batch=70772、child=70774、background=70775、grandchild=70778を`ps`で確認 |
| process group | 4 processはいずれもPGID 70772。grandchildのPPIDはchild 70774 |
| target cancel | Job 34をcancelし、queueから1秒で消滅 |
| cancel後process | targetの4 PIDすべて`residual=NO` |
| 別job分離 | target cancel後もcontrol Job 33は`RUNNING` |
| accounting | Job 33/34=`CANCELLED by 3001`、両batch step=`CANCELLED 0:15` |
| 最終cleanup | Jobs 33/34はqueueになく、PC-210=`IDLE CPUAlloc=0 AllocTRES=(empty)` |
| 最終PID確認 | controlを含む5 PIDすべて不在 |

driverはexit 0で`SMD005_CLIENT_RUN_COMPLETE`まで到達した。6つの成功条件を
すべて満たしたため、SMD-005を`PASS_STAGING`と判定する。
