## 分析

同一subnetの192.168.10.180だけがARP未解決である。このため、Slurm設定や6817

VLAN/AP isolationなど、L2到達性より手前をhead node側で確認する必要がある。

初回事前確認では、SMD-001の成功条件であるjob投入・hostname出力・process

確認できた。`ExitCode=0:0` はclient abortの成功を意味しないため、SMD-001の
判定には使用しない。

## 原因と修正

`client_io_handler_create()` は `client_io_t` を確保し、`ioservers_lock` は明示
初期化していたが、I/O thread状態を守る `io_mutex` と終了待ち用 `io_cond` は
初期化していなかった。直後の `client_io_handler_start()` は未初期化の
`io_mutex`をlockするため、macOS pthreadが `EINVAL` を返していた。

`src/api/step_io.c` に次を追加した。

```c
cio->io_running = false;
slurm_mutex_init(&cio->io_mutex);
slurm_cond_init(&cio->io_cond, NULL);
```

`client_io_handler_destroy()` には対称なcleanupを追加した。

```c
slurm_cond_destroy(&cio->io_cond);
slurm_mutex_destroy(&cio->io_mutex);
```

Darwin限定分岐にはしていない。pthread objectを使用前に初期化し、使用後に破棄
することは全platformで必要なlifecycleだからである。

## 修正版再試験: Job 18

Job 18は2026-09-09 16:02:40 JSTに開始・終了した。

ユーザーがstaging版 `srun` を実行した結果、従来の
`client_io_handler_start: pthread_mutex_lock(): Invalid argument` は発生せず、
client I/O handler開始処理を通過した。したがって、mutex/condition初期化修正の
効果は確認できた。

その後、別の失敗が発生した。

```text
srun: error: _fwd_tree_get_addr: can't find address for host PC-210, check slurm.conf
srun: error: Task launch for StepId=18.0 failed on node PC-210: Can't find an address, check slurm.conf
srun: error: Application launch failed: Can't find an address, check slurm.conf
srun: Job step aborted
```

accountingとqueueの確認結果:

```text
18    hostname  testuser  FAILED     00:00:00  0:116  PC-210
18.0  hostname            CANCELLED  00:00:00  0:116  PC-210
```

`squeue -j 18` はheaderだけを返し、allocationは残っていない。

接続先を分離して確認した。

```text
$ nc -G 2 -zv PC-210 6818
nc: getaddrinfo: nodename nor servname provided, or not known

$ nc -G 2 -zv 192.168.10.127 6818
Connection to 192.168.10.127 port 6818 [tcp/*] succeeded!
```

installed configのcompute node定義には `NodeAddr` がなかった。

```text
NodeName=PC-210 CPUs=18 ... Gres=gpu:apple:1
```

Slurm 26.11.0-0rc1 source tree付属の `slurm.conf(5)` は、`NodeAddr` を通信経路の
確立に使う名前として `getaddrinfo()` へ渡し、IP addressも指定可能としている。
また `src/common/forward.c` の `_fwd_tree_get_addr()` は
`slurm_conf_get_addr()` が失敗した場合、今回と同じerrorを出す。

以上から、Job 18の直接原因はfirewallや6818の待受ではなく、Mac client上での
短縮名 `PC-210` の名前解決失敗と判定した。検証用configを作成し、node定義だけを
次のように変更した。

```text
NodeName=PC-210 NodeAddr=192.168.10.127 CPUs=18 Boards=1 SocketsPerBoard=1 CoresPerSocket=18 ThreadsPerCore=1 RealMemory=131072 Gres=gpu:apple:1
```

```text
/tmp/slurm-smd001-fixed/slurm.conf
sha256=69c6af99259a48add1e690f610869e9ee65d4ead91a860b63fdb2d6328ec9b85
mode=0644
```

次の再試験ではsource fix済みbinaryとaddress fix済みconfigを同時に使用する。

```bash
DYLD_LIBRARY_PATH=/tmp/slurm-smd001-fixed \
SLURM_CONF=/tmp/slurm-smd001-fixed/slurm.conf \
  /tmp/slurm-smd001-fixed/srun \
  --partition=debug \
  --nodes=1 \
  --ntasks=1 \
  --time=00:01:00 \
  --chdir=/tmp \
  /bin/hostname
```

この数値IPがDHCPで変動する構成なら、production反映時にはDHCP reservationまたは
head/worker双方で解決できる固定DNS名を用意する。検証用configで成功するまでは、
production configの変更やSMD-001の合格判定を行わなかった。

## Evidence上の不足

- `/var/log/slurm/slurmd.log` はroot所有で、現在の非対話sudoではpassword入力が
  できず取得できなかった。
- ubuntu2504側のinterface、IP、`slurmctld` service、6817 LISTENはユーザー提供
  出力とMacからの再接続で確認済み。
- Job 16/17のallocationが`squeue`に残っていないことは確認済み。ただし
  client abortにもかかわらず`sacct ExitCode=0:0`であり、正しい失敗code記録は
  未達成。
- `slurmd.log` のJob 19該当行は権限不足で未取得。ただしclient直接出力、
  controller/database record、process、node状態は独立確認済み。
- source fixとconfig fixのproduction install/reconfigure後の再試験は未実施。
- `srun` hashの初回値と再確認値が異なる理由は未確認。ただし再確認値は2回連続
  で一致し、現在のbuild artifactとも一致した。
