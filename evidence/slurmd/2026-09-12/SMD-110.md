# SMD-110 ulimit propagation

- 状態: `PASS`
- 対象: Apple M5 Max / arm64 / macOS上の`slurmd`・`slurmstepd`
- Slurm: `26.11.0-0rc1`
- test user: `testuser`（UID/GID 3001:3001）
- production設定変更: なし
- daemon restart: なし
- package導入: なし

## Research Question

submit processのsoft resource limitは、macOS worker上のbatch payloadへ設定方針どおり伝播するか。
特に`CPU`、`CORE`、`STACK`、`NOFILE`について、既定policyとuserが明示した`--propagate`の
両経路が`slurmd`をabortさせず、hard limitを不正に変更しないか。

## sourceと仕様

`src/common/slurm_rlimits_info.c`は`CPU`、`CORE`、`STACK`、`NOFILE`を伝播対象名として定義する。
同梱`slurm.conf(5)`では、`PropagateResourceLimits`もExceptもなくuser optionもない場合は
全limitを伝播すること、`sbatch --propagate`でuserが対象を上書きできること、伝播するのは
soft limitでありworker daemonのhard limitを越えられないことを説明している。

`src/slurmd/slurmstepd/ulimits.c`の非Linux `_prlimit()`はPID 0に対して`getrlimit()` / 
`setrlimit()`を呼ぶ。`_set_limit()`はjob環境の`SLURM_RLIMIT_*`を読み、configまたはuser指定時に
soft limitだけを変更し、payloadへ渡す前に内部変数を削除する。明示指定の`setrlimit()`失敗は
errorとして記録される。

macOS向けportではDarwinの`RLIMIT_RSS`と`RLIMIT_AS`のalias・有限値拒否を避けるため、memory由来の
自動RSS/VSIZE設定を別途skipしている。本試験はそのnegative memory enforcementではなく、macOSが
提供する4種類の一般resource limit伝播だけを対象とする。memory強制はSMD-302で扱う。

## 仮説

1. production configに`PropagateResourceLimits` / `Except`がなければ、default caseの4 soft limitは
   submit processとjob payloadで一致する。
2. explicit caseで`--propagate=CORE,CPU,NOFILE,STACK`を指定すると、CPU 60秒、CORE 0 byte、
   STACK 4 MiB、NOFILE 256のsoft limitがjobに設定される。
3. hard limitはsubmit soft値で上書きされず、2 job間で同じworker daemon ceilingを維持する。
4. payload環境に`SLURM_RLIMIT_*`は残らず、job/accounting/daemon/final resource stateは正常に収束する。

## 試験方法

小さなC probeを既存Apple clangでrun directoryへbuildし、submit直前とbatch payload内の
`getrlimit(2)`値を同一binaryで取得する。値はkernelのraw単位で記録する。

| case | submit process | sbatch option | 判定 |
|---|---|---|---|
| `default` | limit変更なし | `--propagate`なし | 4 soft limitがsubmit snapshotとjobで一致 |
| `explicit` | softだけCPU=60、CORE=0、STACK=4 MiB、NOFILE=256 | `--propagate=CORE,CPU,NOFILE,STACK` | 4値がsubmit snapshot・固定期待値・jobで一致 |

両caseともhard limitは読取だけで、`soft <= hard`または両方infinityを必須とし、job側hard値が
2 case間で不変であることを確認する。CPU時間を消費させず、core dumpも生成しない。

## 成功条件

1. submit側とjob側で`CPU`、`CORE`、`STACK`、`NOFILE`のsoft値が全て一致する。
2. explicit caseはraw値`60`、`0`、`4194304`、`256`と一致する。
3. hard値が各soft値以上またはinfinityで、2 case間のjob hard値が不変である。
4. payloadの`SLURM_RLIMIT_*`件数が0で、stderrが空である。
5. job/batchが2件とも`COMPLETED 0:0`となる。
6. `_prlimit ... Invalid argument`、`Can't propagate`、mutex/fatal/abortがdaemon logにない。
7. 最終nodeは`IDLE`、割当0、queue・`slurmstepd`・test process残留0。
8. slurmd PID/StartTimeとproduction config/input hashが不変である。

## 安全性とEvidence境界

production config、daemon、account、packageは変更しない。2件とも1 CPU、128 MiB、1分上限の
read-only probe jobであり、異常時はdriverが対象Job IDだけをcancelする。limitを実際に超過させる
enforcement試験ではないため、本試験だけでCPU時間超過時のsignalやNOFILE枯渇時のapplication挙動は
証明しない。またhard limitはsubmit host値との一致ではなく、worker daemon ceilingとして評価する。

### soft limitの比較

| limit | default submit | default job | explicit submit | explicit job | 判定 |
|---|---:|---:|---:|---:|---|
| CPU（seconds） | infinity | infinity | 60 | 60 | PASS |
| CORE（bytes） | 0 | 0 | 0 | 0 | PASS |
| STACK（bytes） | 8372224 | 8372224 | 4194304 | 4194304 | PASS |
| NOFILE（count） | 2560 | 2560 | 256 | 256 | PASS |

default policyと明示`--propagate=CORE,CPU,NOFILE,STACK`の両経路で、全4 soft limitが
submit直前のkernel値とjob payload内で完全一致した。explicit caseも事前固定値どおりだった。

### hard limitと内部環境

job側hard limitは両caseともCPU/CORE/NOFILEがinfinity、STACKが67092480 bytesで不変だった。
submit processではCORE hardが0だったのに対し、jobではinfinityだった。これはhard limitを
submit側から伝播せず、worker daemon側のceilingを保持するという仕様に一致する。hard値を
submit値へ合わせることを成功条件にしなかった試験設計が妥当だった。

submitとjobの双方で`slurm_rlimit_env_count=0`だった。特にjob payloadに内部
`SLURM_RLIMIT_*`が残らないことを確認した。全outputはUID/GID 3001:3001、mode 0644で、
stderrとaccounting command stderrは全て0 byteだった。
