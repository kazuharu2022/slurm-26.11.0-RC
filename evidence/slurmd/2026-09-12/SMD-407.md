# SMD-407 TLS plugin

- 状態: `DUAL_HOST_ISOLATED_ARTIFACTS_COMPLETE_CERT_PLAN_REQUIRED`
- controller/database/Ubuntu worker: `ubuntu2504` / x86_64
- macOS worker: `PC-210` / arm64
- Slurm: `26.11.0-0rc1`
- 現行TLS: `tls/none`

## 目的

`tls/s2n`を使ってSlurm内部RPCを暗号化し、正常Jobだけでなく、非TLS clientおよび信頼できない
証明書がfail closedになること、証明書更新後にJob受付が回復することまで実測する。

## 仕様から確定した境界

同梱の`doc/html/tls.shtml`と`slurm.conf(5)`では次が要件である。

- `TLSType=tls/s2n`は通信する全Slurm componentで一致させる。
- TLS必須listenerは非TLS RPCをparse/auth/dispatch前に拒否する。
- CA certificateは全componentから参照可能にする。
- slurmctld、slurmdbd、slurmdはそれぞれ対応するcertificate/key pairを必要とする。
- CAはSlurmUserまたはroot所有、秘密鍵はotherからread/write/execute不可にする。
- `CommunicationParameters=disable_http`を設定しない限り、daemon portのHTTP受付は
  `TLSType`とは独立である。cleartextを完全排除する試験ではこの設定も必要である。
- slurmd証明書の自動更新は`certmgr/script`で可能だが、static certificateの置換・daemon再起動
  によるrotationとは別の機能である。

`certgen_script.so`と`certmgr_script.so`は存在した。`tls_s2n.so`は存在しない。

## Static certificate contractと隔離stage設計

同梱の`slurm.conf(5)`、`slurmdbd.conf(5)`、`tls.shtml`および

- `ca_cert.pem`は全hostに配置し、mode 0644、ownerはrootまたはSlurmUserとする。
- Ubuntuには`ctld_cert.pem`/`ctld_cert_key.pem`、`dbd_cert.pem`/`dbd_cert_key.pem`、

- 現実装のhostname callbackは常に許可を返すためSAN一致はruntime必須条件ではないが、将来の

- slurmctld/slurmdbd/slurmdはいずれもclient/serverとして通信し得るため、daemon leafには

## Coordinated TLS runtime cutover boundary

次のproduction phaseでは、全Slurm componentが同じTLS modeで通信する必要があるため、単一hostだけを
最終状態として切り替えない。実施順序を次のように固定する。

1. 両node IDLE、queue空、inactive stateとartifact/certificate hashを再確認する。
2. Ubuntuの`slurm.conf`と`slurmdbd.conf`をbackupし、`TLSType=tls/s2n`、明示certificate path、
   `CommunicationParameters=disable_http`を設定する。
3. Ubuntuでslurmdbd、slurmctld、slurmdの順にrestartし、Ubuntu control planeをTLSで復帰させる。
   この時点ではPC-210が一時的に`NOT_RESPONDING`となり得るため、runtime PASSとは扱わない。
4. PC-210のlocal `slurm.conf`をbackupして同じTLS profileへ切り替え、launchd slurmdをrestartし、
   両node IDLEまで待つ。
5. batch CPU、direct `srun`、Apple GPU、accounting、mixed-architecture RPCを実測する。
6. `tls/none` clientとrogue CA clientがTLS listenerから拒否されるfail-closed evidenceを取得する。
7. 検証後はMac local config、Ubuntu controller/database configの順でoriginal `tls/none`へ戻し、
   両node IDLE、queue空、service active、hash readbackを確認してからinactive artifactをcleanupする。

このphaseは設定変更と4 daemonのrestartを伴い、短時間のcontrol-plane/worker不一致が発生する。
個別のapply、runtime、restore markerが揃うまでSMD-407をPASSへ昇格しない。

### Coordinated TLS runtime drivers

ユーザーの明示承認後、上記の順序を機械的に守る2本のruntime driverを追加した。

- Ubuntu control `smd407_ubuntu_tls_runtime_control.sh`は`apply`、`verify`、`restore`、`cleanup`を
  分離する。`apply`は両設定のbackup後にTLSを有効化し、Ubuntu 3 serviceとcontrol planeを復帰させる。
  `verify`はMac runtime完了markerをgateに、Ubuntu TLS control plane、`disable_http`、queue空を確認し、
  元のTLS-none configを使うclientとrogue CAを使うclientがともに拒否されることを検査する。
  Macはruntime試験後に先にlocal TLS-noneへ戻るため、この時点のPC-210 stateは証拠として保存するが
  `IDLE`を必須にしない。`restore`でUbuntuをTLS-noneへ戻した後は両node `IDLE`を必須にする。
