# SMD-402 mixed-architecture multi-node job

- 状態: `PASS`
- controller host: `ubuntu2504` / x86_64
- workers: `ubuntu` / x86_64 / Ubuntu、`PC-210` / arm64 / macOS
- Slurm: `26.11.0-0rc1`
- production変更: Ubuntu node定義、非default partition `smd402`、systemd `slurmd.service`
- validation jobs: 581、582、583、およびPID確認用follow-up jobs

## 目的

x86-64 Ubuntu workerとarm64 macOS workerを同一allocation・同一stepへ割り当て、
architecture-nativeなpayloadを各nodeで起動し、rank、stdio、終了、cancelを確認する。

## 2026-09-12 head-node preflight

Ubuntu側でユーザーがread-only確認を実施した。

```text
hostname=ubuntu2504
architecture=x86_64
systemctl is-active slurmd=inactive
Unit slurmd.service could not be found.
PC-210|debug*|idle|none
ubuntu|pepilog|unknown*|none
```

controller上のnode `ubuntu`は`UNKNOWN+NOT_RESPONDING`で、`BootTime=None`、
`SlurmdStartTime=None`だった。さらにPC-210はpartition `debug`、ubuntuは`pepilog`に属し、
両nodeを含む共通partitionは存在しない。`testuser`のUID/GIDはUbuntuでも3001:3001で一致した。

## 判定

現在の構成には稼働中の第二workerがなく、2-node allocationを作れない。このためJobは投入せず、
SMD-402を`PREREQUISITE_MISSING_SECOND_WORKER`とする。これはmacOS `slurmd`のfailureではない。

## 再開条件

1. x86-64側に同版`slurmd`を構築し、controllerへ正常登録する。
2. UID/GID 3001:3001とauth/slurm keyを両workerで一致させる。
3. PC-210とx86-64 workerを含む一時partitionをcontroller正本へ追加する。
4. `/bin/sh`など各architectureのnative binaryを同じ絶対pathで使う。
5. 両nodeがIDLE、共通partition UP、queue空であることを再確認する。

第二workerの導入とcontroller設定変更は現在の「Mac上のslurmd検証」の範囲を広げるため、
ユーザーの明示承認なしには実施しない。

## 2026-09-12 scope expansion approval

ユーザーは`ubuntu2504`をcontrollerとx86-64 workerの兼用hostにする方針を承認した。
承認範囲は、同版`slurmd`のsystemd管理、既存node `ubuntu`の正常登録、およびPC-210と
ubuntuだけを含むSMD-402用partitionの追加である。

変更前に次をread-onlyで確認する。

- `slurmd -C`と既存`NodeName=ubuntu`のCPU/memory topology差分
- `slurm`、`testuser`のUID/GID、home、shell
- `auth/slurm` keyの存在、owner、mode
- cgroup v2 mountと`proctrack/cgroup`、`task/affinity` plugin
- 6818/TCPの未使用、spool/log/run directory
- `ubuntu`、`ubuntu2504`、`PC-210`の名前解決
- controller、slurmdbdの稼働状態

preflightがPASSするまではunit、directory、config、partitionを変更しない。

### 起動前に修正が必要な差分

`slurmd -C`の実hardwareは次のとおりだった。

```text
NodeName=ubuntu2504 CPUs=8 Boards=1 SocketsPerBoard=1 CoresPerSocket=4 ThreadsPerCore=2 RealMemory=64024 Gres=gpu:nvidia_geforce_rtx_3060_laptop_gpu:1
```

既存controller定義は`NodeName=ubuntu CPUs=8 Boards=1 SocketsPerBoard=8
CoresPerSocket=1 ThreadsPerCore=1 RealMemory=15990`であり、socket/core/thread、memoryが一致しない。
`-N ubuntu`だけではhardware mismatchを解消できないため、登録前にcontroller正本を実値へ直す。

名前解決もそのまま利用できない。

```text
ubuntu      -> 192.168.10.118
ubuntu2504  -> 127.0.1.1
PC-210      -> 192.168.10.128
```

過去のcontroller addressは`192.168.10.180`だったため、現在のinterface addressを再確認し、
node定義へ数値`NodeAddr`と実hostname `NodeHostName=ubuntu2504`を明示する。

`/var/spool/slurmd`と`/run/slurm`は存在せず、`/var/log/slurm`だけがslurm:slurmで存在する。
systemd unit作成時にowner/modeを明示して準備する必要がある。

GPUは`slurmd -C`でNVIDIA RTX 3060 Laptop GPUとして検出されたが、GRESをSMD-402へ含めるか、
CPU-only workerとして明示的に除外するかは`gres.conf`とNVML状態を確認してから決める。

以上によりpreflightは一部PASSだが、まだdaemon/config変更には進めない。

## 2026-09-12 11:21 JST 追加preflight

Ubuntu root shellで、実interface、route、GRES、cgroup設定を追加確認した。

```text
br0              UP             192.168.10.180/24
192.168.10.128 dev br0 src 192.168.10.180 uid 0
ubuntu      -> 192.168.10.118
ubuntu2504  -> 127.0.1.1
PC-210      -> 192.168.10.128
```

したがって既存node名`ubuntu`は維持しつつ、controller正本へ
`NodeAddr=192.168.10.180 NodeHostName=ubuntu2504`を明示する必要がある。DNS名
`ubuntu`や`ubuntu2504`をNodeAddrとして使うと、それぞれ旧addressまたはloopbackへ向くため
不適切である。

Linux worker向け`cgroup.conf`はcgroup v2で使用可能な設定だった。

```text
ConstrainCores=yes
ConstrainDevices=yes
ConstrainRAMSpace=yes
ConstrainSwapSpace=yes
```

NVIDIA RTX 3060 Laptop GPU 1基とNVMLによる自動検出は確認できた。ただしproductionの
`gres.conf`はPC-210だけを対象とする次の1行であり、controllerの`NodeName=ubuntu`にも
GPUは定義されていない。

```text
NodeName=PC-210 Name=gpu Type=apple File=/dev/null
```

SMD-402はCPU mixed-architecture stepの検証であるため、Ubuntu GPUを新たにGRES登録せず、
既存のApple GPU設定にも触れない。`slurmd -C`が表示したNVIDIA GRESはhardware候補であり、
controller登録済みresourceではない。

`slurmd -G`は`/var/spool/slurmd`が未作成のため、GRES評価より前にdomain socket directory
errorで停止した。これはplugin/GPU failureではなく、まだworkerを起動していない変更前状態と
整合する。directory作成後に再実行してCPU-only registrationを確認する。

### 変更計画

1. `slurm.conf`を退避し、node `ubuntu`を実topologyへ更新する。
2. `NodeAddr=192.168.10.180`、`NodeHostName=ubuntu2504`を明示する。
3. PC-210とubuntuだけを含む非default partition `smd402`を追加する。
4. `/var/spool/slurmd`を準備し、upstream `etc/slurmd.service.in`に沿った
   `Type=notify`、`RuntimeDirectory=slurm`、`Delegate=yes`のunitを作る。
5. controller reconfigure、Ubuntu単一node smoke、systemd enableまでを先に検証する。
6. その後だけ2-node success/cancel stepを実行する。

設定候補のnode topologyは`CPUs=8 Boards=1 SocketsPerBoard=1 CoresPerSocket=4
ThreadsPerCore=2 RealMemory=64024`とする。実測値より大きいresourceは宣言しない。

## 実装した検証ハーネス

### Ubuntu worker導入

は承認済みpreflight値を再確認してから、次を一続きで実行する。

途中で失敗した場合はserviceを停止・削除し、退避した`slurm.conf`を戻してcontrollerを

Ubuntu worker導入をPASSとする。

## Mixed-architecture runtime — Evidence readback PASS

### Job 582: success path

stdoutは2 rankが別architectureで起動したことを直接示した。rankの配置順は固定せず、集合
`0,1`と両nodeへの1 taskずつの配置を検証した。

```text
record=success job_id=582 step_id=0 procid=1 node=ubuntu host=ubuntu2504 arch=x86_64 uid=3001 gid=3001
record=success job_id=582 step_id=0 procid=0 node=PC-210 host=PC-210.local arch=arm64 uid=3001 gid=3001
```

success stderrとaccounting stderrはともに0 bytesだった。jobとstepは同じ2 nodeを記録し、
双方とも`COMPLETED 0:0`だった。

```text
582|testuser|COMPLETED|0:0|PC-210,ubuntu|billing=3,cpu=3,mem=195096M,node=2
582.0||COMPLETED|0:0|PC-210,ubuntu|cpu=3,mem=195096M,node=2
```

CPUが3となるのは、`SelectTypeParameters=CR_CORE_MEMORY`下でUbuntuの1 physical coreが
2 thread、Macの1 coreが1 threadとして割り当てられたためである。また明示的なmemory要求を
付けなかったため、両nodeのmemory合計195096 MiBが割り当てられた。これは本試験の
architecture/rank検証を妨げないが、通常運用では`--mem`を明示すべき設定上の注意点である。

### Job 583: cancel path

cancel前に両nodeでshellとchild sleepが生存し、UID/GID 3001:3001であることを確認した。

```text
record=ready job_id=583 step_id=0 procid=1 node=ubuntu host=ubuntu2504 arch=x86_64 pid=82348 child_pid=82349 uid=3001 gid=3001
record=ready job_id=583 step_id=0 procid=0 node=PC-210 host=PC-210.local arch=arm64 pid=39062 child_pid=39063 uid=3001 gid=3001
record=signal procid=1 node=ubuntu pid=82348
record=signal procid=0 node=PC-210 pid=39062
```

clientは143で終了し、両taskがSIGTERMを受けた。job-level会計は`CANCELLED by 0`、stepは
trapが143を返したため`FAILED 143:0`となった。これは正常完了への誤分類ではなく、期待した
cancel経路を表す。

```text
583|testuser|CANCELLED by 0|0:0|PC-210,ubuntu|billing=3,cpu=3,mem=195096M,node=2
583.0||FAILED|143:0|PC-210,ubuntu|cpu=3,mem=195096M,node=2
```

follow-up stepによるPID確認は4件すべて`residual=NO`だった。

```text

residual=NO node=ubuntu pid=82349
residual=NO node=PC-210 pid=39062
residual=NO node=PC-210 pid=39063
```

## 最終判定

`SMD-402: PASS`。

x86-64 Ubuntu workerとarm64 macOS workerを同一allocation・同一stepへ割り当て、native
`/bin/sh`を各nodeで起動できた。rank、stdout、identity、正常終了、cancel、accounting、
親子process回収、resource解放、daemon継続の全成功条件を満たした。

この結果が保証するのはarchitecture-neutralなshell payloadとSlurm step transportである。
単一architecture向けELF/Mach-O binaryの相互実行、外部MPI/PMIx application、共有filesystem、
Ubuntu NVIDIA GPUとMac Apple GPUを同時利用するheterogeneous GPU Jobは別試験であり、
SMD-402のPASSには含めない。
