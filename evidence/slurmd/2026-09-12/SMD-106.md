# SMD-106 複数task

- 状態: `PASS`
- 対象: Apple M5 Max / arm64 / macOS上の`slurmd`・`slurmstepd`
- Slurm: `26.11.0-0rc1`
- test user: `testuser`（UID/GID 3001:3001）
- production設定変更: なし
- package導入: なし

## Research Question

macOS workerの1 node内で、単一`srun` stepが4 taskを同時に起動し、各taskへ一意なrank/local
IDと共通のtask/node countを伝播できるか。また標準出力、終了状態、accounting、process・資源回収が
task間で欠落または干渉しないか。

## 既存Evidenceとの差分

SMD-123とSMD-126では2 task stepが終了し、task IDとplugin/hook経路が一致することを確認済みで
ある。ただし、その試験は全taskが同時に生存した瞬間を成功条件にしていない。SMD-106では4 taskが
それぞれready recordを作り、driverが全4 PIDの生存とjob `RUNNING`を確認するまでreleaseしない
barrierを設ける。これにより、逐次実行を4 task成功と誤認しない。

## 試験設計

1. production configから、現在のen0 IPv4を`NodeAddr`として補ったclient専用configを`/tmp`へ作る。
2. `testuser`で`-N1 -n4`、1 CPU/task、256 MiB、1分上限、`mpi=none`の`srun`を開始する。
3. 各taskはrank別ready recordを書き、release fileが作られるまで待つ。
4. driverはrank 0～3のrecord、4個の一意PID、全PID生存、job `RUNNING`を同時に確認する。
5. barrierを解放し、各taskのstdout record、終了record、client return codeを照合する。
6. job/step accountingと最終node・queue・process・input hashを確認する。

## 成功条件

1. 4 taskがbarrier到達時に同時に生存し、PIDがすべて異なる。
2. `SLURM_PROCID`と`SLURM_LOCALID`の集合が各0～3、`SLURM_NODEID=0`である。
3. 全taskで`SLURM_NTASKS=4`、`SLURM_STEP_NUM_TASKS=4`、`SLURM_NNODES=1`となる。
4. 全taskが`testuser` 3001:3001、同じPC-210 hostnameで実行される。
5. stdoutにtaskごとの1 recordがあり、stderrは空、`srun` return codeは0である。
6. job/step 0が`COMPLETED 0:0`となる。
7. 終了後はnode `IDLE`、CPU/memory割当0、queue・`slurmstepd`・関連process残留0である。
8. slurmd PID/StartTimeとproduction config/payload hashが前後一致する。

## 安全性

production config、daemon、account、packageは変更しない。失敗時は一意なjob nameで対象jobを
探索し、そのjobだけをcancelする。barrierは最大30秒でpayload自身もtimeoutする。4 CPU、256 MiB、
最大1分に制限し、既存processやfileへsignal・変更を行わない。

## 実測結果 — PASS

2026-09-12 00:38 JST、production構成でJob/Step 457.0を4 taskとして実行した。driverがrelease
fileを作る前に、rank 0～3のPID 4458～4461がすべてjob `RUNNING`中に生存していた。

全taskで`step_id=0`、`PROCID=LOCALID=0..3`、`NODEID=0`、`NTASKS=4`、
`STEP_NUM_TASKS=4`、`NNODES=1`だった。実identityは3001:3001、hostnameは
`PC-210.local`で一致した。4 taskのstart/release epochはすべて1789141111で、stdoutは4 record、
stderrは0 byte、client return codeは0だった。

accountingはjob/stepとも`COMPLETED 0:0`で、jobには`cpu=4`、stepにも`cpu=4`が記録された。
最終nodeは`IDLE`、CPU/memory割当0、`AllocTRES`空、queue空だった。`slurmstepd`と関連processは
残らず、slurmd PID 94504、`SlurmdStartTime=2026-09-11T23:11:50`、production configと
payload hashは前後一致した。

生Evidence: [`SMD-106-final.txt`](SMD-106-final.txt)

## 結論

単一Mac node上の4 taskは逐次ではなく、barrier時に4個の一意PIDとして同時に生存した。
task ID集合、共通環境、I/O、accounting、最終資源・process回収がすべて成功条件を満たしたため、
SMD-106を`PASS`とする。

## 未検証として残す範囲

- 複数nodeにまたがるtask配置
- MPI pluginを使うtask起動（今回は`mpi=none`）
- 18 CPUを超えるovercommit（SMD-108で扱う）
- 異常終了taskが他taskへ与える影響（SMD-107またはSMD-111で扱う）
- CPU affinity、NUMA binding、GPU binding
