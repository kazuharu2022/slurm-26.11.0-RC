# SMD-113 isolated disk/spool failure

- 状態: `PASS`
- 対象: Apple M5 Max / arm64 / macOS上のfilesystemと`slurmd`・`slurmstepd`
- Slurm: `26.11.0-0rc1`
- production設定変更: preflightではなし
- daemon restart: preflightではなし
- package導入: なし

## Research Question

system diskやproduction spoolを枯渇させず、容量制限した使い捨てvolumeで`ENOSPC`を再現できるか。
その前提が成立した場合、隔離`SlurmdSpoolDir`でのJob launch failureを明確に検出し、production
daemon、spool、nodeを完全に回復できるか。

## Source根拠

`src/slurmd/slurmstepd/mgr.c::_make_batch_dir()`は、Job用directoryの`mkdir(2)`が
`ENOSPC`で失敗すると`SlurmdSpoolDir is full`のreasonでnodeをdrainする。そのためruntime試験では、
payload未実行、worker logの`No space left on device`、nodeのDRAIN reasonを主要Evidenceにする。

## 二段階設計

### Phase A: disposable volume preflight

1. `/tmp`内に64 MiBのHFS+ disk imageを作成し、同じrun directoryへmountする。
2. production `/var/spool/slurmd`と`/var/log/slurm`の容量を変更前に記録する。
3. 128 MiBまで書こうとするbounded `dd`でimageだけを満杯にし、`ENOSPC`を確認する。
4. 隔離spool内の`mkdir`も`ENOSPC`になることを確認する。
5. fillerを削除し、同じ`mkdir`が成功することで回復を確認する。
6. volumeをdetachし、生成したdisk imageだけを削除する。
7. production config、launchd serviceの稼働状態、slurmd PIDが不変であることを確認する。
   固定パスのplistが存在する場合は、そのhashも監視する。

Phase AではSlurm Jobを投入せず、daemonを停止・再起動せず、production spool/logへ書き込まない。
失敗時も生成したimage/mountだけをcleanup対象にする。

### Phase B: isolated Slurm runtime

Phase AがPASSした後にだけ作成・実行する。production launchdをclean stopし、同じproduction binaryを
隔離configと有限volume上の`SlurmdSpoolDir`で一時起動する。volume full後に1件だけJobを投入し、
payload未実行、`ENOSPC` log、DRAIN reason、held/cancel状態を採取する。filler解放後は一時daemonを
停止・volumeをdetachし、production launchdを再開、必要なRESUMEとsmoke Jobで回復を証明する。

Phase Bはdaemon stateを変更するため、Phase Aの実測結果を確認する前には進めない。

## Phase A成功条件

1. image作成・attachが成功し、mount先とdeviceを一意に記録できる。
2. bounded `dd`とisolated spoolの`mkdir`が`ENOSPC`で失敗する。
3. filler削除後の`mkdir`が成功する。
4. detach後にmountが残らず、disk imageも残らない。
5. production slurmd PID、config、launchd serviceのrunning状態が不変である。
6. launchdが報告するPIDとpidfileのPIDが試験前後とも一致する。
7. production filesystemを対象としたwrite/fill操作がない。

## Attempt 1 — harness precondition failure

2026-09-12の初回実行は、run directoryとdisk imageを作成する前のpath検査で停止した。

```text

```

直接原因はlaunchd label/pathの誤記である。harnessはproductionの
`org.schedmd.slurmd`ではなく、余分な`.slurm`を含む
`org.schedmd.slurm.slurmd`を参照していた。読み取り確認では正しいplistが存在し、正しい

修正版ではlabelを`org.schedmd.slurmd`へ統一した。さらに固定plistだけに依存せず、loaded
service `system/org.schedmd.slurmd`の`state = running`、launchd PID、pidfile PIDの一致を
試験前後で検証する。正しい固定pathのplistが存在する場合は、そのhashも入力不変条件へ含める。

## Attempt 2 — harness false negative from `/tmp` canonicalization

修正版を2026-09-12 09:38 JSTに実行し、64 MiB HFS+ imageの作成とattachは成功した。


`attach.out`には次の成功結果が記録されていた。

```text

```

原因はmacOSのpath canonicalizationである。harnessはlogical path
`/tmp/slurm-smd113-preflight-20260912T093846/volume`をmount表現から完全一致検索したが、
`hdiutil`と`mount`はphysical pathの`/private/tmp/.../volume`を報告する。このためattach成功を
未mountと誤判定した。

cleanupは`"disk4" ejected.`、stderrなしで完了した。再確認時にimageは存在せず、対象mountも
残っていない。production slurm.confとplistのSHA-256は試験前後でそれぞれ
`9c7021e4…577a2`、`5db42efb…ede9`と一致し、launchd PIDとpidfile PIDも94504で一致した。
Job投入、volume満杯化、ENOSPC確認、daemon restartは未実施である。

修正版はmount前に`pwd -P`でphysical mount pathを取得し、`hdiutil -mountpoint`、mount table、
attach device parseの全てで同じphysical pathを使う。device未取得時のcleanupもphysical pathを
優先する。

- `/bin/sh -n`: PASS
- approval gateなし: exit 64
- approvalあり・非root: exit 1
- 保存済みattach出力からphysical pathと`/dev/disk4s1`の再parse: PASS
- mount table形式fixtureの照合: PASS
- 100文字超過、行末whitespace、`git diff --check`: PASS
- 修正版driver SHA-256: `1ae12448e948007c863eea9942c4b5381d6a57810ee6c8296ec875825aaec751`

## Phase B実測結果: PASS

2026-09-12 10:08 JSTに、承認済みPhase B driverをPC-210のroot shellで実行した。
開始時はcontroller UP、node IDLE・未割当、queueと`slurmstepd`空、launchd/PID一致だった。
production PID 94504をclean stopし、64 MiB HFS+ volumeの隔離spoolを使うPID 27936を起動した。

### ENOSPCとlaunch failure

- 隔離volumeは使用1,532 KiB・空き63,964 KiB・Capacity 3%から、使用65,020 KiB・
  空き476 KiB・Capacity 100%になった。
- bounded `dd`は65,011,712 bytesを書いた時点で`No space left on device`となりrc 1だった。
- metadata fillerは`exhaust-1409`でENOSPCとなり、その直後のspool `mkdir`もENOSPCになった。
- Job 547は`testuser` 3001:3001で投入されたが、payloadは実行されず、batch stepも生成されなかった。
- isolated daemon logはJob 547のlaunch要求後、`cred_state.new`作成でENOSPCを2回記録した。
- Job 547は`PENDING`、`Reason=launch_failed_requeued_held`、`Restarts=1`、Priority 0となった。
- nodeは`IDLE+DRAIN`、`Reason=SlurmdSpoolDir is full`となり、CPU/memory/GRES割当は0だった。
- 対象Jobだけをcancelし、accountingは`CANCELLED by 0|0:0`、payload markerは最後まで不存在だった。

`mkdir-full-retry.err`のENOSPCは容量解放後の失敗ではない。これは最初の`dd`後にmkdirが
成功できた場合、metadata fillerを追加して満杯状態を確定するための同時刻10:08:09の再試行である。
その後filler群を削除し、別名`recovery-dir`のmkdir/rmdir成功を必須判定としている。

### 回復とproduction復帰

- filler削除後は使用2,044 KiB・空き63,452 KiB・Capacity 4%へ戻り、spool mkdirが成功した。
- PID 27936をTERMで停止し、disk4をdetachしてdisk imageを削除した。mount/image残留はない。
- production plistをbootstrapし、PID 29439、SlurmdStartTime `2026-09-12T10:08:12`で再登録した。
- DRAIN reason確認後に対象nodeだけをRESUMEし、最終nodeはIDLE、CPUAlloc=0、AllocMem=0、
  AllocTRES空となった。
- recovery smoke Job 548は`PC-210.local`とmarkerを出力し、job/batchとも`COMPLETED 0:0`、
  stderr 0 byteだった。
- 最終queueと`slurmstepd`は空、launchdはrunning、launchd/PID fileは29439で一致した。
- production `slurm.conf`、`gres.conf`、plistと全試験入力のbefore/after SHA-256は完全一致した。

```text
SMD113_SPOOL_ENOSPC_COMPLETE failure_job=547 smoke_job=548 old_pid=94504 candidate_pid=27936 restored_pid=29439 production_restored=PASS run_dir=/tmp/slurm-smd113-runtime-20260912T100801
```

### 判定

Phase Aでsystem diskを使わないENOSPC生成・解放・detachを確認し、Phase Bで実際の
SlurmdSpoolDir書込失敗、payload未実行、明示的DRAIN、対象Job取消、production launchd復帰、
後続Job成功、資源・process・volume残留なしを確認した。SMD-113を`PASS`とする。

制約として、試験対象は64 MiB HFS+の隔離spoolであり、production filesystem自体の枯渇試験では
ない。またJob 547はbatch step生成前に失敗したため、accountingに`.batch` recordは存在しない。
