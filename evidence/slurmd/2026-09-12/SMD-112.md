# SMD-112 bounded memory pressure

- 状態: `PASS`
- 対象: Apple M5 Max / arm64 / macOS上の`slurmd`・`slurmstepd`
- Slurm: `26.11.0-0rc1`
- test user: `testuser`（UID/GID 3001:3001）
- production設定変更: なし
- daemon restart: なし
- package導入: なし

## Research Question

macOS版Slurmで`--mem=256M`を要求したJobが、OS全体へ危険なpressureを与えない上限内で
1,024 MiBを実際にtouchした場合、Jobはどのように扱われ、scheduler上の割当値とprocess RSSは
どう異なるか。また、終了後にJob、memory allocation、processが正常に回収されるか。

## Sourceと設定から得た仮説

`src/slurmd/slurmstepd/ulimits.c`のmacOS分岐は、Darwinで`RLIMIT_RSS`が`RLIMIT_AS`の
aliasとなり有限値を拒否するため、RSS/VSIZE rlimit設定を`!defined(__APPLE__)`の外へ除外している。
またproduction configは`JobAcctGatherType=jobacct_gather/none`で、cgroupによるmemory隔離も
使っていない。`src/slurmd/slurmd/job_mem_limit.c`のenforcementは`job_acct_oom_kill`と
job accounting実測値を前提とする。

従って、`--mem=256M`はscheduler accountingには残るが、macOS kernel側でJob processを
256 MiBへ強制せず、1,024 MiBのresident allocationが成功すると仮説を置く。これは既知制約を
実測する試験であり、memory limitの成功を示すものではない。

## 安全設計

- 実行直前にnodeが`IDLE`、未割当、queue空であることを確認する。
- `memory_pressure -Q`の物理memoryが64 GiB以上、free percentageが50%以上でなければ停止する。
- fixtureは最大値をsource内で1,024 MiBに固定し、物理memoryの2%以下であることをdriverでも確認する。
- 256 MiBずつ4段階でpageをtouchし、各段階でdriverのackを待つ。
- 各waitは120秒、Job全体は3分で自己収束する。
- 既存Jobやdaemon、設定には触れず、異常時は記録したJob IDだけをcancelする。
- swap枯渇、system disk圧迫、fork storm、memory allocation failureの強制は行わない。

設計時のread-only snapshotは物理memory 137,438,953,472 bytes、page size 16,384 bytes、
system-wide free 95%だった。実行時にも同じpreflightを再評価する。

## 測定項目

1. 256、512、768、1,024 MiBの各touch完了markerと同一PID。
2. 各段階のprocess RSS、UID、command identity、Job state。
3. 各段階のcontroller `AllocMem`、`memory_pressure -Q`、`vm_stat`。
4. Job/batch accountingの`ReqTRES`と`AllocTRES`。
5. stdout/stderr、終了後process、queue、node allocation、`slurmstepd`。
6. slurmd PID/StartTime、production configとtest input hash、worker log delta。

## 成功条件

1. fixture PIDが全段階で同一、UID 3001で、全4段階を完了する。
2. peak RSSが1,024 MiB targetの75%以上かつrequest 256 MiBの2倍を超える。
3. 実行中のcontroller `AllocMem`は256 MiB、Jobは`RUNNING`を維持する。
4. Job/batchが`COMPLETED 0:0`で、Req/Alloc TRESに`mem=256M`が残る。
5. stderr、OOM、allocation failure、`_prlimit` fatal、daemon crashがない。
6. 終了後nodeは`IDLE`、CPU/memory割当0、queue・step・fixture process残留0。
7. slurmd PID/StartTimeとproduction/test input hashが不変である。

条件2～4が成立した場合の判定は`LIMIT_NOT_ENFORCED_OBSERVED`である。これはSMD-112の
安全なcharacterizationとしてはPASSだが、resource isolationとしてはnegative resultであり、
SMD-302の既知制約Evidenceとしても参照する。

## Attempt 1 — harness failure

2026-09-12 02:29 JSTの初回実行は、Job投入前の安全preflightで停止した。

```text
/usr/bin/awk: can't open file /tmp/slurm-smd112-20260912T022903/evidence/memory-pressure-before.txt
 source line number 1
error: invalid physical memory bytes=
recovery: production was not changed; test job was cancelled; inspect run_dir=/tmp/slurm-smd112-20260912T022903
```

`controller-before.txt`、`node-before.txt`、空の`slurmstepd-before.txt`、成功したclang出力までは
作成された。一方、submit marker、Job ID、Job outputはなく、production設定・daemonへの変更経路にも
到達していない。

原因はdriverの実行順序である。物理memory値を
`evidence/memory-pressure-before.txt`からparseしていたが、同ファイルを作る
`capture_pressure before`がその後に置かれていた。captureをparse直前へ移動した。

修正後は以下を確認した。

- `capture_pressure before`のsource行が最初の同ファイル参照より前にある
- 実際の`memory_pressure -Q`出力から137,438,953,472 bytesとfree 95%をparseできる
- shell構文、CのWerror build、approval/root guard、上限拒否、小規模handshakeは引き続きPASS
- accounting正例はaccept、batch memory不一致の負例はreject
- `git diff --check`: PASS
- 修正版driver SHA-256: `b0345bc33a8a46e22c7a055765a94ca734462270a153c4b10d3b6973b792db3a`

この失敗はmacOS memory機能やSlurmのfailureではなく、Job投入前に検出されたtest harnessの
順序不備である。修正版による全工程の再試験が必要なため、まだSMD-112をPASSにはしない。

## Attempt 2 — PASS

修正版を2026-09-12 09:25 JSTにproduction構成で再実行し、Job 546が全工程を完了した。

```text
stage_mib  pid    rss_kb   node_alloc_mem_mib  job_state
256        21430  263600   256                 RUNNING
512        21430  525744   256                 RUNNING
768        21430  787888   256                 RUNNING
1024       21430  1050032  256                 RUNNING
```

fixtureは全段階でPID 21430、UID 3001、同一binary・record pathを維持した。peak RSS
1,050,032 KiBは、Job要求256 MiB（262,144 KiB）の約4.01倍、1 GiB touch target
（1,048,576 KiB）の約100.14%だった。一方、controller上の`AllocMem`は全段階で256 MiB、
`CPUAlloc=1`、node stateは`MIXED`であり、Jobは`RUNNING`を維持した。

```text
546|testuser|COMPLETED|0:0|...mem=256M...|...mem=256M...
546.batch||COMPLETED|0:0||cpu=1,mem=256M,node=1
```

Job/batchは`COMPLETED 0:0`で、root recordのReqTRES/AllocTRESとbatch AllocTRESは
`mem=256M`だった。`memory_pressure -Q`はbefore、1 GiB peak、afterの全てで物理memory
137,438,953,472 bytes、free 96%を示した。

全pressure/vm/accounting/submit stderr、worker unexpected error、input diff、最終残留processは
0 byte。最終nodeは`IDLE`、`CPUAlloc=0`、`AllocMem=0`、`AllocTRES`空、queueと
`slurmstepd`も空だった。slurmd PID 94504、`SlurmdStartTime=2026-09-11T23:11:50`、
production configと3入力hashは不変だった。

以上からSMD-112の安全なmemory pressure試験は`PASS`とする。ただしresource isolationの
分類は`LIMIT_NOT_ENFORCED_OBSERVED`である。`--mem=256M`はschedule/accounting値としては
正しく機能したが、このmacOS構成ではJob processを256 MiBへkernel強制していない。
この結果はSMD-302のnegative testを実測済みに更新する根拠にもなる。
