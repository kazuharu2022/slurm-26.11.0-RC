# SMD-306 `/proc`非存在時のOOM・process scan

- 状態: `PASS`
- 対象: Apple M5 Max / arm64 / macOS上の`slurmd`・`slurmstepd`
- Slurm: `26.11.0-0rc1`
- worker設定: `proctrack/pgid`、`jobacct_gather/none`
- test user: `testuser`（UID/GID 3001:3001）
- production binary: candidateと同一SHAのため差替えskip
- package追加: なし

## Research Question

Linux procfsを持たないmacOSで、通常のstep起動ごとのOOM調整、PGID process列挙、
process tree cancelを反復しても、未guardの`/proc`参照、stepd異常終了、process残留が
発生しないか。またsource全体の関連経路に、通常試験だけでは見えないmacOS欠落がないか。

## source audit

### OOM調整

`src/slurmd/slurmstepd/mgr.c`はstepd開始時に`set_oom_adj(STEPD_OOM_ADJ)`を呼び、
`SLURMSTEPD_OOM_ADJ`が`-1000..1000`なら再度`set_oom_adj()`を呼ぶ。

`src/slurmd/common/set_oomadj.c`の既存macOS修正は`__APPLE__`をFreeBSDと同じstubへ
分岐し、Linuxの`/proc/self/oom_score_adj`と`/proc/self/oom_adj`を開かない。
したがって値なしと`-1000`、`0`、`1000`を各3回通してもprocfs errorは出ないはずである。

### 通常のprocess group列挙

`src/plugins/proctrack/pgid/proctrack_pgid.c`の既存macOS修正は
`sysctl(KERN_PROC_PGRP)`で同一PGIDを列挙し、zombieを除外する。Linux側だけが
`opendir("/proc")`と`/proc/<pid>/stat`を使う。SMD-005、SMD-006、SMD-009、SMD-109で
終了・cancel・timeout・daemon restart時のprocess回収は既に実測しているが、SMD-306では
同じ4-process treeのcancelを3回繰り返してprocfs errorと残留を改めて判定する。

### source auditで新たに発見した欠落

`src/slurmd/slurmstepd/req.c::_wait_extern_pid()`には、`REQUEST_ADD_EXTERN_PID`で追加した
外部PIDが終了した後、同一containerに残る孤児のPPIDを`/proc/<pid>/stat`から読む処理が
OS分岐なしで残っていた。macOSでは`fopen()`が失敗して黙ってcontinueするためdaemonは
落ちないが、外部PIDの孤児追跡が行われない。

今回、PPID取得を`_get_process_ppid()`へ分離した。macOSは
`sysctl(KERN_PROC_PID)`と`kinfo_proc.kp_eproc.e_ppid`を使い、それ以外のOSは既存の
procfs parserを維持する。process消滅raceは両分岐とも`false`で読み飛ばす。

この経路の実運用callerは`pam_slurm_adopt`である。今回のmacOS構成にはPAM adoptを
導入していないため、実際の`REQUEST_ADD_EXTERN_PID` lifecycleは未実測であり、build成功を
もってruntime PASSとはしない。SMD-306のruntime判定は現在構成のOOM・PGID scanに限定し、
PAM adoptはoptional integrationとして別途残す。

### 今回の構成で選択していない経路

- `proctrack/linuxproc`、cgroup、RAPL、NVIDIA系pluginの`/proc`参照
- parallel debugger用`pdebug.c`の`/proc/<pid>/status`確認
- `argv[0]`が相対pathのときだけ使う`slurmd.c`の`/proc/self/exe`

productionは`proctrack/pgid`、`jobacct_gather/none`、絶対pathからのlaunchd起動であり、
これらをSMD-306の正常経路Evidenceへ混ぜない。

## 修正

- [`req.c`](../../../src/slurmd/slurmstepd/req.c)
  - Appleだけ`sysctl(KERN_PROC_PID)`でPPID取得
  - Linux等は既存`/proc/<pid>/stat` parserをhelperへ移動
  - self PID・既存accounting task除外後にPPIDを取得
- [`smd306_proc_absence_payload.sh`](../../../contribs/macos-tests/smd306_proc_absence_payload.sh)
  - `/proc`非存在、UID/GID、OOM環境を各jobで記録
  - normalでは4 childの正常回収、cancelでは4-process treeを生成
- [`smd306_proc_absence_driver.sh`](../../../contribs/macos-tests/smd306_proc_absence_driver.sh)
  - normal 12件、cancel 3件、合計15件
  - accounting、stderr、worker log delta、PID、node資源をfail-closedで検査
- [`smd306_install_and_test.sh`](../../../contribs/macos-tests/smd306_install_and_test.sh)
  - active stepなしを確認し、`slurmstepd`だけを時刻付きbackup後に原子的に差し替える
  - stress失敗時は旧binaryを自動復元する
  - `slurmd`は再起動しない

## runtime成功条件

1. 実行前にcontroller UP、node IDLE、割当0、queue・stepdなしである。
2. candidateだけをproduction `slurmstepd`へ入れ、owner/modeが`root:wheel 0755`である。
3. 12 normal jobでOOM値4条件を各3回通し、全job/batchが`COMPLETED 0:0`になる。
4. 3 cancel jobで各4 PIDが同一PGID・UID 3001で生存し、cancel後に全12 PIDが消える。

6. 最終node IDLE、割当0、queue・stepd・試験process残留0である。
7. slurmd PID/StartTimeとproduction config/source hashが不変である。

### normal job

Jobs 564～575の12件は、OOM環境`UNSET`、`-1000`、`0`、`1000`を各3回実行した。
driverは各jobのstdoutについて`proc_state=ABSENT`、指定OOM値、UID/GID 3001:3001、
4 child完了markerを個別照合し、stderr 0 byteを確認した。accountingは12 jobと12 batchの
全24 recordが`COMPLETED 0:0`、各`cpu=1,mem=64M,node=1`だった。

job output directoryはtestuser所有0700であり、Codex observerからは直接再読込できなかった。
ここはroot driverによる個別検証とterminalのphase markerをEvidenceとし、observerが直接確認した
accounting、worker log、node/process/hashとは区別する。

### process scanとcancel

Jobs 576～578では各4 process、合計12 PIDをcancel前に保存した。各組はUID 3001かつ
同一PGIDで、zombieはなかった。

signal 15と`stepd_cleanup: done with step`が記録された。

## Evidence境界

今回のruntime stressがPASSしても証明できるのは、現在選択中のOOM stubと
`proctrack/pgid`通常経路である。`pam_slurm_adopt`からの外部PID追加、parallel debugger、
未選択pluginのmacOS対応は未検証のまま残す。
