# SMD-402 Open MPI mixed-architecture multi-node runtime Evidence

日時: 2026-09-24 13:11–13:27 JST

最終状態:

```text
PASS_MIXED_ARCH_OPENMPI_MULTINODE / ARCH_HETEROGENEOUS_DATA_LAYOUT_HOMOGENEOUS
```

## 対象と境界

承認済みPhase 2として、Ubuntu x86-64 controller/workerとMac arm64 workerを同じ
Slurm allocationへ割り当て、各architectureでnative buildしたOpen MPI 5.0.11を
同じlogical prefix `/tmp/smd402-openmpi-5.0.11/install`から起動した。

成功条件は次のとおり。

- `mpirun`へrank数を渡さず、Slurmの2 node・2 task・1 task/nodeを継承する
- `MPI_Init`、Bcast、Allreduce、ring Sendrecvが2 architecture間で成功する
- success job/stepが`COMPLETED 0:0`
- 実行中jobを`scancel`し、両rank PIDが各nodeで消滅する
- queue、node allocation、MPI/PRRTE processが残らない
- production config/binary、daemon PID、service状態を変えない

この試験はx86-64とarm64というarchitecture heterogeneityを扱う。一方、両hostは
little-endian、pointer/long 8 bytes、int 4 bytes、double 8 bytesであり、異なるendianや
異なる基本型sizeを扱うtrue data-layout heterogeneityは試験していない。

## 失敗試行と訂正

### Job 693: Attempt 1

`btl=self,tcp`で起動した。allocationとPRRTE stepは両nodeへ作成されたが、probe stdoutは
0 bytesのままlauncherがSIGABRTした。

```text
693|smd402-ompi-success-20260924T131130|testuser|FAILED|0:6|PC-210,ubuntu
693.0|prted||FAILED|1:0|PC-210,ubuntu
free(): double free detected in tcache 2
```

Ubuntu local 2-rank probeで`self,tcp`が停止し、default BTLおよび`self,sm,tcp`は成功したため、
最初はshared-memory BTL除外が原因候補となった。ただしこれはlocal controlの結果であり、
multi-node SIGABRTの根本原因を証明していなかった。

### Job 696: GDB診断

既存GDBでUbuntu上の`prterun`を追跡した。GDB wrapper自身が0を返したためroot jobは
`COMPLETED 0:0`だが、PRRTE stepは`FAILED 1:0`でありruntime PASSではない。

```text
696|smd402-ompi-gdb|testuser|COMPLETED|0:0|PC-210,ubuntu
696.0|prted||FAILED|1:0|PC-210,ubuntu
PRTE does not currently support multi-endian operations.
Nodename:      PC-210
Endian:        unknown
Local endian:  le
#9 prte_plm_base_daemon_callback
free(): double free detected in tcache 2
```

Macも実測probeではlittle-endianである。Open MPI 5.0.11同梱PRRTEの
`prte_hwloc_base_get_topo_signature()`は`__BYTE_ORDER`形式だけを参照し、Apple Clangが提供する
`__BYTE_ORDER__` / `__ORDER_LITTLE_ENDIAN__`形式を扱わないため、Macのsignature末尾が
`unknown`となっていた。Ubuntu側は`le`であり、daemon callbackのmulti-endian拒否経路へ入り、
そのerror pathで二重解放した。

## 隔離修正

productionではなくMacの`/tmp` isolated source/build/installだけを修正した。

```text

SHA-256=96202183be6e5ff469371dffa73e512baf5a3539e6aa7a3f06eff1cadd781566
```

`__BYTE_ORDER__ == __ORDER_LITTLE_ENDIAN__`も認識する最小修正である。再現用build driverは
Darwinだけへこのpatchを適用する。runtime driverは異なるnode topologyを明示する
`--hetero-nodes`を使用する。

## 保持したwarningと観測制限

- success/cancel起動時、Ubuntu hwlocはnon-16-bit PCI domainを無視するwarningを出した。
  upstream message自身がABIを壊すため`--enable-32bits-pci-domain`を必要時以外使わないよう
  指示しており、本試験のCPU/TCP通信は成功している。warning 0とは扱わない。
- 意図的`scancel`後、PRRTEはremote daemonとの通信喪失をstderrへ報告した。job/stepの
  CANCELLED、両PID消滅、queue/resource解放が一致するため期待したcancel経路である。
  `cancel.err`末尾にはNUL 1 byteも保持した。
- Mac `/var/log/slurm/slurmd.log`は通常ユーザーから`Permission denied`で、直接log readbackは
  行えなかった。代わりにcontroller journal、Slurm accounting、node-local PID probe、Macの
  production hash/PID/process一覧を独立確認した。
- shellcheckは未導入のため未実施。`sh -n`、unapproved gate、`git diff --check`はPASSした。
- 修正は既存isolated treeをincremental rebuild/installしてruntime検証した。更新したclean-build
  driverへのpatch dry-runと構文検査はPASSしたが、修正版driverによるarchive展開からのfull clean
  rebuildは未実施であり、runtime PASSとは分離する。
- `/tmp`の両architecture build、Attempt 1保存領域、runtime run directoryは証跡確定時点で
  保持している。cleanupは本Phaseに含めない。

## 判定

Open MPI 5.0.11の同一version・同一logical prefixを各architectureへnative buildし、Slurmの
同一allocation/同一PRRTE stepでx86-64 Ubuntuとarm64 macOS間のMPI通信、正常終了、実行中
cancel、rank PID回収、resource解放を実測した。production Slurmは変更・再起動していない。

したがってSMD-402 Open MPI extensionを
`PASS_MIXED_ARCH_OPENMPI_MULTINODE / ARCH_HETEROGENEOUS_DATA_LAYOUT_HOMOGENEOUS`
とする。異なるendian、異なるC基本型size、heterogeneous GPU collective、production prefixへの
Open MPI導入は未検証であり、このPASSには含めない。
